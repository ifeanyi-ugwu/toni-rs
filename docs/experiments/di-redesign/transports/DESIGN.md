# Transport layer: design

## 0. Principles

1. **The core's pipeline is the only pipeline.** Every transport opens an `Execution`, seeds its inputs, and calls `fw::dispatch`. No transport writes its own guard walk, error-handler walk, or panic catch.
2. **Transport crates own the wire, never the semantics.** Extraction, answers, errors, metadata, and cancellation are defined once in `fw-transport`. Each transport only says how they look on its wire.
3. **Specifications decide.** HTTP follows RFC 9110/9112/9113, problem details follow RFC 9457, SSE follows the WHATWG HTML spec, WebSocket follows RFC 6455, gRPC follows its HTTP/2 protocol spec and the canonical status codes, MQTT follows v5, AMQP follows 0-9-1 (what RabbitMQ speaks), GraphQL follows GraphQL-over-HTTP and graphql-transport-ws, and span attributes follow OpenTelemetry semantic conventions. Where no specification exists (the WebSocket message envelope, the RPC frame grammar, the backend and embedding SPIs), the design defines one and says so.
4. **Everything the wiring pass can see, it checks.** Global middleware, gateways, patterns, and gRPC methods are declared through module metadata or mounted handlers, so they're validated at `wire()` like any binding. Server builders in `main` carry only addresses, TLS, and limits.
5. **Transports may depend on tokio. The core still doesn't.** Every listed backend and broker client is tokio-based, so transport crates use tokio I/O traits. `fw-tokio` supplies the core's `Timer`, signals, and spawn helpers.
6. **Names follow std's rules.** A trait is named after its predominant method, as `Clone::clone` and `FromStr::from_str` are: `FromCall::from_call`, `IntoReply::into_reply`, `Classify::classify`, `Validate::validate`. A trait with no single method is named for its concept or role (`Iterator`, `Error`): `Transport`, `Link`, `Engine`, `Backend`, `Guard`. An error is named after its operation as users understand it, so `FromStr` fails with `ParseIntError` and `into_string` with `IntoStringError`: `ExtractError` beside `from_call`, `IntoReplyError` beside `into_reply`. An error shared by a family of operations is named after the domain (`io::Error`): `CallError`, `RpcError`, the core's `LookupError`. An error that reports a condition rather than an operation's failure is named for the condition, the class std has in `PoisonError`, written here in the past participle the core uses: `GuardRejected`, `PanicRecovered`, `TimerMissing`, `ConnectRefused`. `Closed` stays, its subject implied wherever it appears; `Redacted` is a wrapper named for what was done to its contents, not an error. `From*` builds `Self` from a source and `Into*` consumes `self`; `Try*` appears only beside an infallible sibling, so a fallible conversion with none returns `Result` under the plain name (`EventId::new`). A `From*` constructor may record its source for a later step and stay infallible: `Tls::from_pem_files` builds a `Tls` from two paths and reads neither, and `Tls::load` parses them in `prepare` (§2.7). Abbreviations are not names: `HandlerSpec`, `Inputs`.

## 2. Common to every transport

### 2.1 Handlers and keys [1][12][13]

A handler is a method on a controller, marked by its transport's attribute. One `#[routes]` impl may mix transports. DESIGN §7 already checks each handler's enhancers against its own transport's roles.

**X1: transport keys.** `Transport` gains `const KEY: &'static str` (`"http"`, `"ws"`, `"ws_connect"`, `"rpc"`, `"grpc"`). The `__handler` protocol gains one obligation: a transport's attribute must emit, next to `fn __fw_mount_<name>`, an associated constant `const __FW_KEY_<name>: &'static str = <Http as Transport>::KEY;`. An attribute macro on an impl item may emit several items, so this fits the protocol as it stands.

`#[routes]` expands first. It knows every scoped key written at the controller level (the `htpp` in `#[guards(htpp = AuthGuard)]`) and every handler name, so it emits one assertion per key, as a free `const _` after the impl naming the controller type:

```rust
const _: () = assert!(
    ::fw::__private::key_in("htpp", &[UsersController::__FW_KEY_get, UsersController::__FW_KEY_get_rpc]),
    "`htpp` is not the key of any handler's transport in this impl (handlers: get, get_rpc)"
);
```

A free `const _` is evaluated unconditionally. Inside the impl it would need a name, and a named associated constant is evaluated only where it is read, so a misspelled key would compile unnoticed. Const evaluation runs after every attribute has expanded, so the `__FW_KEY_*` constants exist by then. The assertion is spanned on the key token, which makes a misspelling a compile error (E0080) pointing at `htpp`. A generic controller is the one case a free const cannot name: there `#[routes]` emits a named associated constant and the generated `Controller::mount` reads it (`let () = Self::__FW_KEYS_CHECK_htpp;`), which evaluates it when `mount` is instantiated. `key_in` compares bytes in a loop, since a trait method is not callable in a `const fn` on stable (X11). A misspelled transport key on a controller-level entry is therefore refused at compile time.

A handler behind `#[cfg(..)]` is ordinary Rust. An attribute macro receives the `cfg` unevaluated, so `#[routes]` copies each handler's `cfg` attributes onto its checks read and its mount call, and the key assertion is a `const` block of `cfg`-gated statements rather than one `key_in` over an array literal; a handler the feature strips leaves no reference behind, and the assertion's message lists it apart ("behind `#[cfg]`: get_rpc"). A controller-level key whose every handler is gated out fails the assertion in that build, and the entry goes behind the same gate: `#[cfg_attr(feature = "rpc", guards(rpc = ..))]`, which rustc evaluates before `#[routes]` runs even when written below it.

A method's attributes are read through `cfg_attr` as well, at any depth. `#[routes]` cannot tell a transport attribute from another attribute macro by name, so it decides by position: an attribute macro written outside any `cfg_attr` makes the method a handler in every build, and when every attribute macro on the method sits inside a `cfg_attr`, the first in source order is taken as the transport attribute and the method is a handler where that attribute's predicates hold. `__handler` is appended inside a `cfg_attr` under the same predicates, after every attribute the method carries, so rustc expands it into place in exactly the builds that have the transport attribute; the mount call, the checks read and the key are gated as a `#[cfg]` handler's are, nested predicates joining as `all(a, b)`. Where the predicate fails the method is a plain method, and `dead_code` fires unless something calls it. Nothing suppresses that warning: a method nothing calls in that build is what the gate expresses. A `guards(..)`, `interceptors(..)`, `error_handlers(..)` or `meta(..)` inside a `cfg_attr` on a method is taken out of it and carried in `__handler`'s method tier behind one `#[cfg(<predicate>)]` per enclosing predicate, and the transport attribute writes each entry as one gated statement. What `#[routes]` does not take stays in the `cfg_attr`, in order, and a `cfg_attr` left empty is removed. The controller tier carries no gates, since rustc evaluates an impl's own `cfg_attr` before `#[routes]` reads it. The key assertion lists handlers gated either way under one label, "behind `cfg`". Two method-tier mistakes are refused in every build, read before the gates are evaluated: a gated enhancer or `#[meta]` on a method with no transport attribute, and a gated entry naming a key that is not the handler's transport.

Four forms are not supported, and each fails to compile rather than mounting a handler wrongly: a transport attribute inside `cfg_attr` beside an attribute macro outside one, in either order, which makes the method an ungated handler whose mount function the build without the predicate lacks; every attribute macro inside `cfg_attr` with a macro other than the transport attribute first, which gates the handler on that macro's predicate; a helper whose attribute macros all sit inside `cfg_attr`, a handler where the first predicate holds; and an enhancer or `#[meta]` inside an inner `#![cfg_attr(..)]` in the method body, which rustc refuses as an unstable inner attribute. Two live transport attributes on one method fail as they do ungated: the first consumes `__handler` and the second reports itself outside `#[routes]`. Each diagnostic states the rule it applied. A transport attribute that finds no `__handler` says `#[routes]` took another attribute for the transport attribute and how the choice is made; a `__handler` nothing consumed names the attribute macro that made the method a handler, says no transport attribute supporting `#[routes]` is present in this build, and sends a helper to a separate impl block.

**X2: impl-level shared values.** A controller-level `value = expr` becomes legal again [13]. `#[routes]` generates `impl Controller`, and its `mount` builds each impl-level value **once**, into an `Arc`. It passes them to every per-handler mount function in one `fw::__private::Shared<(Arc<V0>, Arc<V1>, ..)>`, a core tuple wrapper (`Shared(())` when there is none), one tuple position per impl-level `value` entry in the order written across the three enhancer attributes, inferred by `mount` from the expressions, since `#[routes]` cannot name a value's type: `fn __fw_mount_<name><V0: Interceptor<Http>, ..>(m: &mut Mount<'_>, shared: &Shared<(Arc<V0>, ..)>)`. The core supplies the type: a struct `#[routes]` generated would need a name unique per module, and the transport attribute on a method cannot learn the controller's name to spell it. Each per-handler function bounds the positions it uses by the role for its own transport and leaves the others unbounded, so an `http(value = ..)` entry is a position an RPC handler's function never names, and a value lacking the role fails E0277 at that handler's mount call, which the macro spans at the handler's name. The position of each `value` entry is part of the `__handler` contract, as the turbofish order of `Contribute::try_singleton` already is; the transport attribute learns it from the controller-tier tokens it receives. `EnhancerSpec` gains `guard_arc(Arc<V>)`, `interceptor_arc` and `error_handler_arc`. Each handler unsizes its own clone of the same `Arc` into its transport's role, so the role check still runs per handler. A rate limiter declared on the impl now limits the controller as a whole. The compile error from wave 2 (M 1) is removed.

### 2.2 Parameters and extraction [2][3]

```rust
/// A handler parameter built from the call.
#[diagnostic::on_unimplemented(
    message = "`{Self}` cannot be built from a `{T}` call",
    note = "a transport implements `FromCall` for its own extractors; `FromContainer` types (`Dep`, `Ext`, ...) are accepted on every transport"
)]
pub trait FromCall<T: Transport>: Sized + Send + 'static {
    /// Whether this parameter consumes the body or payload. At most one may.
    const CONSUMES_BODY: bool = false;
    /// What it reads from the container, if anything, for the wiring pass.
    fn dependencies(_d: &mut Dependencies) {}
    fn from_call(cx: &T::Cx) -> impl Future<Output = Result<Self, ExtractError>> + Send;
}
```

The pair `FromContainer` / `FromCall` names where a parameter comes from, the container or the call, and both appear in diagnostics. The generated code reads every parameter through one doc-hidden trait, `fw_transport::__private::Param<T, M>`, implemented for every `FromCall<T>` type with `M = ViaCall` and for every `FromContainer` type with `M = ViaContainer`. `M` is inferred at each parameter: a handler writes `Dep<U, Q>`, `Many`, `Ext`, `ModuleRef`, `ExecutionRef` or `Option<Dep<U>>` bare, and the core's injection-point types implement no `FromCall`, since a type implementing both traits would be ambiguous under `Param`. The dependency reads, the extraction and the body assertion all name `<P as Param<T, _>>`; the assertion sits in a constant, where autoref ranking does not run, and `<Dep<U> as FromCall<T>>` would not compile there. A dependency read passes the parameter's label, `fw::__private::HandlerParam::Named(ident)` or `At(index)`, and `Param::dependencies(d, label)` runs the type's declaration under that label through `fw::__private::handler_param` (§2.5, X18). A parameter of neither kind reads `Param`'s `on_unimplemented` note, placed at the parameter's type. Generic code over a `T: Transport` writes `Injected<S>` for the `FromCall` form of a `FromContainer` type, and `impl<T, P: FromCall<T>> FromCall<T> for Option<P>` forwards `CONSUMES_BODY` for an optional extractor and answers `None` for `Missing` and `HostMissing`; `Option<Dep<U>>` goes through the core's `Option<S: FromContainer>`. Every parameter's reads are recorded on the handler's `HandlerSpec` (§2.5), so wiring checks handler parameters like any constructor's. Execution inputs are plain `Dep<RequestHead>`, and extension values are `Ext<CurrentUser>`. The context itself is a parameter, through `impl FromCall<Http> for HttpCx`. The call extracts every parameter in order, then resolves the controller, then runs the method; a failed extraction builds no per-execution controller.

A handler takes `&self`, or `self: Arc<Self>` for a reply that outlives the call (§2.3); `&mut self` and `self` are refused at the receiver, and an alias of `Arc` is refused because the generated call passes `std::sync::Arc<Self>`.

**The single body consumer is checked at compile time and names both parameters.** For each pair of parameters, the macro emits one assertion, n(n−1)/2 of them for n parameters:

```rust
const _: () = assert!(
    !(<Json<NewUser> as Param<Http, _>>::CONSUMES_BODY && <Form<Login> as Param<Http, _>>::CONSUMES_BODY),
    "`user` and `login` both consume the body; a handler reads the body once"
);
```

It's spanned on the second parameter. Each parameter is named as the signature binds it, a destructuring pattern by its tokens: the error points at the signature, where the pattern is in front of the reader. No pair is skipped by spelling: `CONSUMES_BODY` is a property of the type, and `type Body<T> = Json<T>` consumes whatever it is called. The compile cost is one comparison per constant.

**Extraction failure has one shape everywhere**, flat, each variant carrying the parameter's name so one pattern matches it:

```rust
#[non_exhaustive]
pub enum ExtractError {
    Missing { param: &'static str },                                       // a required header, query field or path segment
    Malformed { param: &'static str, source: Redacted },                   // could not decode
    UnsupportedMediaType { param: &'static str, expected: &'static str },
    TooLarge { param: &'static str, limit: u64 },
    Invalid { param: &'static str, violations: Vec<FieldViolation> },      // validation rules failed
    HostMissing { param: &'static str, type_name: &'static str },          // an embedding host wrote no `T` for `Host<T>` (§3.8)
}

impl ExtractError { pub fn param(&self) -> &'static str; }
```

`Malformed`'s `source` is built through `AppHandle::redact` (X14), which runs the graph's own redaction over the decoder's error; the transport holds an `AppHandle` from `Mounted`. `ExtractError` implements `Classify` (§2.4), `BadRequest`, `Unprocessable` for `Invalid`, and `Internal` with the message withheld for `HostMissing`, a deployment fault rather than a bad request, so it reaches the error handlers as a `CallError` of that kind through the blanket `From`, holding the `ExtractError` as its source. An error handler reshapes it with `err.downcast_ref::<CallError>()?.source_as::<ExtractError>()`. Each transport documents its rendering in §§3–7, and HTTP adds the exact statuses 413 and 415 from the variant.

**Validation** is declarative and opt-in through the parameter type:

```rust
#[derive(Deserialize, Validate)]
pub struct NewUser {
    #[validate(length(min = 1, max = 64))] name: String,
    #[validate(email)] email: String,
    #[validate(range(min = 13))] age: u8,
}

async fn create(&self, user: Valid<Json<NewUser>>) -> Result<Created<User>, CallError>
```

`Valid<P>` is `impl<T, P: FromCall<T> + Validate> FromCall<T> for Valid<P>`, forwarding `CONSUMES_BODY` as `Option<P>` does. `Json`, `Form`, `Query` and `Path` implement `Validate` by delegating to what they wrap; a custom extractor under `Valid` writes its own impl. It runs `Validate::validate` after `P` extracts, and turns violations into `ExtractError::Invalid`, whose `param` is `P`'s outermost type without generics (`"Json"` for `Valid<Json<NewUser>>`) and whose violations name the fields.

The rules are `length(min, max)` with either bound optional, `range(min, max)` and `email`, a shape check rather than RFC 5322; several may share one attribute. `length` counts characters for text and items for a collection, chosen by autoref: a byte count would have `length(max = 64)` refuse a 40-character name in a non-Latin script, and the `validator` crate counts characters too. The cost is that a type with an inherent `len()` and no borrowing `ExactSizeIterator` does not compile under `length`. A violation's `field` is the name serde gives it, `rename` and `rename_all` applied and `r#` stripped; `flatten` and nested structs are not followed. The bridge for the `validator` crate is the `validator` feature, which exposes `validator_bridge::violations(&ValidationErrors) -> Vec<FieldViolation>`; a type that already derives `validator::Validate` writes a three-line `Validate` impl calling it. No blanket `impl<T: validator::Validate> Validate for T` is written: a blanket impl behind a feature changes coherence for every downstream crate when it turns on, and features must be additive.

### 2.3 Replies [4]

A handler returns `()`, a value, a stream, or any of those inside a `Result`. The error side always reaches the error handlers:

```rust
pub trait IntoReply<T: Transport>: Send + 'static {
    fn into_reply(self, cx: &T::Cx) -> Result<T::Reply, IntoReplyError>;
}
```

`IntoReplyError` is the conversion's own failure, a serializer refusing a value for example; it implements `Classify` as `Internal` and holds the cause as its source. A transport implements `IntoReply` for the types it owns: `Json<T>`, `Sse<S>` and `Response` on HTTP, `Frame` and `Reply` on WebSocket, `Reply` and `Data` on RPC. What a handler may _return_ is wider than that set and is stated per transport (§3.1, §4.1, §5.1, §6.1): a `Serialize` value, a stream of `Result` items or a prost message is answered through a crate-local conversion, because a blanket `impl<T: Serialize> IntoReply<Ws> for T` puts an uncovered type parameter ahead of the local marker and is refused by the orphan rule (E0210) before coherence is reached. The spelling of the return type decides nothing on any transport. For a `Result<V, E>`, the generated code probes the _type_ by autoref, at the concrete call site:

```rust
let out = Self::get(&this, a, b).await;              // whatever the return type is spelled as
(&&&::fw::__private::IntoReplyProbe::new(out)).into_reply::<Http>(&cx)
```

The probe has three arms. Every error the first arm accepts the second accepts too, a `CallError` being an `Error`, so the arms are not disjoint and the one reached first wins. Method lookup tries the impl on `&&IntoReplyProbe` first, then `&IntoReplyProbe`, then the bare type, so each arm sits one reference deeper than the priority order reads:

- `Result<V, E>` where `E: Into<CallError>`, on `&&IntoReplyProbe<Result<V, E>>`: `Err` becomes `BoxError::from(CallError::from(e))`. Through the blanket `From` (§2.4) this catches every `Classify` error, a `CallError` itself, and a user type with its own `From<MyErr> for CallError`.
- `Result<V, E>` where `E: Into<BoxError>`, on `&IntoReplyProbe<Result<V, E>>`: `Err` is boxed unchanged.
- Any `V: IntoReply<T>`, on `IntoReplyProbe<V>`: answered as the value.

The ranked methods take `&self`, so the value sits in a `Cell<Option<_>>`, as the core's factory probe already does. The compiler resolves a type alias (`type ApiResult<T> = Result<T, ApiError>`) before method resolution, so an alias takes the same arm as the plain `Result`. In the value API, `r.map_err(CallError::from)` does the same thing explicitly.

**Streaming returns and `'static`.** A reply outlives the handler call, and on edition 2024 an opaque return type captures `&self`'s lifetime whatever the hidden type borrows. The transport attribute appends `+ use<>` to every opaque type in a handler's return position, inside an `async fn`'s return type included, unless the opaque type already names a `use<..>` or a lifetime, which is left as written. A stream that borrows `self` then fails inside the handler body.

A handler with a type or const parameter of its own is refused at compile time, at its name: the generated call, the dependency reads and the checks constant name each parameter's type outside the method, where the method's parameters are out of scope and nothing at the call could infer them. A generic _controller_ works, and on one `#[routes]` rewrites a handler's opaque returns to `+ use<T, N, ..>` over the impl's type and const parameters. The idiom for a stream that needs the controller is `self: Arc<Self>` as the receiver, a stable arbitrary self type, so the stream captures the `Arc` instead of borrowing: `async fn watch(self: Arc<Self>, ..) -> impl Stream<..>`. The generated call already holds the controller in an `Arc`.

**Errors in the middle of a stream (X7).** An `Err` from the outer `Result` goes through `dispatch`'s error handlers like any other error. `dispatch` returns the reply without pulling the stream, so an SSE handler's headers are never held back for its first event, and every item error, the first included, takes the late path: an `Err` _item_ cannot change a status. The core gains `fw::dispatch_late(handler, cx, err) -> LateOutcome`, which runs the same error handlers with `cx.exec().is_late() == true`:

- A handler returning `Err(e2)` reshapes the error, and the transport renders `e2` in its mid-stream form (§§3–6).
- A handler returning `Ok(_)` is ignored and logged, and the original error renders canonically. An `Ok` written for the pre-stream case is a failure rendering, and ending the stream cleanly on it would tell the client "complete" when the stream failed.
- A clean end is explicit: `Err(fw::EndStream.into())` ends the stream as if it had returned `None`. `EndStream` is a unit struct an error handler constructs, and the one public error type without `#[non_exhaustive]`: a unit marker has nothing to add later. It ends the stream when it is the error the walk ends with, an unclaimed `EndStream` item error included; one wrapped inside another error renders as that error.

### 2.4 One error model [5]

```rust
#[non_exhaustive]
#[derive(Clone, Copy, PartialEq, Eq, Hash, Debug)]
pub enum ErrorKind {
    BadRequest, Unauthorized, Forbidden, NotFound, Conflict, Unprocessable,
    TooManyRequests, Timeout, Unavailable, Unimplemented, Internal,
}

/// A domain error that knows its transport-neutral kind.
pub trait Classify: std::error::Error + Send + Sync + 'static {
    fn classify(&self) -> ErrorKind;
    fn public_message(&self) -> Cow<'_, str> { self.to_string().into() }
    fn details(&self) -> Details { Details::default() }
}

/// The one concrete error every transport renders.
pub struct CallError { kind: ErrorKind, message: String, details: Details, source: Option<BoxError> }

impl CallError {
    pub fn new(kind: ErrorKind, message: impl Into<String>) -> Self;
    pub fn unauthorized(challenge: impl Into<String>) -> Self;   // `Unauthorized` carrying its own `WWW-Authenticate` challenge
    pub fn from_boxed(err: BoxError) -> Self;                    // the recogniser, below
    pub fn with_details(self, d: Details) -> Self;
    pub fn kind(&self) -> ErrorKind;
    pub fn source_as<E: Error + 'static>(&self) -> Option<&E>;   // reach the domain error
}

impl<E: Classify> From<E> for CallError { /* keeps `e` as the source */ }
```

`#[derive(Classify)]` with `#[classify(not_found)]` is sugar for the trait impl; a derive's helper attribute is scoped to it, so `#[classify(..)]` sits beside thiserror's `#[error(..)]`. The attribute goes on each variant, or on the enum as the default for the variants without one; a variant left without a kind is a compile error at its name, every such variant reported in one compile. The blanket `From` is what makes `?` work: inside a function returning `Result<_, CallError>`, a `Classify` error converts itself. It compiles because **`CallError` never implements `Classify`**: with that impl the blanket would collide with std's `impl<T> From<T> for T` (E0119, "conflicting implementations of trait `From<CallError>` for type `CallError`"), which is why `CallError` carries an inherent `kind()` instead. The trait's documentation states the rule, since no `on_unimplemented` can carry it.

`Details` is a list of typed entries chosen to map one-to-one onto `google.rpc` error details, so gRPC gets them natively and the other transports get stable JSON:

```rust
#[non_exhaustive]
pub enum Detail {
    FieldViolations(Vec<FieldViolation>),      // google.rpc.BadRequest
    ErrorInfo { reason: String, domain: String, metadata: BTreeMap<String, String> },
    RetryAfter(Duration),                      // google.rpc.RetryInfo; HTTP Retry-After
    Help(Vec<Link>),
    Json(serde_json::Value),                   // anything else; gRPC carries it as a google.protobuf.Value packed in an Any
}
```

**Recognising a `BoxError` at render time.** `CallError::from_boxed(BoxError)` walks the error and maps the core's own errors. It is a named constructor rather than a `From<BoxError>` impl: coherence would accept the impl, since `Classify` is local and `Box<dyn Error>` can never implement it, but a recogniser that walks an error should not run invisibly on every `?`. It takes the error by value because that is what `source` stores and what the error handlers hand on.

| Error                                                    | Kind                                                                                                                       |
| -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `CallError`, bare or boxed by the reply probe            | its own                                                                                                                    |
| `ExtractError`                                           | `BadRequest` or `Unprocessable`                                                                                            |
| `GuardRejected`                                          | `Forbidden`                                                                                                                |
| `PanicRecovered`, and anything `fw::is_panic` recognises | `Internal`, with a generic message                                                                                         |
| `LookupError::Construct { reason: Errored(r) }`          | recurses into `r.downcast_ref::<CallError>()`, so a constructor's "tenant not found" becomes 404, as DESIGN §10.2 requires |
| `Closed`, `LookupError::Closed`                          | `Unavailable`                                                                                                              |
| anything else                                            | `Internal`, with the message withheld                                                                                      |

A passed deadline is not in the error a handler returns: the reason lives on the execution (X5), so each transport tests `cx.exec().cancel_reason()` before calling `from_boxed` and renders `Timeout` for `CancelReason::Deadline`. One deadline rule holds on every transport that has a deadline. When the clock wins, the pipeline is dropped at its current await, the execution is cancelled with `Deadline`, and the error handlers run with a `Timeout` `CallError` under the server's `timeout_grace`, a `Bound` of one second at `Default`; when the grace passes first, the canonical rendering is written without them. HTTP's route timeout (§3.6), RPC's `deadline-ms` (§5.2) and gRPC's `grpc-timeout` (§6.2) each follow it, so an application that reshapes every error into its own envelope reshapes its timeouts too, and one that logs or counts errors sees them. The grace covers a deadline that passes before the reply begins, and what the handlers answer is delivered when it is a single reply produced within it. A streamed answer is not delivered: it is ended with the canonical `Timeout` rendering, logged at `warn` as "an error handler answered a timed-out call with a stream; the stream was ended at the deadline": the grace bounds the handlers and not a stream they return, and a caller at its deadline has stopped reading. Each transport defines a single reply by its own protocol. On RPC it is `Reply::One` or `Reply::None`, and a `Reply::Many` is a stream told at once (§5.2). On gRPC it is one length-prefixed message, and a second message, or a body still open at the grace's end, is a stream (§6.2). On HTTP, which has no message boundaries, it is a body that completes within the grace, and a body still open at the grace's end is a stream (§3.6). On gRPC and HTTP the error handlers and the body share the one grace, so the body is read under what the handlers left of it. One passing while a streamed reply is written ends the stream in the transport's mid-stream form, offered to no error handler: once a stream has begun no handler can change its status, and an item's error already takes the late path (§2.3). The execution is cancelled before the pipeline is dropped, so a handler's future dropped at the deadline reads `Deadline` from its execution. A caller enforcing the same deadline on its own side, tonic's `Channel` among them, has stopped reading by the time the handlers answer; the grace serves the application's log line, count or reshaping, and a caller enforcing no deadline of its own reads the answer.

### 2.5 Declared metadata [6]

```rust
#[routes]
#[meta(RequiresRole::any(["staff"]))]
impl AdminController {
    #[fw_http::delete("/users/{id}")]
    #[meta(RequiresRole::any(["admin"]), RateClass::Strict)]
    async fn delete(&self, id: Path<u64>) -> Result<NoContent, CallError> { /* ... */ }
}
```

Metadata values are plain `Send + Sync + 'static` values, built once at mount. `meta` is in the `#[routes]` inert list: `#[routes]` parses it at both tiers and carries it in the protocol as `__handler(name, controller(..), method(..), meta(controller(..), method(..)))`, and a method carrying `#[meta]` alone is not a handler. `fw` exports a `meta` attribute macro whose body is the error "goes below `#[routes]`", so a stray `#[meta]` outside a `#[routes]` impl is a compile error.

**X3: handler information on the execution.** `Mount::handler` takes a `HandlerSpec<T, H>` builder instead of positional arguments, named as the core's `EnhancerSpec` is: `.controller(spec)`, `.method(spec)`, `.meta(Metadata)`, `.route(impl Into<Cow<'static, str>>)`, `.shape(Shape)` and `.dependencies(Dependencies)`. The generated code fills `.dependencies` from each parameter's `FromCall::dependencies`, and the wiring walk adds those reads to its roots as it adds a closure's, so a handler reading `Dep<RequestHead>` on an RPC controller, or `Dep<Foo>` its module cannot see, fails at `wire()` rather than at the first call, the report naming the parameter by its identifier (``UsersController::get (param `svc`)``) whether the call or the container builds it. The identifier is written with `r#` and `mut` stripped: `mut r#type` names ``param `type` ``. A destructuring pattern has no identifier and is named by its position among the parameters after the receiver, from 1: `Injected(svc): Injected<Dep<Unbound>>` written third reports `param #3`, a number the reader can count in the signature. A `FromCall` impl declaring two reads has both named after the one parameter. The label travels as `fw::__private::HandlerParam { Named(&'static str), At(usize) }`, and `fw::__private::handler_param(d, param, declare)` runs the declaration and relabels every record it added (X18); `FromCall::dependencies(d)` carries no label of its own, and a transport crate's impl declares its reads unnamed. The compile-time body check (§2.2) names a pattern by its tokens instead: that error points at the signature, and a wiring report has no span to point at. A parameter's reads take no part in the cycle check or the needs-execution pass: a handler reading `Ext<T>` makes nothing per-execution. `route` takes a `Cow` so a path can be built at runtime. For a configured module the common need is a prefix: `ModuleDef::controller::<C>()` returns a handle with `.at(prefix)`, a runtime value applied to every HTTP route and every gateway path of that controller, which covers GraphQL and health endpoints without exposing `Mount` closures. The prefix joins as a route joins: one `/` between the two, the prefix's trailing slash dropped, so `.at("/graphql")` with a gateway at `/` serves `/graphql`. An RPC pattern and a gRPC method path ignore it: a pattern is a subject or topic a caller names in full, and a gRPC path is its proto's, so a prefix on either would move a handler to a path no client dials. Which transports read it is declared on the marker, **X25: `Transport::READS_PREFIX: bool`**, `false` unless a transport declares it: `Http`, `Ws` and `WsConnect` answer `true`, `Rpc` and `Grpc` keep the default. The default is `false` because the refusal exists for the silent no-op: a transport that joins no prefix and does not know the constant then ignores nothing, and one that joins prefixes and forgets the constant is refused the first time someone sets one, which names the controller and the transport. `Ws` answers `true` though a `#[message]` handler's events carry no prefix, because every controller with one also mounts its gateway's connect handler, whose path does, and a `Ws`-only declaration list, which a hand-written mount can produce, would otherwise be refused. A controller whose handlers all belong to transports answering `false`, or which mounts no handler, has a prefix nothing reads, and the freeze refuses `.at(..)` on it as a wiring error naming the controller, the prefix, its handlers' transports or "it mounts no handler", and the `.at(..)` call's location, the method being `#[track_caller]`; a controller mixing HTTP routes with gRPC methods keeps its prefix for the routes, and one whose handlers all sit behind a `cfg` that is off is refused in that build alone, as its routes are absent in that build alone. A case a prefix cannot express, per-route paths from configuration or one controller mounted twice, has no spelling; a `controller_with(closure)` exposing the mount is the form to add when one appears. `dispatch` sets the mounted handler's `HandlerInfo` on the execution before the first guard runs, so enhancers read it through `cx.exec().handler()`:

```rust
impl Guard<Http> for RoleGuard {
    async fn can_activate(&self, cx: &HttpCx) -> Result<bool, BoxError> {
        let info = cx.exec().handler().expect("set by dispatch");
        let Some(required) = info.meta::<RequiresRole>() else { return Ok(true) };  // most specific wins
        Ok(required.allows(cx.ext::<CurrentUser>()?.roles()))
    }
}
```

- `info.meta::<T>()` returns the method's declaration if there is one, otherwise the controller's.
- `info.meta_all::<T>()` lists both tiers, method first.
- `info.entries()` lists every declaration, as (type name, tier).
- `AppHandle::handlers()` lists every mounted handler with its transport key, route or pattern, and metadata. That supports permission reports and generated documentation.

**X24: metadata that names its transport.** A metadata type that means something on one transport alone names it through `fw::TransportMetadata { type Transport: Transport; }`: `fw_http::Timeout` and `fw_http::BodyLimit` name `Http`. A type that implements it is refused on every other transport at compile time, where it is written. The transport attribute knows its transport, so for each `#[meta]` value at either tier it binds the value to a local, emits one autoref-ranked probe on that local, `let (): () = (&&&fw::__private::MetaProbe::<Http, _>::new(&value)).check();`, and then records it, so an expression with side effects runs once. The probe has three arms, imported anonymously: `MetaSame` on `&&MetaProbe<T, V>` where `V: TransportMetadata<Transport = T>`, which answers `()`; `MetaOther<T, U>` on `&MetaProbe`, which answers the type `fw::__private::MetaMismatch<Http, Rpc>`, so the `let (): ()` fails E0308 at the value with both transports in the message: `#[meta(Timeout::after(..))]` on an RPC handler fails where it is written, in an application that binds no HTTP server too, which a check in HTTP's `prepare` would never see; and `MetaAny` on the bare `MetaProbe`, which answers `()` for a value implementing no `TransportMetadata`, so a user's own `RequiresRole` is valid on every transport and needs no impl. `TransportMetadata: Send + Sync + 'static`, which every metadata value is. The probe is written once, in `fw-handler-codegen`, as `emit::metadata(meta, paths)`, and takes the transport's `Paths` for the marker it names; every transport's attribute emits it.

### 2.6 Cancellation and stream ends [7]

**X5: cancellation reasons.** The core gains `cancel_with(CancelReason)` on `Execution` and on `ExecutionRef`, since a disconnect is noticed in a task holding a clone, and `ExecutionRef::cancel_reason() -> Option<CancelReason>`. The reason sits in a write-once slot beside the cancellation signal. `cancel()` stays, as `cancel_with(CancelReason::Explicit)`, so a cancelled execution never answers `None`; the drain's end writes `Drain`:

```rust
#[non_exhaustive]
pub enum CancelReason { Disconnected, ClientCancelled, Deadline, Drain, Explicit }
```

Each transport fires the reason its wire tells it:

- `Disconnected`: the backend observed the peer close the connection or reset the stream, through a dropped response body, a closed connection or, on HTTP, an h2 `RST_STREAM`. The server dropping an unread request body is not one. On RPC a link that loses a caller with calls in flight, a TCP connection closing, delivers a `cancel` for each with no reply path, which the server reads as this reason (§5.3).
- `ClientCancelled`: a WebSocket or RPC `cancel` frame, or a gRPC caller abandoning its call. On gRPC the reason covers every abandonment hyper reports, the call's future dropped before it answered and the reply body dropped before its end alike: hyper reports neither the reset's error code nor whether the connection closed, and a gRPC caller that gives up resets with `CANCEL`, so naming the common case is the honest reading and `Disconnected` is never fired there.
- `Deadline`: a passed `grpc-timeout`, RPC `deadline-ms` header, or configured route timeout. The error handlers run under the server's `timeout_grace` on all three (§2.4).
- `Drain`: the core's end of the drain.
- `Explicit`: `cancel()` by whoever holds the execution.

**Clean end versus cut off.** Every streaming answer is wrapped in `fw_transport::Tracked<S>`, which records one of two outcomes:

- `Completed`: the stream returned `None` and the transport finished writing.
- `CutOff(reason)`: dropped before that.

The handler or an interceptor registers for the outcome with `cx.exec().on_stream_end(|outcome| ..)`, a callback the core runs synchronously when the reply stream finishes. It is runtime-free, needs no spawned task, and works from an interceptor, which returns the reply before the stream is consumed and so could not await it. The outcome is the reply stream's; an inbound stream's end is already visible to the handler that reads it. On the wire, each transport uses its protocol's own end marker:

- HTTP/1.1: the terminating zero-length chunk, versus a closed connection.
- HTTP/2: `END_STREAM`, versus `RST_STREAM`.
- gRPC: trailers with `grpc-status: 0`, versus a non-OK status or a reset.
- RPC: an `end` frame, versus an `err` frame or a cut link.
- WebSocket: a `complete` envelope, versus an `error` envelope or a close frame.

SSE has no end marker in its specification, so a client can't tell a clean end from a cut-off from the protocol alone. The server side still can. `Sse::end_event("end")` adds an opt-in final named event for clients that want the distinction. It's off by default, because the specification doesn't define one.

### 2.7 Binding, TLS and configuration order [9][10]

```rust
pub enum Endpoint {
    Addr(SocketAddr),                     // "0.0.0.0:8080"; port 0 allowed
    Inherited(ListenerName),              // a socket from LISTEN_FDS (systemd socket activation)
}
```

A server builder takes text, an `Endpoint` or a `SocketAddr` (`impl Into<EndpointSpec>`): `Server::new("0.0.0.0:0")`, `Endpoint::inherited("http")` (matched by `LISTEN_FDNAMES`) and `Endpoint::inherited_index(0)` cover the three cases. Text resolves in `prepare`: `main` writes no `?` on an endpoint, and one startup reports every failure together. An inherited socket is accepted only when `LISTEN_PID` equals the process ID, which follows the systemd protocol; a mismatch fails `prepare` as `PidMismatch`, where `sd_listen_fds` would answer no sockets, a `Missing` naming the endpoint would hide the cause. The environment is read only when an endpoint is inherited, and an address-only server under a stale `LISTEN_PID` is unaffected; no `LISTEN_PID`, no `LISTEN_FDS`, or `LISTEN_FDS=0` is no sockets. `fw-net` sets `FD_CLOEXEC` on every inherited socket and leaves `LISTEN_FDS`, `LISTEN_FDNAMES` and `LISTEN_PID` in the environment: in edition 2024 `std::env::remove_var` is `unsafe` because it races with other threads, and under `#[tokio::main]` the runtime's threads exist before user code runs. The protocol covers the stale case without it, since a child spawned later fails the `LISTEN_PID` check; the documentation says why the variables stay.

Every inherited descriptor is vetted before any is adopted, through a borrowed descriptor, so a `LISTEN_FDS` that overstates the count and reaches the runtime's own descriptor is refused without closing it. A descriptor passes when its `SO_TYPE` is `SOCK_STREAM`, its local address is IPv4 or IPv6, and it is listening; one failing descriptor fails the activation as `NotListening { index }`, adopting none. The listening read is per platform. Linux, Android, FreeBSD, Fuchsia and AIX read `SO_ACCEPTCONN` through socket2. Apple targets read `getsockopt(IPPROTO_TCP, TCP_CONNECTION_INFO)` and compare `tcpi_state` with `TCPS_LISTEN`, because xnu answers `ENOPROTOOPT` for `SO_ACCEPTCONN` on every TCP socket, unbound, bound and listening alike, while defining the constant in its headers. DragonFly, NetBSD and OpenBSD read `SO_ACCEPTCONN` through `libc`; those kernels were not checked to serve it, so `ENOPROTOOPT` from the read falls through to the fallback below rather than refusing every inherited socket. Every other Unix target keeps a fallback, a nonzero bound port, and logs at `warn` when it accepts a descriptor on that basis, since a socket that never called `listen` then fails at its first accept instead of at `prepare`; a port of 0 refuses without a log. Any other error from a listening read refuses the descriptor. Off Unix, an inherited endpoint fails `prepare` as unsupported, and `Endpoint::Addr` is unaffected.

**X6: two-step binding.** `Server` gains `prepare(&mut self, Mounted<'_, T>) -> impl Future<Output = Result<(), BoxError>> + Send`. `listen()` changes its order to:

1. Call `prepare` on **every** server. That's route-table construction, duplicate checks, TLS loading and key/certificate matching, CORS validation, endpoint parsing, and checking that inherited sockets exist. Every failure is collected and reported together as `StartupError::Configure(ConfigureErrors)`, a new variant (`StartupError` is `#[non_exhaustive]`) mirroring `Wiring(WiringErrors)`, one `ConfigureError { transport: TypeName, source: Redacted }` per server whose `prepare` failed; each transport's `prepare` answers one error listing its own failures, the way `WiringErrors` does. Nothing has bound yet, so a configuration error is always reported before a port conflict. A `prepare` error whose text names types is a `PrepareError` (DESIGN §10.2), boxed: the names as `TypeName`s, and a closure writing the text given the set of names to write in full. When `listen()` builds the report it downcasts each server's error, runs one `TypeName::colliding` pass over every failing transport and every name a `PrepareError` carries, and writes each `PrepareError` against that set before the entry's text is redacted; a server answering a plain error keeps its text, and its transport still enters the pass. Two different types printing alike anywhere in the report, `a::User` from one transport and `b::User` from another, or two transports whose markers share a last segment, print with their full paths in every entry.
2. Call `bind` on each server in order. A server's `bind` is all-or-nothing for its own listeners: it closes any listener it opened before returning `Err`. `listen()` then closes the servers already bound, which it already does. So nothing is ever left half-bound.

`Server::bound(&self) -> Vec<BoundAddr>` reports actual addresses, and `App<Bound>::addresses()` gathers them, so port 0 reports the port the OS chose.

**TLS** uses rustls. `fw_net::Tls::from_pem_files(cert, key)` and `Tls::from_pem(..)` record their source and return a `Tls`; `Tls::load` reads and parses it in `prepare`, so a bad certificate, a key that doesn't match, or an unreadable file fails startup as `Configure`, never in `main` and never inside the serve loop, and a PEM error from a file names the file. ALPN is set per transport (`h2` and `http/1.1` for HTTP, `h2` for gRPC). The standalone WebSocket server (`wss`) and the TCP link take the same `fw_net::Tls`. Broker links take their client libraries' TLS configuration. UDP has no `tls` method at all, because DTLS isn't supported, so trying it is E0599.

### 2.8 Load shedding [11]

`fw_transport::Admission` is a runtime-free semaphore built on `async-lock`, with two counters: one per server and one per connection where a connection exists. Over the limit, each transport refuses in its protocol's own way. §§3–6 list the refusals. Where a refusal carries `Retry-After`, the value is the server's `.shed_retry_after(..)`, one second unset.

### 2.9 Spans [14]

Each transport wraps `dispatch` in a `tracing` span, created by `fw_transport::span::call(..)`. Span names and attributes follow the OpenTelemetry semantic conventions:

- HTTP: the span is named `GET /users/{id}`, with `http.request.method`, `http.route`, `url.path`, `url.scheme` and `http.response.status_code`; under a mount prefix (§3.8) the name and `http.route` carry the full route, `/api/users/{id}`, and `url.path` is the `embed::OriginalPath` the adapter inserted where one is present and the path the app received otherwise.
- RPC: `rpc.system` (`"fw"`), `rpc.method` (the pattern) and `messaging.system` for brokers, with the registry's values, `nats`, `redis`, `rabbitmq`, `mqtt` and `kafka`; TCP and UDP record none.
- gRPC: the span is named `$package.$service/$method`, with `rpc.system = "grpc"`, `rpc.service`, `rpc.method` and `rpc.grpc.status_code`.
- WebSocket has no convention of its own. A message's span is named after the event, `chat.send`, with `ws.event = "chat.send"` and `otel.name` the same; the connect phase's span is named `ws.connect` and carries `url.path`.

Every span also carries `fw.transport` (the key) and `fw.handler`. `span::call` declares every field empty up front, so a transport sets what its wire tells it and no field is added per transport.

### 2.10 Execution inputs without user imports

**X4: transports declare their own inputs.** `Transport` gains `fn inputs(d: &mut Inputs) {}`. The freeze calls it once per transport type, the first time a handler of that transport mounts, and records each input with that transport as its seeder and `InputOrigin::Transport { name, at }` as its origin, `name` the marker type's `TypeName`, so users never import a module to declare inputs and no transport ships an input module. A declaration arriving by both paths, a module's `m.input::<T>().seeded_by::<Tr>()` and a transport's `inputs`, with the same `(key, seeder)` is one declaration rather than a duplicate. **X19: an input several transports seed.** Each of those transports declares it and names the others: `Inputs::input::<T>()` keeps its shape and gains `also_seeded_by::<U: Transport>()`, applying to the last `input` written, so `Ws::inputs` writes `d.input::<SessionHandle>().also_seeded_by::<WsConnect>()` and `WsConnect::inputs` writes the mirror. The freeze merges two declarations of one key whose seeder sets are equal into one `InputDecl` carrying both seeders, the declaring transport first; the per-handler check passes a handler of any seeder, and the declaration's origin is the first transport's, which is what a report names, an `InputNotSeeded` carrying that first seeder alone. A module's `seeded_by::<Tr>()` naming one of a transport's several seeders is the same declaration too: an earlier module entry in the graph is widened to the transport's full set, so a handler of every seeder passes, and a seeder outside the set stays `InputConflict`. An `also_seeded_by` with no `input` written before it is a no-op, since the core may not panic there and no wiring error names the case. A second transport declaring a key another transport declared with a different seeder set, a transport's declaration beside a module's with another seeder, or beside a single binding under the key, is the wiring error `InputConflict { key, first, second }`, each side an `InputOrigin` (DESIGN §10.2): the transport that declared it, the module and seeders that declared it, or the module that bound the key, each with the call's location: a report prints "declared by transport `Http`" rather than inventing a module, the marker in full where the report's pass finds a different one printing alike (DESIGN §10.1), and a test matches the parts. Inputs only modules declare keep `DuplicateBinding`:

- HTTP: `RequestHead`, `ClientAddr`.
- WebSocket: `ConnectionInfo`, `UpgradeHead`, `SessionHandle` (§4.1), declared by `Ws` and by `WsConnect`, each `also_seeded_by` the other, which the freeze merges into one declaration.
- RPC: `CallHeaders`, `LinkInfo`.
- gRPC: `GrpcMetadata`, `PeerAddr`.

The per-handler input check from DESIGN §6.4 then works across transports unchanged. A transport whose handlers mount nowhere declares no inputs, so in such an app a non-optional `Dep<RequestHead>` reads as a missing dependency rather than an unseeded input.

**X8: routing to a module after the execution opens.** The pre-dispatch stage's unscoped entries (§3.3) run before the controller, and so before its module, is known. The core gains `Execution::route_to(&ModuleRef)`. It's callable once, by the holder only, before `dispatch`. The execution opens with root visibility, and after routing it switches to the controller's module. Extensions written before the switch survive it. Two consequences are visible to a middleware author: a resolver created before `route_to` keeps the root module, and a key that names a different binding under the controller's module is a second instance in the one execution, since instances sit in the execution cache under their binding.

## 3. HTTP

### 3.1 API

```rust
#[routes]
#[guards(http = AuthGuard)]
#[interceptors(value = Timing::new())]                     // impl-level value: built once, shared (X2)
#[meta(RequiresRole::any(["staff"]))]
impl UsersController {
    #[fw_http::get("/users/{id}")]
    async fn get(&self, Path(id): Path<u64>, user: Ext<CurrentUser>) -> Result<Json<User>, UserError> {
        Ok(Json(self.users.find(id, &user).await?))
    }

    #[fw_http::post("/users")]
    #[guards(value = RateLimit::per_second(20))]
    async fn create(&self, body: Valid<Json<NewUser>>) -> Result<Created<Json<User>>, UserError> {
        let user = self.users.create(body.into_inner().0).await?;
        Ok(Created::at(format!("/users/{}", user.id), Json(user)))
    }

    #[fw_http::get("/users/events")]
    async fn events(self: Arc<Self>, last: LastEventId, cx: HttpCx) -> Sse<impl Stream<Item = Result<Event, UserError>>> {
        let resume = last.0;                                              // the stream captures the Arc rather than borrowing
        let exec = cx.exec().clone();                                     // the controller; the macro appends `+ use<>` (§2.3)
        Sse::new(self.feed.since(resume).take_until(exec.draining()))   // ends cleanly when the drain starts
            .keep_alive(Duration::from_secs(15))                          // ": keepalive" comments
    }
}

#[derive(Debug, thiserror::Error, Classify)]
pub enum UserError {
    #[error("user not found")] #[classify(not_found)] NotFound,
    #[error("email already registered")] #[classify(conflict)] Taken,
}
```

**`HttpCx`** is `Clone + Send + Sync`: an `ExecutionRef`, an `Arc<RequestHead>`, the matched route, path parameters, the client address, a take-once body slot, an interior-mutable response-head writer, and the app's `Timer`. Its methods include `head()`, `method()`, `uri()`, `headers()`, `route()`, `mount_prefix()` (§3.8), `exec()`, `ext::<T>()`, `take_body()`, `response_headers()`, `client_addr()` and `timer()`, the app's `Timer` as an `&Arc<dyn Timer>`, which anything timed inside a response reads.

**Extractors** [17] are `Path<T>`, `Query<T>`, `Json<T>`, `Form<T>`, `Bytes`, `BodyStream`, `Multipart`, `Header<H>` (typed, from the `headers` crate), `HeaderMap`, `LastEventId`, `HttpCx`, and every container type. `Json`, `Form`, `Bytes`, `BodyStream` and `Multipart` consume the body. The body limit is a server setting (`.body_limit(2 * MB)`) that `#[meta(BodyLimit(..))]` can override per route. Bodies over the limit fail with 413 before deserialization.

**Responses** [18] are any `T: IntoReply<Http>`:

- `Json<T>`, `Bytes`, `String`, `()` (204), `Created<T>`, `NoContent`, and `(StatusCode, T)`.
- `WithHeaders<T>`, and `Response::builder()` for any status, headers and body.
- `Body::stream(s)` for a streaming body.
- `Sse<S>` with `Event::default().data(..).id(EventId).event(EventName).retry(..)`. Data is split into `data:` lines at CR, LF and CRLF alike, since a reader ends a line at any of the three. `EventId` and `EventName` are built fallibly (`EventId::new(..)?`) and refuse line terminators, and the id refuses U+0000, which a reader ignores, so a bad value fails where it is built and never mid-stream. Keep-alive comments are written as `: keepalive`, per the SSE spec, when the period passes with nothing written. The period is timed by the app's `Timer`, which `HttpCx::timer()` reads; `fw-http` picks no runtime, and a body with `keep_alive` is polled wherever the app runs. `Timer` offers `sleep(d)` and no resettable sleep, and the body requests one sleep of the period at the first poll that finds the stream waiting after a write; a write drops the running sleep, and events written back to back request none. The guarantee is a comment after at least the period of idleness, sometimes a little later, never sooner. A period comfortably below the shortest proxy idle timeout in the deployment is the one to set. `keep_alive(Duration::ZERO)` turns the keep-alive off, as leaving it uncalled does, and a later zero turns off an earlier period: a zero period taken literally would write a comment every time the stream is found waiting. An error after the stream has started (§2.3) is written as an event named `error` carrying the problem document, and the stream ends. The content type is `text/event-stream; charset=utf-8`, with `Cache-Control: no-cache`.

### 3.2 Routing [15]

`fw-http` owns the router, so every backend routes identically:

- Patterns use `{name}` segments plus an optional trailing `{*rest}`. A name is identifier-like, Unicode included; an empty segment (`/a//b`) is refused. The attribute macro and the router check one grammar with the same reason texts, so a literal refused at compile time and a prefix-joined pattern refused at `prepare` read alike.
- A trailing slash is insignificant: both the pattern and the request path drop it, except for `/`.
- Each request segment is percent-decoded as a path: `+` stays `+`, `%2F` decodes to `/` inside its segment without splitting it, and a `{*rest}` value is the raw remainder decoded the same way. A static segment matches the request segment as sent or once decoded, so `/caf%C3%A9` matches `/café`. A decoded sequence that is not UTF-8 is captured with U+FFFD per invalid sequence, since the path does name a route; a typed `Path<T>` over it then fails as `Malformed` naming the field. A parameter or rest never captures an empty segment: `/u//x` does not match `/u/{id}/x`.
- Precedence is decided once, in `prepare`, by a key compared segment by segment, static before parameter before rest, so `/users/me` answers before `/users/{id}` whatever the declaration order. The first matching pattern decides the method check: its handler, else `GET` for `HEAD`, else 204 for `OPTIONS`, else 405. A less specific pattern is not consulted for the method: with `GET /users/me` and `DELETE /users/{id}` declared, `DELETE /users/me` answers 405, because the URI names the resource and 405 says that resource lacks the method (RFC 9110).
- Routes are built in `prepare`. Two routes with the same method and the same normalized pattern, or two patterns that differ only in parameter names at one position (`/u/{id}` and `/u/{name}`) whatever their methods, are a `Configure` error naming both handlers as `Controller::method`; `HttpCx::param` would otherwise answer differently by method.
- `prepare` also checks every `Path<T>` against its route, by running `T`'s `Deserialize` impl against a deserializer that records what it asks for, so a mismatch is caught at startup rather than by the first request. A struct is checked by its field names, serde renames included; a tuple by its count; a scalar or newtype requires exactly one parameter. A map, a `#[serde(flatten)]` struct and a hand-written impl calling `deserialize_any` ask for no names and are not checked, which the documentation says.
- A path that matches nothing answers 404. The global error handlers receive it as `CallError::new(NotFound, ..)` whose source is `fw_http::NoRoute`, a public marker, so `source_as::<NoRoute>()` tells a miss from a handler's own `NotFound`; unclaimed, it renders by kind.
- A matching path with the wrong method answers 405 with an `Allow` header, which RFC 9110 requires. The error handlers receive it as a `CallError` of kind `BadRequest` whose source is `fw_http::MethodNotAllowed`, a public type with `method()`, the request's, and `allow()`, the header value as the router computed it; `err.downcast_ref::<CallError>()?.source_as::<MethodNotAllowed>()` reaches it, the pattern `NoRoute` uses. It is wrapped rather than offered bare because `from_boxed` answers `Internal` for a type it does not recognise, and an app reshaping every error would then send a 500 for a 405. No `ErrorKind` is 405: every kind maps on all four transports and 405 is HTTP's alone. `BadRequest` is the generic client-error kind, and 413 and 415 already ride on it with the exact status applied at rendering: an unclaimed 405 renders as problem details with status 405 and `Allow` while the kind is `BadRequest`, and one reshaped to another kind renders by that kind. `Allow` is the pattern's methods in declaration order, then `HEAD` after `GET` when only `GET` is declared, then `OPTIONS` when no handler declares it, computed once in `prepare`.
- `HEAD` is answered from the `GET` handler with the body omitted, unless a `HEAD` handler exists (RFC 9110 requires general-purpose servers to support `HEAD`). The body is dropped unread; when the response carries no `Content-Length` and the dropped body's size hint is exact, that size is set, except on 1xx, 204 and 304.
- `OPTIONS` without a handler answers 204 with `Allow` directly, offered to no error handler. CORS preflight never reaches routing (§3.4).

### 3.3 Pre-dispatch [19]

Middleware is HTTP-specific, so it isn't a core role. Middleware types are still ordinary container bindings, and the metadata that declares them reports its dependencies (`Meta::dependencies`), so wiring checks them.

```rust
pub trait Middleware: Send + Sync + 'static {
    fn handle(&self, req: Request, next: fw_http::middleware::Next<'_>) -> impl Future<Output = Result<Response, BoxError>> + Send;
}
```

A middleware's `Err` is a pre-dispatch failure like a layer's: an authentication middleware returns `Err(CallError::unauthorized(..).into())` and the app's error handlers shape it; no middleware renders its own errors. The `Err` is caught at the entry's own boundary, where its panic is caught, and offered from there. `Next::run(req)` answers the same `Result<Response, BoxError>`, and what it answers is `Ok`: a failure further in has already reached the error handlers and been answered or rendered at its own entry, and that response is what the outer middleware receives, so an outer CORS entry adds its headers to the 401 an inner authentication middleware's `Err` became, which a browser needs to read the 401. Propagating the inner `Err` outward would skip every outer entry's response handling on a failure and move a scoped entry's failure to the unscoped side, where only the global handlers apply. The `Result` keeps `next.run(req).await` a middleware's answer as it stands, and `?` on it compiles. `fw_http::middleware::Next` holds the middleware chain and the request; the core's `Next<'a, T>` holds the interceptor chain. A module importing both qualifies one or writes `use .. as ..`, as std's `fmt::Result` and `io::Error` are imported by module. No alias ships, and the two differ in signature, so a wrong import fails at the type.

There is one middleware stage, **pre-dispatch**, declared in module metadata:

```rust
m.meta::<fw_http::PreDispatch>()
    .apply_value(Cors::new().allow_origin("https://app.example").allow_credentials(true))
    .apply::<RequestId>()                                           // unscoped: every request, misses included
    .layer(TraceLayer::new_for_http())                              // tower, unscoped (§3.4)
    .layer(HostAuthLayer::new()).supplies::<CurrentUser>()          // the layer inserts `CurrentUser` (§3.8)
    .layer_for(["/files/*"], RequestBodyLimitLayer::new(50 * MB))   // tower, scoped by route pattern
    .apply_for::<ApiKeyAuth>(["/admin/*"]).exclude(["/admin/health"])
    .adopt::<CurrentUser>();                                        // into the execution, as `Ext<CurrentUser>`
```

`.adopt::<T>()` is a further entry, unscoped, which copies `T` from the request's `http::Extensions` into the execution's at its place in declaration order (§3.8). `.supplies::<T>()` is a declaration about the entry written before it: that entry puts `T` in the request's `http::Extensions`, as a tower layer authenticating the request does. The declaration runs nothing, on a backend or embedded, and only an embedding whose adapter declares `host_extensions: false` reads it, where the entry runs (§3.8). `prepare` refuses a `supplies` with no entry before it, on a backend as well, as it refuses a stray `exclude`: "`supplies` at src/main.rs:196:33 follows no pre-dispatch entry; it declares what the entry before it inserts, and a value the host keeps is copied in by the embedding with `Embedded::forward`". A `supplies` written after an `adopt` entry is refused the same way, on a backend and on every embedding and whatever the two types, with "`adopt` copies a value out of the request and inserts none; declare the `supplies` after the entry that inserts it", and the declaration is kept off the entry, so the embedding's check counts only entries that insert.

The stage runs in two sub-steps, because a path rewrite has to happen before route matching while scoping by route pattern needs the match. Unscoped entries run first: they can rewrite the path with `req.set_path(..)`, they see misses, and they can answer without calling `next`, which is how a CORS preflight is answered; an authentication middleware refuses by returning `Err`, which reaches the error handlers. Then the route is matched and `route_to` (X8) switches the execution to the controller's module. Then the entries whose pattern matches the route run. Then `dispatch` (guards, interceptors, handler, error handlers). To the user it is one stage in one order: the order written, with modules in collection order (DESIGN §3.2) where several declare entries. Both sub-steps run inside the error chain: an entry's `Err` reaches the error handlers as a `BoxError` and its panic as `PanicRecovered`, and on a miss only the global error handlers apply, since no handler matched. A request that arrives with no execution to open, during the drain, never reaches the stage (§10).

A scope is a route pattern whose last segment may be `*` or `{*name}`, matching one or more segments: `/admin/*` covers `/admin/users` and `/admin/{id}/notes`, not `/admin`, and a scope's parameter covers a route's parameter or static segment whatever the names. `exclude` applies to the entry written before it; `apply_for` or `layer_for` with an empty pattern list is refused at `prepare`.

The request has two heads. The `RequestHead` input is seeded at `Execution::open` with the head as the client sent it, and the `HttpCx` that `dispatch` receives is built from the request as the stage leaves it, so a rewritten path or a header an entry set reaches the extractors: `HttpCx::head()` reads the stage's head, `Dep<RequestHead>` the client's. An entry's failure is offered with a context built from the head as its sub-step received it, no body and no upgrade; in the scoped sub-step the matched handler's tiers run before the global ones, in the unscoped sub-step only the global ones run, even when a route matches later.

Each entry is resolved through the module that declared it, inside the request's execution: `Mounted::module_meta::<T>()` (X9) yields `(ModuleRef, Arc<T>)` in collection order, and `ModuleRef::with_execution(&ExecutionRef)` gives a resolver with that module's visibility, so a per-execution middleware is built once per request and a binding only its own module sees resolves as `wire()` checked it.

There is no per-module middleware. Auth for a group of routes is a pattern-scoped pre-dispatch entry, which runs before guards and can set `CurrentUser`; logging, metrics or transforming a module's responses is an interceptor; rejecting a request is a guard. What the stage cannot express is "every controller in this module" by naming the module: `.at(prefix)` (§2.5) with a pattern-scoped entry covers it. If a case needs the module named, the enhancer stack gains a module tier (global, module, controller, method), inside the error chain and with the existing tiers' semantics; middleware does not return for it.

### 3.4 CORS and tower [20]

`fw_http::Cors` follows the Fetch specification's CORS protocol. It answers preflights (`OPTIONS` with `Access-Control-Request-Method`) with 204 and the `Access-Control-Allow-*` headers, adds `Vary: Origin`, and never echoes `*` together with credentials. That last combination is forbidden by the spec, so it's refused in `prepare`.

`.layer(L)` accepts any `tower::Layer` over `fw_http::Service`, which is `Service<http::Request<HttpBody>, Response = http::Response<HttpBody>>`, and `.layer_for(patterns, L)` scopes one by route pattern. Layers are composed once, in `prepare`, never per request. An unscoped layer wraps the whole stage before matching, so it can rewrite and it sees misses. For scoped layers, `prepare` builds each route's own stack from the layers whose pattern matches it, in declaration order, and routes with the same set of layers share one stack; a matched request runs its route's prebuilt stack. Layers run inside the pre-dispatch stage, so they behave the same on the backend and under every embedding host (§3.8), the native ones that are not tower-based included, and they sit inside the error chain: a layer's `Err` reaches the error handlers as a `BoxError` and its panic as `PanicRecovered`. A response a layer builds itself, tower-http's auth answering 401 for example, is a response and not an error, so error handlers don't see it; that is inherent to tower, and the documentation says so. The continuation (the rest of the chain, the connection info and the upgrade future, which an `http::Request` cannot carry) rides the request's extensions in a take-once slot every clone shares, and the chain is one-shot: a layer that calls its inner service twice for one request, a retry layer, or that builds a new request without the original's extensions, gets a bare 500 and an `error` log line. The body has been read and the middleware consumed by then; no slot shape could replay it, and `layer`'s documentation says retries belong in a client. **X23: one stage type for HTTP and gRPC.** `PreDispatch<T: HttpCarried = Http>` is one type and one set of scope rules: `fw_http::PreDispatch` is HTTP's instance and `PreDispatch<Grpc>` gRPC's, each a distinct metadata key read by its own server (§6.2), so an entry declared for one never runs on the other. `HttpCarried` is `Transport + __private::Carried`, `Carried` a public, doc-hidden trait that `fw-http` implements for `Http` and `fw-grpc` for `Grpc`, the two transports whose requests are `http::Request`s, so `m.meta::<PreDispatch<Ws>>()` is E0277. The seal holds by the `__private` convention, the workspace's boundary for sibling and generated code, and not by the compiler: a `pub(crate)` seal would keep `fw-grpc` out, and moving `Grpc`'s impl into `fw-http` behind a feature would couple the two crates. `fw_http::stage::{Stage<T>, ScopedStage<T>, StageHost, Rest}` are public so that `fw-grpc` runs its `PreDispatch<Grpc>` entries through the one stage rather than a copy of it. WebSocket and RPC have no pre-dispatch stage: guards and interceptors cover them.

### 3.5 WebSocket upgrades [21]

When a gateway's path matches a request carrying `Upgrade: websocket`, the router hands the request to `fw-ws` through the upgrade future the backend (§3.7) or the embedding adapter (§3.8) took from the connection; an adapter declaring `upgrades: false` has no gateway on its port, refused in `prepare`. `fw-ws` completes the RFC 6455 handshake and runs the connection on the upgraded I/O. The hand-off is `fw_http::UpgradeHandler`, registered through the `Upgrades` module metadata by `fw_ws::WsModule` (§4.1), and the server reads it before route matching on any request carrying `Upgrade`.

**X21: the upgrade handler has the server's lifecycle.** An upgraded connection has left hyper, so the backend's `drain` and `close` never reach it, and the handler holds the connections nothing else sees. `UpgradeHandler` therefore carries, beside `paths(&self, &AppHandle)` and `upgrade(&self, Request)`, four defaulted methods mirroring `Server`: `prepare(&self, app: &AppHandle) -> Result<(), BoxError>`, whose failures join the HTTP `PrepareError` (duplicate gateway paths, a gateway's own zero limits); `bound(&self, app: &AppHandle)`, called after `bind`, where `AfterInit` runs; `drain(&self, token: DrainToken) -> BoxFuture<'_, ()>`, the 1001 close of idle connections and the stop of reading on busy ones; and `close(&self) -> BoxFuture<'_, ()>`. `Server<B>::drain` and `close` call every registered handler's beside the backend's, concurrently, and `Embedded<A>` does the same, since a host with `upgrades: true` has the same connections. The handler finds its gateways through `AppHandle::mounted::<Ws>()` (X20, §4.1). A gateway on the HTTP server's port and one on its own port are then identical in what runs for them and when.

For a separate port, `fw_ws::Server::new(endpoint)` is an HTTP/1.1 server over `fw-hyper-serve` (§3.7), hyper's `http1::Builder` with upgrades enabled, the same `header_timeout` and `handshake_timeout` settings as the HTTP server with the same zero refusals, `fw_net::Tls` for `wss`, and one `AppService`-free path that answers 404 off the gateway paths and the 101 on them. The upgrade is HTTP/1.1's: the HTTP/2 builder does not advertise extended CONNECT (RFC 8441, `SETTINGS_ENABLE_CONNECT_PROTOCOL`), and WebSocket over HTTP/2 is `fw-ws`'s to decide.

### 3.6 Wire behavior, limits, shutdown

- **Success:** the answer's status, headers and body. Streaming bodies use chunked encoding on HTTP/1.1 and data frames on HTTP/2.
- **Failure:** RFC 9457 problem details (§2.4). Extraction failures are 400, 413, 415 or 422 depending on the `ExtractError` variant, with field violations in `details`; the renderer reads the variant off the `CallError`'s source and applies the exact status while the kind is still `BadRequest`, and a 415 carries `Accept` naming the media type the extractor expected. An error reshaped to another kind renders by that kind.
- **Load shedding:** over the server's in-flight limit, a request gets 503 with `Retry-After` set to `.shed_retry_after(..)`, one second unset. On HTTP/2, `SETTINGS_MAX_CONCURRENT_STREAMS` bounds each connection, and excess streams are refused with `RST_STREAM(REFUSED_STREAM)` per RFC 9113.
- **Cancellation:** the peer closing the connection or resetting the stream before the response has ended fires `Disconnected`. A route timeout (`#[meta(Timeout::after(..))]`, below) is armed after routing, on the app's `Timer`, around the scoped sub-step and `dispatch`; the unscoped entries run before it. When it passes first, the pipeline is dropped at its current await, the execution is cancelled with `Deadline`, and the error handlers run with a `Timeout` `CallError`, the matched handler's tiers then the global ones, under `timeout_grace`: a `Bound` on the server (`Server::timeout_grace(..)`), one second at `Default`, `Unbounded` waiting for the handlers, timed by the same `Timer`. They see `cancel_reason() == Some(Deadline)` and the matched handler, and read a context built from the head as the scoped sub-step received it, with the matched route, no body and no upgrade. Their answer is the response once its body has completed within the grace. The body is read under what the handlers left of the grace, the two sharing one sleep; a body that ends in time, by its end or by its trailers, is rewritten as one data frame and the trailers with an exact `size_hint`, so the backend writes its `Content-Length`, and a body already at its end is passed on as it stands. HTTP has no message boundaries, so a body that completes is HTTP's single reply (§2.4), and a single payload written through `Body::stream` is delivered. A body still open when the grace runs out, an `Sse` among them, was not a single reply produced in time: it is dropped for the canonical 504 without the headers they wrote, logged at `warn` naming the route; a body failing while it is read answers the same 504, logged at `debug`. Under an `Unbounded` grace the body is read until it ends. The read takes at most 32 ready frames per poll and then yields, since a body whose frames are always ready never returns `Pending` on its own and the grace's timer fires only once the task yields. What a body yields within the grace is held in memory, bounded by nothing but the grace's length, and a `Tracked` stream inside it reports its end when the read reaches it, not when the client receives the copy. An error they return renders as it stands, an unclaimed `Timeout` as 504 and a reshaping to another kind by that kind; §2.4's `Deadline` rule does not apply, since the error offered already says `Timeout`. When the grace passes first, their future is dropped and the canonical 504 renders without the headers they wrote. When the pipeline answers first, the pending deadline moves into the response body; a streaming body observes it through `cancelled()`, and an SSE error written on an execution cancelled with `Deadline` renders as `Timeout`.
- **Route timeouts:** `fw_http::Timeout(pub Bound)` is declared metadata on a handler or a `#[routes]` impl, `#[meta(Timeout::after(Duration::from_secs(5)))]`, with `Timeout::after(d)` for `Timeout(Bound::After(d))` and `Timeout::OFF` for `Timeout(Bound::Unbounded)`, both usable in a `const`. The most specific declaration wins, as for all metadata, so under an impl that declares a timeout a handler's own declaration decides:

  | Handler declares          | Effect                                            |
  | ------------------------- | ------------------------------------------------- |
  | nothing                   | the impl's timeout                                |
  | `Timeout::after(d)`       | `d`                                               |
  | `Timeout::OFF`            | no timeout                                        |
  | `Timeout(Bound::Default)` | the server's route-timeout default, which is none |

  `Bound::Default` means the server's default here as it does on a hook or a construction, never the impl's timeout; a handler inherits by declaring nothing. The router resolves the declaration each route runs with to an `Option<Duration>` in `prepare`, which is how a handler's `Timeout::OFF` lifts the timeout its impl declares. A zero, `Timeout::after(Duration::ZERO)` under either spelling, is refused in `prepare` once per declaration, listing every route that runs with it in declaration order: ``#[meta(Timeout(..))]` on the `#[routes]` impl of `ZeroFive` would cancel every request on `GET /a`, `POST /b`, `GET /c/{id}`; write `Timeout::OFF` to turn the timeout off``, or "on the handler `Api::slow`" for a handler's own declaration. The text writes `Timeout(..)` whatever the zero's spelling, and the controller is named as the route table's other failures name one. These failures follow the route table's others, each at the position of its declaration's first route, since a declaration's list is complete only once the whole table is walked. A zero that every handler under it replaces reaches no route and is not refused.
- **Server settings:** `fw_http::Server::new(endpoint)` takes text, an `Endpoint` or a `SocketAddr` (§2.7) and carries `tls`, `body_limit` (2 MiB unset; `#[meta(BodyLimit(..))]` overrides per route), `max_inflight`, `shed_retry_after`, `challenge` (the 401 default, §2.4), `h2c`, `timeout_grace`, `max_concurrent_streams`, `header_timeout` and `handshake_timeout`. No setting is an `Option`, because `None` would leave "the default" and "no limit" indistinguishable: a count is `fw_transport::Count { Default, Max(u32), Unlimited }`, and a timeout is the core's `Bound`. Each setting documents what its `Default` is. `Count` lives in `fw-transport`: a WebSocket connection limit and an RPC in-flight bound are the same three-state count, and its count is a `u32`, which no in-flight or stream limit exceeds. Neither type takes a conversion: `.max_concurrent_streams(100)` does not compile, and `Count::Max(100)` is the one spelling, as `Bound::After(d)` is for a timeout. `max_inflight` at `Default` bounds nothing, as `Unlimited` does, the server having no in-flight default; `Max(n)` sheds over `n`, converted to `Admission`'s `usize` at that one boundary. `max_concurrent_streams` at `Default` leaves hyper's own value, which hyper places outside its stability guarantee; the documentation names no number. `Max(n)` advertises `n`, and `Unlimited` sends no `SETTINGS_MAX_CONCURRENT_STREAMS`. `header_timeout` bounds the arrival of a request head from the moment the backend starts reading it, a clock that also runs while a keep-alive connection waits for its next request, and `handshake_timeout` bounds a TLS handshake; both are 30 seconds at `Default`, and `Unbounded` turns the clock off, under which a peer can hold a connection open until the drain's deadline. The 30 seconds is the server's, not a backend's: `HttpConfig::header_timeout_after()` and `handshake_timeout_after()` resolve each `Bound` to an `Option<Duration>`, `None` for `Unbounded`; every backend applies one value, and `None` means no clock. `header_timeout` is HTTP/1.1 only; an HTTP/2 connection is bounded by the backend's own HTTP/2 limits, hyper's HTTP/2 builder having no head-read clock. A failed or timed-out handshake is logged at `debug` with the peer address and the connection dropped, the accept loop unaffected. `HttpConfig`, which `Backend::bind` receives, is `#[non_exhaustive]` with those fields. The types the builders take from other `fw` crates are re-exported under `fw_http::config`: `Bound`, `Count`, `Tls`, `Endpoint` and `EndpointSpec`, each `#[doc(no_inline)]`: each type has one documentation page, at its defining crate, and an application configuring HTTP imports from one place with no `fw-net` or `fw-transport` dependency of its own. A type an application only matches on (`ListenerName`), only receives in a `prepare` report (`TlsError`, `EndpointError`) or a backend alone names (`BoundListener`, `TlsAcceptor`) is not re-exported.
- **Refused in `prepare`:** a setting that would refuse everything it governs as a standing configuration. `Bound::After(Duration::ZERO)` on `header_timeout`, `handshake_timeout` or `timeout_grace` is one `Configure` failure each: ``.header_timeout(Bound::After(Duration::ZERO))` would close every connection before its first request head; write `Bound::Unbounded` to turn the timeout off``, and the same form for `handshake_timeout` ("drop every TLS connection before its handshake") and `timeout_grace` ("send the 504 before any error handler could answer a route timeout"). `Count::Max(0)` on `max_inflight` or `max_concurrent_streams` is refused the same way, ``.max_inflight(Count::Max(0))` would shed every request; write `Count::Unlimited` to remove the limit`` and "would let no HTTP/2 stream open": RFC 9113 §6.5.2 sanctions a zero stream limit for short durations, and a configured zero is not short. A server that must refuse traffic for a while does it with a pre-dispatch entry it can switch. Each hint names its type's spelling of no bound, `Bound::Unbounded`, `Count::Unlimited` or `Timeout::OFF`. The embedding runs the same checks over the settings it has. A `Duration` setting is not refused: `shed_retry_after(Duration::ZERO)` is a valid `Retry-After: 0`, and a zero `Sse::keep_alive` is defined as off (§3.1), being built per response where `prepare` cannot see it. The check covers HTTP's settings; a `Bound::After(Duration::ZERO)` on a hook, a construction or a readiness check is not refused by the core's wiring pass.
- **Shutdown:** at `drain` the backend stops accepting, sends HTTP/2 GOAWAY, closes idle HTTP/1.1 keep-alive connections, and marks busy ones `Connection: close` on their next response. SSE handlers observe `draining()` and end their streams. A request that still arrives once `Execution::open` is refused, on a keep-alive connection before its `Connection: close` response, is answered directly with 503, `Retry-After` and `Connection: close`: no execution exists, so the pre-dispatch stage does not run for it. `close` closes everything that's left.

### 3.7 Backend SPI [16], written without macros

```rust
pub trait Backend: Send + Sync + 'static {
    const NAME: &'static str;
    fn limits() -> BackendLimits;                    // documented limits, checked in `prepare`

    fn bind(&mut self, listeners: Vec<BoundListener>, tls: Option<TlsAcceptor>, svc: AppService, cfg: &HttpConfig)
        -> impl Future<Output = Result<(), BoxError>> + Send;
    fn serve(&self) -> impl Future<Output = Result<(), BoxError>> + Send;
    fn drain(&self) -> impl Future<Output = ()> + Send;   // GOAWAY, close idle keep-alives
    fn close(&self) -> impl Future<Output = Result<(), BoxError>> + Send;
}

/// What a backend calls per request: global middleware, routing, dispatch, rendering.
#[derive(Clone)]
pub struct AppService { /* Arc inside */ }
impl AppService {
    pub fn call(&self, req: Request) -> impl Future<Output = Response> + Send;
}

pub struct Request {
    pub head: http::request::Parts,
    pub body: HttpBody,                              // stream of Bytes; dropping it unread is not a disconnect (§2.6)
    pub conn: ConnInfo,                              // peer address, TLS info, protocol version
    pub upgrade: Option<OnUpgrade>,                  // resolves to an AsyncRead + AsyncWrite + Send + Unpin stream; `Some` only for an HTTP/1.1 request asking to upgrade
}
```

`fw_http::Server<B: Backend>` implements the core `Server`. `fw-http-hyper` is the one backend, the reference and the default: its type is `fw_http_hyper::Hyper` with `NAME` `"hyper"`, it binds the listeners, runs the accept loop and drives hyper 1.x connections into `AppService`, handing hyper each response as `http::Response<HttpBody>` with no body wrapper, and the `http` crate's types are the common language.

The accept loop is not the backend's own. `fw-hyper-serve` holds it once for the three socket-owning servers, the HTTP backend, the gRPC server (§6.2) and the standalone WebSocket server (§3.5): `fw_hyper_serve::Serve::new(listeners, tls, &ServeConfig) -> io::Result<Serve>` takes the `BoundListener`s `fw-net` bound, an optional `TlsAcceptor` and a `ServeConfig { handshake_timeout: Option<Duration> }`. It adopts each listener into tokio through `TcpListener::from_std`, which can fail and runs inside the runtime, so a server builds it in `bind`. `ServeConfig::default()` carries no handshake clock; a server passes its resolved `handshake_timeout`, which is why the field is an `Option<Duration>` rather than a `Bound`. `run(&self, connection)` accepts on every listener, performs the TLS handshake under the timeout, abandoning a handshake the drain interrupts, and spawns one task per accepted stream into a `JoinSet`, handing the `connection` closure the consumer supplies an `Accepted { io, conn: ConnInfo, draining: Draining }`: `conn.version` is HTTP/2 where ALPN settled `h2`, and `Draining` carries `wait()` and `is_draining()`, on which the closure starts its hyper connection's `graceful_shutdown`. `run` takes `&self` because a server calls `serve`, `drain` and `close` on one `&self` and holds one `Serve` across the four; a second `run`, or one after `drain` or `close`, returns at once. That closure is where the three differ: the HTTP backend drives hyper's auto builder with upgrades, or `http1` with upgrades where neither TLS nor h2c selects HTTP/2, the gRPC server drives `http2`, and the WebSocket server drives `http1` with upgrades. `Serve::drain()` stops accepting, drops the listeners and resolves every connection's `draining`, then waits for the tasks; `Serve::close()` aborts whatever is left through `JoinSet::shutdown` and marks the loop finished, on which `drain` and `close` wait. A `drain` or `close` before `run` releases the listeners. A failed or timed-out handshake is logged at `debug` with the peer address and the accept loop is unaffected. The loop depends on tokio, as every consumer does, and `fw-http` does not depend on it: `Backend::bind` receives listeners and a service, and what accepts on them is the backend's. A backend written outside the workspace has the same shape, conversion plus the drain mapping. An application that runs inside another framework's server embeds instead (§3.8).

`BackendLimits` is enforced in `prepare`: asking a backend for something it declares it can't do is a `Configure` error naming the limit. One entry is `upgrades`: a backend that cannot hand over a per-request upgraded I/O declares `upgrades: false`, and `prepare` refuses a gateway on its port. `fw-http-hyper` declares no limit: h2c, per-request upgrades, inherited sockets and port 0 all work on it, and the conformance suite confirms that before release.

### 3.8 Embedding [16]

A `Backend` owns sockets. An embedding owns none: a host application binds, accepts and parses, and the app runs inside it, nested under a path or as the host's fallback, with the host's own middleware around it and the host keeping its own server setup. Routing, extraction, pre-dispatch, dispatch and error rendering run inside the app either way, so controllers move between the backend and a host unchanged.

**Engines and adapters.** An engine parses HTTP off the wire: framing, keep-alive, HTTP/2 streams, upgrades. Three are in play, hyper 1.x, actix-http, and the hyper 0.14 under rocket 0.5, and the framework talks to none of them directly. `fw-http-hyper` is the case where the app owns the sockets. actix-http owns no sockets in this design: an application wanting actix's per-core runtime model embeds in an actix-web host, where the app's pipeline runs inside actix's single-threaded workers and the model is kept. The five adapters are the case where the host owns the sockets, and they split by how they connect:

- **axum** is the one tower embed. The adapter names `type HostRequest<'r> = http::request::Parts;` and hands the host `fw_http::embed::Service<Axum>`, a cheap-clone `tower::Service<http::Request<B>>` over `AppService` whose `Error` is `Infallible`. The impl exists for an `A` whose `HostRequest<'r>` is `Parts` for every `'r`: the head is the only request a copy on a tower host can read, and the restriction is what keeps a `forward` on such a host from declaring a value it never copies. Its `call` runs every `Embedded::forward` copy on the request's head, adds what they inserted to the head's extensions, and builds the app's `Request` from the host's. `ConnInfo` is read from the request's `http::Extensions`, and one carrying only the HTTP version is built when none is there; an adapter whose host keeps the peer elsewhere, axum in `ConnectInfo`, inserts a `ConnInfo` from a layer of its own ahead of the service, which keeps `fw-http` free of any host's types. That layer also inserts `embed::OriginalPath`, built from the host's `OriginalUri`. What it writes is a host extension, axum declaring `host_extensions: true`, and `Host<T>` reads it as it reads any other. `hyper::upgrade::OnUpgrade` is removed from the extensions on every request and converted into the `Request`'s `upgrade` only where `A::limits().upgrades` holds; `fw-http` depends on `hyper` without features and on `hyper-util` with `tokio` for that. The response body is mapped back. `embed::Service<A>` is a type apart from `fw_http::Service`, the inner service a pre-dispatch layer wraps (§3.4), which answers a bare 500 outside the stage.
- **salvo, poem, actix-web and rocket** are native embeds: each adapter implements the host's own handler trait (`salvo::Handler`, `poem::Endpoint`, actix-web's `HttpServiceFactory`, rocket's `Handler`), builds the app's `Request` itself with `conn` and `upgrade` filled from what the host hands it, and calls `embed::Service::respond(&host_request, Request)`, the entry point that takes the host's own request beside the app's. `respond` runs every `Embedded::forward` copy on the host's request before answering, and borrows that request for the call alone, the copies having run before it returns: a rocket handler passes the `&'r Request<'_>` it holds and awaits the answer after the request is gone. Each native adapter names its host's request as its `HostRequest<'r>`: rocket's is `rocket::Request<'r>`, which a rocket handler holds for the lifetime `'r`, and actix's is `HttpRequest`, which borrows nothing and ignores the lifetime. That shape holds on rocket 0.5.1: an `Embed` with `type HostRequest<'r> = rocket::Request<'r>` and `host_extensions: false` compiles on rustc 1.98.1 and 1.88, its rocket `Handler` passing the `&'r Request<'_>` it receives to `Service::respond`. A `forward` copy reading a request header reaches `Host<T>` there, and the handler answers 200 with the header present and 500, `HostMissing`, without it. The copy compiles with its parameter unannotated, `.forward(|req| req.headers().get_one("x-user") ..)`, as it does annotated. `http` 1 requires everything in `Extensions` to be `Clone` and an upgrade future is not, so a host with its own upgrade mechanism cannot reach the app through the tower `call`; the tower `call` converts the request and answers through the path `respond` takes, both running the copies first, so no adapter reaches the app without them. salvo's and poem's tower bridges drop what a native handler reads, the peer address on both and the upgrade future and original URI on poem, and salvo's sits behind a non-default feature. actix's request payload is `!Send` while the app's body must be `Send`, so the adapter forwards payload chunks through a bounded channel from actix's worker-local task. rocket 0.5 is on `http` 0.2, and the adapter converts at its edge.

| Host      | Exposed as                                                                                                            | Mounting                                                                                     |
| --------- | --------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| axum      | `tower::Service` (`fw_http::embed::Service<Axum>`, aliased `fw_http_axum::Service`), behind `fw_http_axum::HostLayer` | `Router::nest_service("/api", HostLayer.layer(handle.service()))` or `.fallback_service(..)` |
| salvo     | `salvo::Handler` (`fw_http_salvo::handler(&handle)`)                                                                  | nested under a path or as the catch-all                                                      |
| poem      | `poem::Endpoint` (`fw_http_poem::endpoint(&handle)`)                                                                  | nested under a path or as the fallback                                                       |
| actix-web | `HttpServiceFactory` and `ServiceFactory<ServiceRequest>` (`fw_http_actix::scope(path, &handle)`, an `ActixScope`)    | `App::service(scope("/api", &handle))` or `App::default_service(scope("", &handle))`         |
| rocket    | `rocket::Handler`, one catch-all route per method (`fw_http_rocket::routes(&handle)`)                                 | `rocket.mount("/api", routes(&handle))`                                                      |

**`Embedded<A: Embed>`.** The embedding is a second `Server` implementation, generic over its adapter as `Server<B: Backend>` is over its backend, and it binds nothing: the app still goes through `listen()`, `prepare` still builds the route table, checks CORS and validates every `Path<T>`, and `Embedded::prepare` then checks the app against `A::limits()`. `Server::bound` answers nothing, so `App<Bound>::addresses()` is empty; port 0, inherited sockets and `fw dev --listen` are the host's business. Each adapter crate exports its aliases (`fw_http_axum::{Embedded, Handle, Service}`) and the functions that hand the app to its host. `Embedded::handle()` answers the `embed::Handle<A>`, as `App::handle()` answers the `AppHandle`: `Clone + Send + Sync`, usable before `listen()` returns, carrying `service()`, `host(fut)`, `stopping()`, `app()`, `register_listener()` and `listeners_closed()`. `Handle<A>` and `Service<A>` carry the host as a type parameter: each `forward` copy is typed over `A::HostRequest<'r>`, and running it needs that type at the call. `Stopping` carries none.

```rust
pub trait Embed: Send + Sync + 'static {
    const NAME: &'static str;
    type HostRequest<'r>;                             // the host's request as its handlers receive it, borrowed for one call
    fn limits() -> EmbedLimits;                       // documented limits, checked in `prepare`
    const STRIPS_PREFIX: bool = true;                 // the host removes `.nested_at` before its handler sees the path; `false` has `Service::respond` strip it

}

impl<A: Embed> Embedded<A> {
    pub fn forward<T: Clone + Send + Sync + 'static>(
        self,
        copy: impl for<'r> Fn(&A::HostRequest<'r>) -> Option<T> + Send + Sync + 'static,
    ) -> Self;                                        // records `T` as supplied and stores the copy
}

impl<A: Embed> Service<A> {
    pub fn respond(&self, host: &A::HostRequest<'_>, req: Request) -> impl Future<Output = Response> + Send + use<A>;
}

impl<A, B> tower::Service<http::Request<B>> for Service<A>
where
    A: for<'r> Embed<HostRequest<'r> = http::request::Parts>,

```

```rust
let server = fw_http_axum::Embedded::new()           // Embedded<Axum>
    .nested_at("/api")                               // the prefix the host strips
    .peer_addr(true)                                 // the host supplies `ConnectInfo`
    .body_limit(4 * MB);                             // app-level settings only
let embedded = server.handle();                      // `embed::Handle<Axum>`, aliased `fw_http_axum::Handle`: Clone + Send + Sync, usable before `listen()` returns

let app = App::builder(AppModule).timer(fw_tokio::Timer).wire()?
    .connect().await?
    .bind(server)
    .listen().await?;

let router = axum::Router::new()
    .route("/legacy", get(legacy))
    .nest_service("/api", fw_http_axum::HostLayer.layer(embedded.service()))   // the layer inserts `ConnInfo` and `OriginalPath`
    .into_make_service_with_connect_info::<SocketAddr>();   // what `.peer_addr(true)` relies on
fw_http_axum::run(app, &embedded, axum::serve(listener, router), fw_tokio::shutdown_signal()).await?;
```

`Embedded` carries the five app-level settings `Server<B>` has, `body_limit`, `max_inflight`, `shed_retry_after`, `challenge` and `timeout_grace`, plus three the adapter reads, `nested_at`, `peer_addr` and `on_miss`, and the copies `forward::<T>(..)` registers (below), all set before `listen()` so `prepare` sees them. `.nested_at` is normalized to a leading `/` and no trailing one; `/` or an empty string means not nested; a prefix carrying a parameter, or one that does not parse as a route, is refused in `prepare`. The host's settings, the endpoint, `tls`, `h2c`, `max_concurrent_streams`, `header_timeout` and `handshake_timeout`, have no method on it, so writing one is E0599 rather than a setting ignored; `prepare` refuses a zero `max_inflight` or `timeout_grace` on it as on a backend (§3.6). `Server<B>::prepare` and `Embedded<A>::prepare` call one crate-private function that builds the stage, the router, the upgrade paths and the admission, taking the parts both have as plain arguments, so the conformance suite compares one route table with itself. `EmbedLimits` and `BackendLimits` stay separate structs, which keeps each builder's compile-error story exact.

The handle moves through three states, `Unbound → Bound → Closed`, and the state a request meets decides its answer. In `Unbound`, before `listen()` has returned, a request is answered 503 with `Retry-After` and a problem document naming the state ("the application is not yet listening"), rendered from the settings every builder method copies into the handle's shared state, since no `AppHandle` exists yet; starting the host after the app's bind is the host's responsibility. In `Bound` the app serves. In `Closed`, after `Embedded::close`, a request is answered the drain's 503 with `Connection: close`. A `listen()` that fails after this server bound closes it, so a failed app does not keep serving through the handle. An answer given in `Unbound` or `Closed` carries `Routing::Unrouted`.

**Prefix.** The app sees the request with the nest prefix stripped: on axum `/api/users/1` arrives as `/users/1` and `/api` as `/`. Two hosts strip it themselves, axum's `nest_service` and poem's `Route::nest`, and their adapters declare `Embed::STRIPS_PREFIX` as `true`, its default. salvo hands its handler the full `uri().path()`, actix's `web::scope` leaves `req.path()` whole with the rest in `match_info`, and rocket's `mount` leaves `req.uri()` whole with the tail in a `<path..>` segment, so those three adapters declare `false`, under which `embed::Service::respond` strips the normalized `.nested_at` from the path, keeping the query, before the app routes. The rule holds by construction: the adapter that strips declares it, and the one place that strips reads the declaration. A request those adapters receive outside the prefix is the host's misconfiguration. `respond` marks it with a crate-private `OutsidePrefix` extension, which routing answers as the app's 404 with `Routing::NotFound` before the router runs, so no in-app route matches it by accident, and logs it at `warn` once per embedding with the host, the path and the prefix. No adapter compares `.nested_at` with the host's own nesting: on a host that strips the prefix itself, a wrong `.nested_at` shows in `HttpCx::mount_prefix()` and the joined route alone. `.nested_at("/api")` tells the app, which routes on the stripped path. `HttpCx::route()` is the in-app pattern routing matched, `/users/{id}`. The span's name and its `http.route`, and `Routing::Matched::route`, carry the joined route, `/api/users/{id}`, under which `/api` joined with `/` is `/api` (§2.9). `HttpCx::mount_prefix()` answers the normalized prefix, empty when not nested and on a backend, so `format!("{}{path}", cx.mount_prefix())` builds a `Location` header for an app path starting with `/` without doubling a slash; a method with no argument cannot join an arbitrary path. The host's original path crosses as `embed::OriginalPath`, built with `OriginalPath::new(..)` or `From<&http::Uri>`, which keeps the URI's path and drops its query, and read back with `as_str()`. It is one of the adapter's built-in values, a `forward` the adapter registers in `Embed::builtin_forwards` (below), rocket's reading `req.uri().path()`; on axum the adapter's `HostLayer` ahead of the service inserts it into the request's `http::Extensions`, built from the host's `OriginalUri`, a host extension under `host_extensions: true`. The span's `url.path` records it when present and the path the app received otherwise, on a backend as well, where nothing outside the app can insert one: axum delivers both `/api` and `/api/` as `/`, and the original is not recoverable from the stripped one. Only the span reads it inside the framework; `Routing::Matched::route`, `HttpCx::route()` and `HttpCx::mount_prefix()` are unaffected, and a handler reads it as `Host<OriginalPath>`, a type the `host_extensions: false` check counts as supplied through the adapter's forward. The embedded app may own `/`, which is `/api` from outside, and the route table's trailing-slash rule decides `/api/` against `/api` as it does unembedded.

**The host and the app.** The app's `Execution` opens inside the app's service, so host middleware runs before any execution exists and never touches one. Information crosses the boundary in two places:

- _Host to app, through request extensions._ A host layer writes a value into the request's `http::Extensions`. The app reads it with the `Host<T>` extractor, `Host<T>(pub T)` with `FromCall<Http>` for `T: Clone + Send + Sync + 'static`, or copies it into the execution with the pre-dispatch entry `.adopt::<T>()`, so guards and services read it as `Ext<T>`. `adopt` is an unscoped entry: it copies `T` into the execution's extensions when the request carries one and passes the request on unchanged when not, and it runs at its place in declaration order, so a tower layer written before it can be its source. A value missing is a deployment fault rather than a bad request: `Host<T>` fails with `ExtractError::HostMissing { param: "host", type_name }`, which classifies as `Internal` with its message withheld, the type name in the error's `Display` and not in the body, and `Option<Host<T>>` is the spelling for a value that may be absent, `Option<P>` answering `None` for `HostMissing` as for `Missing`. Where the host's store is neither `http::Extensions` nor enumerable, actix's request store and rocket's `local_cache`, the adapter declares `host_extensions: false`. A value in that store crosses through a copy the embedding registers, and `prepare` refuses each `Host<T>` a handler reads and each `adopt::<T>()` entry that no copy and no declared entry reaches (below). `Host<T>` is found by a probe: `#[fw_http::get]` and its siblings emit one autoref-ranked probe per parameter, which records the `TypeName` of a `Host<T>` or `Option<Host<T>>` on the handler's record for `Embedded::prepare` to read. The probe sees direct parameters only, so a custom extractor calling `Host::<T>::from_call` inside escapes the refusal and fails at the call with `HostMissing`.
- _App to host, through response extensions._ Every response the app gives carries one `fw_http::Routing`, `#[non_exhaustive]`, and a response without one is the host's own: nested or as the fallback, a request the host routed elsewhere has none, and presence tells "the app answered without routing" from "the app never saw this request". `Matched { route, handler }`: a handler answered; `route` is an `Arc<str>` holding the pattern as the host sees it, the `.nested_at` prefix and the controller's prefix applied (`/api/users/{id}`), and `handler` the `Arc<HandlerInfo>` that `AppHandle::handlers()` lists, with the transport key, the controller, the method name and the metadata. `Options { route }`: the path matched a route and the router answered the 204 with `Allow` on its behalf, `route` the same value `Matched` carries, which a metric keyed on the variant does not count as an error. `NotFound` and `MethodNotAllowed`: the two misses, the second the 405 alone; a `HEAD` answered from a `GET` handler is `Matched`. `Unrouted`: the app answered before routing decided. The refusal renderer sets it on a load-shedding refusal, the drain's 503 and the embedding's 503 before `listen()` and after `close`, and every other response leaving the service with no decision recorded gains it on the way out: a response an unscoped pre-dispatch entry gave without calling `next`, one whose `Err` or panic the global error handlers rendered, and an upgrade request an upgrade handler took, which exposes no `HandlerInfo` for `Matched` to name. A response already carrying a `Routing` keeps it, so the decision rides a response a pre-dispatch entry rebuilt. rocket's `Response` has no extensions; there the value lives in the request's local cache, where a fairing's `on_response` reads it.

**Host values under `host_extensions: false`.** The host's store does not reach the app, so a host value enters the request's extensions through a copy the embedding registers: `Embedded::forward::<T>(copy)`, with `copy: impl for<'r> Fn(&A::HostRequest<'r>) -> Option<T> + Send + Sync + 'static`, actix's `|req: &HttpRequest| req.extensions().get::<CurrentUser>().cloned()`. `Embed::HostRequest<'r>` is the host's own request as its handlers receive it, borrowed for one call, which is how rocket hands its request over; a request borrowing nothing ignores the lifetime. The method records `T` as supplied and stores the copy, so a declared type is a copied type and no call declares a value nothing copies. An adapter's built-in values are `forward` registrations in its `Embed::builtin_forwards(Embedded<Self>) -> Embedded<Self>`, which `Embedded::new()` passes the fresh server through, and the forward is the insertion: rocket's registers `.forward(|req: &rocket::Request<'_>| Some(OriginalPath::new(req.uri().path().as_str())))`, and salvo's, poem's and actix's register `OriginalPath` the same way, while axum's `HostLayer` inserts it ahead of the service. An adapter on a `host_extensions: false` host inserts a value into the request through a `forward` and through nothing else, and the registration the check counts is the code that supplies the value. `respond` runs a built-in forward as it runs any copy. Each adapter's documentation lists its built-in forwards. The copies run on every request before the app sees it, in `Service::respond` on the host's request and in the tower `call` on the request's head. `None` inserts nothing. A copy that panics inserts nothing, is logged at `error` with the host and the type, and the request goes on: the copy runs in the host's task before any execution exists, so no error handler can be offered the panic, and the handler reading the value answers `HostMissing`. `prepare` moves the registered copies into the slot every handle shares once the app is accepted, so a handle taken before `.forward(..)` runs them too; before then the list is empty, and a request is answered 503 regardless.

A pre-dispatch entry that inserts `T` itself is declared with `PreDispatch::supplies::<T>()` written after it (§3.3), and `prepare` reads the declaration where the entry runs. A `Host<T>` read is checked per route: `T` reaches it through a `forward` copy, through a `supplies` on any unscoped entry, or through a `supplies` on a scoped entry whose prebuilt stack the route runs. An `adopt::<T>()` is reached by a `forward` copy or by a `supplies` on an unscoped entry earlier in stage order, modules in collection order and entries as written; a scoped entry runs after routing, so its declaration reaches no `adopt`. An unscoped entry's `exclude` is not consulted: it matches the request path as that entry receives it, which an entry after it may rewrite before routing, and comparing it with route patterns would refuse a route every request reaches through a rewrite. The cost is that a `supplies` after an excluding entry lifts the refusal for the routes it excludes too, and a handler there reading `Host<T>` answers 500 per request. The `supplies` documentation states that cost and names the two placements that avoid it: the supplying entry where its exclusion covers none of the routes that read the value, or a scoped entry, whose exclusions are applied per route in `prepare`.

Each refusal names what reads the value and why nothing reaches it. `prepare` answers its failures as one `PrepareError` (DESIGN §10.2) holding every type they name as a `TypeName`, the `T` of each `Host<T>` and `adopt::<T>()` and the controller of each handler a refusal names, and each failure's text is written when the startup report is built, against the names of every transport's failures (DESIGN §10.1): a type prints cut to its last path segment, `Host<User>`, and in full only where that one report would print two different types alike, `Host<a::User>` beside `Host<b::User>`, or two controllers named `Api` answering one route. The route table's failures take the same path: "`embed::Api::user` and `embed::other::Api::user` both answer `GET /users/{id}`". For a route: "`Api::maybe` on `GET /maybe` reads `Host<User>`, and the rocket embedding declares `host_extensions: false`: the `.supplies::<User>()` at src/main.rs:227:83 follows a scoped entry whose scope does not cover `/maybe`, so it does not reach this route". The route is the app's own pattern, the one scopes are matched against, and the refusals come in the router's precedence order. With no `supplies` of `T` anywhere the reason reads "nothing supplies it. A value the host keeps is copied in with `Embedded::forward::<User>(..)`, and a pre-dispatch entry inserting it is declared with `.supplies::<User>()` after it". For an `adopt`, the refusal names its source location and every reason that applies, joined by `;`: a `supplies` on an unscoped entry at or after it "follows an entry that runs after this `adopt`, which then finds nothing; write the `adopt` after it", one on a scoped entry "follows a scoped entry, which runs after routing and so after every `adopt`", and with neither the "nothing supplies it" text. When the stage or the route table fails, `prepare` reports those failures and leaves the `Host<T>` reads unchecked, since which routes a scoped entry covers is then unknown; the `adopt` check needs only the metadata and runs regardless. A `Host<T>` refusal therefore appears once the stage's own failures are fixed.

Errors render inside the app: host middleware sees the finished response, problem details through the app's error handlers, never a `BoxError`, so the app's error shape is the same embedded or not. Panics are caught inside the app on every host, a body the host polls included. `ExecBody::poll_frame` runs the inner poll under a panic catch. On a panic it marks the body ended, reports `StreamOutcome::CutOff(exec.cancel_reason())` (the first report wins, and a `Tracked` inside reporting the same on its drop changes nothing), drops the panicked body under a second catch, logs at `error`, and answers the error frame, after which the body is empty. The `PanicRecovered` it logs, stage `Handler`, is built by resuming the payload inside the core's own panic catch and polling that future once, which completes on the first poll because nothing in it awaits. Resuming runs no panic hook, so the panic is reported once, where it happened, and `PanicRecovered`'s constructor stays crate-private. Host code that wants the app's services holds the `AppHandle` and calls `handle.execute(..)` for anything execution-scoped or `handle.get::<T>()` for a singleton, which is how an existing application adopts the container one route at a time.

**Misses.** Nested, the app answers everything under its prefix, misses included: its 404 and 405 go through its global error handlers with `NoRoute` and `MethodNotAllowed` as on the backend, and the host answers everything else. As the fallback, the app answers whatever the host did not match, and its 404 is final. Unscoped pre-dispatch entries run for every request that reaches the app, in both modes. Handing a miss back to the host needs a host that supports fallthrough, which rocket does (`Outcome::Forward` with the request's original `Data`, unread) and a tower service cannot, so `.on_miss(Miss::Forward)` is refused in `prepare` on every adapter whose limits declare `forward_miss: false`. Under `Miss::Forward` the decision is per request and the app's. The service wraps the request body in a watcher that records the first `poll_frame` and keeps the path as the client sent it; an unscoped entry is opaque to `prepare`, and whether one consumed the body or rewrote the path is known only after it ran. A `NotFound` miss with the body never polled and the path unchanged is answered with the `NoRoute` 404 problem document carrying `embed::Forwardable` in its extensions and `Routing::NotFound`, and the error handlers are skipped: the host answers that request, and a host ignoring the marker still sends a 404. `Forwardable` tells the adapter the original request is intact for the host, and the rocket adapter forwards on it. Any other miss is the app's own 404 without the marker, logged at `warn`. A 405 is never forwarded: a route of the app matches the path, and the resource is the app's. Under `Miss::Final` no watcher is built. rocket's own routes outrank an unranked catch-all, so the forward matters once the app's routes are mounted with a rank above them.

**Shutdown.** The app is the one owner of the shutdown trigger, `serve(signal)` or `AppHandle::close` as DESIGN §9.5 requires, and the host's own signal handling is turned off (actix `disable_signals()`, rocket `shutdown.ctrlc = false`). `Handle::stopping()` is a `'static` future that `Embedded::drain` resolves, and that `Embedded::close` also resolves for an app closed without a drain. It resolves at the moment the core's `draining()` does, and it is the signal adapters wire to the host's graceful stop, axum's `with_graceful_shutdown`, salvo's `stop_graceful`, actix's `ServerHandle::stop(true)`, rocket's `Shutdown::notify()`, because it is available before `listen()` returns and needs no `AppHandle`. `Embedded::drain` resolves it and returns at once; an embedding cannot cut a connection, so the host's lingering connections are `close`'s business. A host that keeps its listener until its connections end registers it with `Handle::register_listener()`, which counts one listener registered and open and answers a `HostListener` whose drop reports it closed. `Handle::listeners_closed()` answers `None` while nothing was registered on that handle, and otherwise a future resolving once every registered listener has closed, which the adapter's `run` awaits before telling the host to stop. The count covers a handle that sees more than one listener, a server rebuilt or a value built and dropped before `run`: `run` waits for the one inside its server whichever else exists, and a listener dropped unused reports itself closed by its drop. `Handle::host(fut)` takes `&self` and installs the host's server future in a slot, which `run` does before calling `app.serve(signal)`. `Embedded::serve` waits for the slot when it is empty and polls the future; `Embedded::close` awaits the completion notice when `serve` holds the future, and drops one installed and never polled; no task is spawned. A second `host` call, or one after `close`, answers `Err` and drops the future. When the host future ends, `serve` reads `AppHandle::phase()`. In `Running` the shutdown has not begun, and a host that ended `Ok` leaves the app with nothing serving it, a failure reading "the `A::NAME` host server stopped before the shutdown began"; a host `Err` is a failure in any phase, "the `A::NAME` host server failed: ..". Either way `serve` answers `Err` and the app shuts down under "transport `Http` failed: ..", as it does for a dead backend. A host stopping during the before-shutdown stage (`Stopping`) is after the trigger. For axum, `run` takes `axum::serve::Serve` and attaches `with_graceful_shutdown(stopping)` itself; a `WithGracefulShutdown` the user built would be a second signal owner, and `run`'s parameter type does not accept one.

Each adapter's `run` takes the host object before its terminal call, so it can attach the stop signal and the drain bound, awaits `app.serve(signal)` and answers `Result<Shutdown, BoxError>`; four are `async fn`s, and actix's is a plain `fn` answering a `Send` future, for the reason its bullet gives. A `run` whose `Handle::host` refuses the host closes the app, since the app is bound by then and nothing would serve it:

- axum: `run(app, &handle, serve: axum::serve::Serve<L, M, S>, signal)`, attaching `with_graceful_shutdown(handle.stopping())`.
- salvo: `run(app, &handle, server: salvo::Server<Closing<A>>, service: salvo::Service, signal)`, the server the caller's, built over `fw_http_salvo::Closing::new(&handle, acceptor)`, which the parameter type requires, so `with_http_builder`, `http1_mut`, `http2_mut` and `fuse_factory` stay the caller's to set. `Closing<A>` is a public `salvo::conn::Acceptor` over the acceptor it wraps: its `accept` races the inner accept against the handle's `stopping()`, and once that resolves it drops the inner acceptor, closing the listener, and pends from then on, so a connection arriving during the drain is refused as on the other hosts; `holdings()` answers a copy taken at construction. salvo's own `try_serve` keeps its acceptor, and so the bound listener, until every connection has closed or the stop bound passes, under which a connection arriving during the drain is completed by the kernel and never served. `Closing::new` registers the acceptor with the handle through `Handle::register_listener` and holds the `HostListener` beside the inner acceptor, the acceptor dropped first, so the listener is closed before it is reported closed. `run` takes `server.handle()`, serves with `try_serve`, and calls `stop_graceful(drain)` in the first poll that finds `handle.listeners_closed()` resolved, whether or not the server has been polled since: salvo's loop selects between its acceptor and its command channel in random order, and a stop read with the acceptor still alive would keep it, and the bound listener, inside `try_serve` until its connections end; a stop sent once the acceptor is gone depends on no poll order of salvo's. A `Closing` built from another embedding's handle is refused before serving: `handle.listeners_closed()` then answers `None`, and `run` closes the app and answers `Err` naming `Closing::new(&handle, acceptor)` from the handle passed to `run`. A second `Closing` built from `run`'s handle and kept outside the server holds the stop until it is dropped, the app's `close` then bounded by the core's close bound. salvo 0.92 has no `serve_with_graceful_shutdown`, and the crate enables salvo's `server-handle` feature.
- poem: `run(app, &handle, server: poem::Server<L, A>, endpoint, signal)`, calling `run_with_graceful_shutdown(endpoint, handle.stopping(), Some(drain))`.
- actix-web: `run(app, &handle, server: HttpServer<F, I, S, B>, signal) -> impl Future<Output = Result<Shutdown, BoxError>> + Send + use<F, I, S, B, Sig>`, a plain `fn`. actix's `HttpServer` holds `Rc`s and is `!Send`, while the server its `.run()` yields is `Send`, so `run` does the builder work, `.disable_signals().shutdown_timeout(secs).run()`, and the `Handle::host` installation in its body, installing a future that awaits `handle.stopping()`, calls `ServerHandle::stop(true)` and then awaits the server, and answers a future over `app.serve(signal)` holding the app, the signal and the installation's result and nothing `!Send`, which `tokio::spawn` takes as it takes the other four; a refused installation closes the app inside that future. A caller writing `run(..).await` reads no difference. Like actix itself, `run` must be called inside a tokio runtime.
- rocket: `run(app, &handle, rocket: Rocket<Build>, signal)`, setting `shutdown.ctrlc = false`, `shutdown.signals = []` (rocket otherwise handles SIGTERM on Unix itself) and `shutdown.grace` before `ignite()`, taking the `Shutdown` handle off the ignited rocket and installing a future that notifies it on `stopping()` then awaits `launch()`. An ignite failure is installed as a host future failing at once, so the app shuts down naming the error rather than staying bound with nothing serving it; rocket's errors cross as their `Display`, which marks them handled.

The drain window is one clock, set once by the user: `run` reads `AppHandle::drain_timeout()` (X17) through `Handle::app()`, which answers the `AppHandle` once `prepare` has run, and passes it to the hosts that take a stop bound, salvo's `stop_graceful`, actix's `shutdown_timeout`, rocket's `grace`. The accessor reports the window in force, ten seconds unset and zero on an app without a `Timer`, where the drain is zero-length. actix's `shutdown_timeout` takes whole seconds as a `u64` and rocket's `grace` and `mercy` as a `u32`, so on those two hosts the window is rounded up to the second and the host's copy of the clock exceeds the app's by under a second. axum's drain has no bound of its own, and the app's `close` bound contains it: `close` runs under what is left of `shutdown_timeout`, or under `hook_timeout`, ten seconds unset, with no cap (DESIGN §9.5), so a host still stopping past that is recorded `ShutdownFailure::Close` with `TimedOut` and the shutdown report says so. What a host's stop takes inside the window is the host's, declared in the limits table: a `Released` host ends once an abandoned response is dropped, a `Window` host takes the whole window for it, and a host under `DrainHttp2::Reset` takes the whole window while an HTTP/2 connection is open. A request arriving once `Execution::open` is refused is answered 503 with `Connection: close` as on the backend (§3.6). §10 maps each step.

**Conformance.** `fw-http-conformance` runs one scenario list against the hyper backend and against every adapter in both modes, nested and fallback. Its shape is the RPC suite's (§5.2): a `Host` trait, `start(app: App<Connected>, mode: Nested | Fallback) -> Self`, which binds the suite's app into the host, runs `listen()` and serves it, `base_url(&self)`, `limits() -> EmbedLimits` and `stop(self)`, one implementation per adapter crate in its `tests/`, the hyper backend as the reference `Host`, and the macro `http_conformance_suite!(HostType)` stamping every scenario per implementation in both modes. The suite's surface beside the trait is `app()`, `app_for(EmbedLimits)` (the app without its upgrade handler where `upgrades` is `false`, which `prepare` would otherwise refuse), `PREFIX`, `HyperHost`, `report(error: &(dyn Error + 'static)) -> String`, which joins the error's text with each cause under `source()`, a colon and a space between, skipping a cause whose text the message already carries, and the contract through which a host's test middleware writes `Routing` into the response header `ROUTING_HEADER` as `routing_label` spells it and copies a `HostValue` read from `HOST_VALUE_HEADER` into its own store, with `ORIGIN` for the preflight. Every startup path of a `Host` panics with `report`'s text when it fails, the app's wiring and connect and the host's `listen`, listener, address and adoption, so a scenario failing while its host starts says what failed and why; the rocket host awaits its serving task and reports `run`'s answer, where a lift-off channel would report only that the launch sent nothing. The suite's app drains in four seconds, set by `app_for`: a `Window` host takes all of it, and half of it still covers a `Released` host dropping a response at its next write.

Two rules hold over every scenario. **Nothing passes on silence.** A request the client's own timeout ends fails the scenario it ends, the suite's I/O primitives (`Running::send`, `Raw::read_until`, `Raw::read_to_close`) failing it with the message that a timeout is neither an answer nor a refusal, and so does a wait for a close or a frame that does not arrive in time; a scenario about a timeout is the one place a timeout is an answer. **A scenario that cannot apply to a host is declared, not skipped.** `http_conformance_suite!(HostType; not_applicable { scenario: "reason", .. })` stamps each named scenario `#[ignore = "not applicable: <reason>"]`, so the test report counts it as ignored rather than passed; a declared name that is no scenario fails to compile; a scenario run on a host it does not apply to fails rather than returning, so a host leaving out a declaration it needs fails, and `cargo test -- --ignored` runs the declared ones, which fail the same way. The declaration sits in the stamping macro because libtest cannot skip at run time, `macro_rules!` cannot read a trait item, and the `Host` trait is frozen.

Nineteen scenarios per mode: a routing hit; a 404 with `NoRoute`; a 405 with `Allow`; `OPTIONS` answered 204; `HEAD` answered from `GET`; each extraction failure's status, 400, 413, 415 and 422, with its problem document; an error reshaped by an error handler; a domain error an error handler answers with a value of its own, `GET /recover` answered 200 with the substitute item as JSON through `Json(..).into_reply(cx)`; an unscoped entry answering a preflight; SSE with an `error` event; a disconnect mid-stream firing `Disconnected` at the declared `Disconnect` moment; a 101 upgrade with one frame echoed where `upgrades`; `Host<T>` present, and absent as a 500, one scenario sending the same two requests on every host, `host_extensions` deciding only whether the assertions name the host's request extensions or the `Embedded::forward` copy `start` registers on a host declaring `false`, the reference running the absent half alone, having no host to write the value; `Routing` in the response extensions, and on rocket in the request's local cache through a test fairing, since every declared capability is asserted, the reference declaring it not applicable, having no host around the app to read `Routing`; the 503 after `close`, accepting no listener as well as a 503 with `Connection: close`; and four drain scenarios. `drain_http1` writes half a request head, proves the host accepted that connection by getting a 200 on a second one, since a listener hands connections over in arrival order and a host closing its listener at the drain resets one still in the backlog, and starts `close`: where the host declares `DrainPending::Served` it waits 250 ms for the host to apply its stop to its connections, then finishes the head and requires the 503 with `Connection: close`; where `Closed` it never finishes the head and requires the connection to close with nothing written, since a head finished before the host processes its stop would reach the app. `drain_http2` holds an HTTP/2 connection open through the drain with an endless stream and sends a request during it through a client with prior knowledge: where `GoAway` the request is answered 503 on the held connection or refused on the new connection the client opens after GOAWAY; where `Reset` it has to be answered 503, no GOAWAY telling the client to leave the held connection; either way it ends within half the drain window, a request that ends only when the host's own stop deadline cuts it having waited in silence. `drain_goaway` drives an `h2` client directly, opens the endless stream, starts the drain and polls `SendRequest::ready()` until it fails: where `GoAway` the failure has to be a remote GOAWAY with `NO_ERROR` within the patience, which is how an HTTP/2 client learns to stop sending; where `Reset` the connection has to keep taking requests until it fails with no GOAWAY received, no sooner than the drain window and within the window plus the patience. `drain_abandoned` opens an SSE stream, starts the drain, drops the client and times the app's `close`, which waits for the host: under half the window where `Released`, at least the whole window where `Window`. `Host::start` returns once the app listens and every adapter's `run` serves the host only after `listen()`, so the 503 before `listen()` is unreachable through `Host` and is not run; a `Host` method for a host started before `listen()` does not exist. Where a backend cannot do what a host does, a scenario checks whether the host is the reference by `TypeId` and runs the half that applies, since the frozen `Host` trait cannot say it. The suite asserts byte-identical responses wherever a scenario depends on no declared limit. `Routing` is asserted outside the byte-identical rule. The limits table is checked in the other direction too: an adapter that passes a scenario it declares unsupported fails, so the declared limits stay honest, and an adapter declaring `forward_miss` that answers a `Forwardable` 404 itself fails the same way. The actix crate runs the suite twice: its default target on a host listening with `listen`, which serves HTTP/1.1 alone and declares `drain_http2` and `drain_goaway` not applicable for that reason, and a second target, `conformance_http2`, behind a test-only `conformance-http2` feature enabling `actix-web/http2`, on a host listening with `listen_auto_h2c` and declaring nothing not applicable, so the `Reset` declaration is asserted on a build that serves HTTP/2 rather than assumed; the feature is a suite feature, described as one in the manifest and the crate doc: it changes nothing in the adapter, and an application serving HTTP/2 enables actix-web's `http2` itself.

## 4. WebSocket

### 4.1 API [22]–[26]

```rust
#[module(imports = [fw_ws::WsModule::for_root()], controllers = [ChatGateway])]   // registers the hand-off, binds `Rooms` and the broadcast adapter
pub struct ChatModule;

#[derive(Default)]
pub struct ChatSession { nick: Mutex<Option<String>> }

#[routes]
#[fw_ws::gateway(path = "/chat", namespace = "lobby", event = "event",
                 session = ChatSession, connect_guards(TokenGuard))]
impl ChatGateway {
    #[fw_ws::message("chat.send")]
    #[guards(value = RateLimit::per_second(5))]
    async fn send(&self, msg: Payload<ChatMessage>, session: Session<ChatSession>, rooms: Dep<Rooms>)
        -> Result<Ack, ChatError>
    {
        rooms.gateway::<ChatGateway>().to_room("lobby").except([session.conn_id()]).emit("chat.message", &msg.0).await?;
        Ok(Ack::default())
    }

    #[fw_ws::message("chat.history")]
    async fn history(self: Arc<Self>, q: Payload<HistoryQuery>) -> impl Stream<Item = Result<ChatMessage, ChatError>> {
        self.store.page(q.0)                                   // captures the Arc; the macro appends `+ use<>` (§2.3)
    }
}

impl fw_ws::OnConnect for ChatGateway {                        // after the connect guards; may refuse
    async fn on_connect(&self, cx: &ConnectCx) -> Result<(), ConnectRefused> {
        cx.conn().join("lobby").await;                         // `cx.ext::<CurrentUser>()` reads what the guards wrote
        Ok(())
    }
}

impl fw_ws::OnDisconnect for ChatGateway {
    async fn on_disconnect(&self, conn: &Connection, why: DisconnectReason) { self.presence.leave(conn.id()).await; }
}

impl fw_ws::AfterInit for ChatGateway {
    async fn after_init(&self, gw: GatewayRef) { tracing::info!(path = gw.path(), "chat ready"); }
}
```

`#[fw_ws::gateway(path = "/..", namespace = .., event = .., codec = msgpack, subprotocols = [..], refuse = handshake, overflow = drop_oldest, port = http | own, session = T | session_with = .., message_limit = .., max_connections = .., max_inflight = .., max_outbound = .., ping_interval = .., pong_timeout = .., connect_guards(..))]` sits on the impl next to `#[routes]`. `#[routes]` passes it through untouched, and it then emits `impl fw_ws::GatewayConfig`, the trait carrying what the attribute declares: `settings() -> GatewaySettings`, `connect_guards(&mut EnhancerSpec<WsConnect>)`, `session() -> SessionFactory` and `mount_gateway(&mut Mount<'_>)`. `GatewaySettings::at(path)` with one setter per field is the value form, its `message_limit` an `Option<u64>` that defers to the server or `WsModule` when unset. A gateway written by hand implements `GatewayConfig` and `fw_ws::Gateway: GatewayConfig`, whose `on_message(&self, &Connection, Frame)` receives each data message as it arrived, text or binary, with `on_connect`, `on_disconnect`, `after_init` and `mount` defaulted on the trait; the attributed gateway's hooks are instead the traits below, found by probing the concrete type, which a generic default cannot do. A hand-written gateway's instance is resolved once per connection, in the connection phase's execution, and kept while the connection lasts. Messages reach `on_message` one at a time, in order, on a task of their own, one queued or running counting against `max_inflight`; a panic in `on_message` closes 1011; work that outlives a message runs in an execution the gateway opens through `Connection::open_execution`. A hand-written gateway that also declares `#[message]` handlers is refused in `prepare`, since it reads every message raw. The connection hooks are traits on the gateway type, `OnConnect`, `OnDisconnect` and `AfterInit`, following the core's rule that a role comes from the traits a type implements: they are not handlers, receive no `__handler`, and impl-level enhancers do not reach them; an impl-level `#[guards]` applies to message handlers alone. `connect_guards(..)` on the gateway attribute is the one spelling for connect guards, and its entries are an enhancer attribute's: a type, a DI key the module binds; `value = expr`; or `with = |..| ..` and `with(<scope>) = |..| ..` closures, each closure's non-`async` body wrapped in `async move` through `fw_handler_codegen::util::wrap_async` as `#[guards(with = ..)]` wraps one, so one closure compiles in both attributes. An entry carrying a transport key is refused at the key, every entry being a `Guard<WsConnect>`. The connect handler is mounted by `fw-ws` through `Mount::once`, not by a method, so no `__FW_KEY_*` constant is `"ws_connect"`, and an impl-level `#[guards(ws_connect = ..)]` fails the key assertion (X1) with "is not the key of any handler's transport in this impl".

**Two transports.** `Ws` covers message handlers (one execution per message). `WsConnect` covers the connection phase, with key `"ws_connect"`: its `Cx` is `ConnectCx` and its reply is admit or refuse. `fw-ws` mounts the connect handler itself, one per gateway, with the gateway attribute's `connect_guards(..)` as its guards; its body calls `OnConnect` when the type implements it, which `fw-ws` detects by probing the concrete type. Connect guards are ordinary `Guard<WsConnect>` implementations, running through `dispatch` like any guard, so refusals, error handlers, kinds and panics all work the same at connect time. A connection isn't an execution. The connect phase and each message are; `on_disconnect` runs as a terminal execution without guards, its failures and panics logged; `after_init` is a once-per-gateway lifecycle call, not an execution.

**X20: the mounted handlers of a second marker.** `Server::Transport` is one associated type, and a server's `prepare` receives `Mounted<'_, T>` for that one marker, so a `Server<Transport = Ws>` would never see the connect handlers mounted under `WsConnect`. `Mounted::handlers_of::<U: Transport>()` answers another marker's mounted handlers: `fw_ws::Server::prepare` reads `mounted.handlers()` for the message handlers and `mounted.handlers_of::<WsConnect>()` for the connect handlers, pairing them by controller key. `AppHandle::mounted::<T: Transport>() -> Result<Vec<MountedHandler<T>>, TimerMissing>` is the same read for code holding an `AppHandle` alone, which is what the `UpgradeHandler` on the HTTP port holds (§3.5): a same-port gateway finds its handlers, their enhancer tiers and their handler values through it. Both are additive core changes.

`#[routes]` doesn't know the impl is a gateway, so each `fw_ws::message` mount function calls `<Self as GatewayConfig>::mount_gateway(m)` under **X15, `Mount::once::<K>(..)`**, which makes the call idempotent per controller type. A gateway with no message handlers would mount nothing, and the gateway attribute refuses that case at compile time. A `#[message]` handler written by a `macro_rules!` call inside the impl is not seen, since an attribute macro reads the impl unexpanded, as `#[routes]` reads it, and such an impl is refused as a gateway with no handler.

**Which port.** `GatewaySettings::port: Port { Http, Own }`, written `port = http | own` on the attribute, selects which server serves a gateway; `Http` is the default. The hand-off serves the `Http` gateways on the HTTP server's port and on an embedding host declaring `upgrades`, and `fw_ws::Server` serves the `Own` gateways on its own port, its `prepare` refusing a server with none to serve. No gateway is served on both: serving every gateway on both ports would expose one on a port its author did not choose, and neither server can learn at `prepare` whether the other is bound. For the same reason a `port = own` gateway in an application that binds no `fw_ws::Server` is reachable by nothing, and nothing reports it: a wiring-time check needs the server's existence, which no module sees.

**`WsModule`.** `fw_ws::WsModule::for_root()` is imported once per application and is global. It registers the gateway hand-off in the HTTP `Upgrades` metadata (§3.5), writes the hub as module metadata that `fw_ws::Server::prepare` reads, so the standalone server finds the hub whichever module imported it, binds `Rooms` and the broadcast adapter, the in-memory one unless `.broadcast(..)` names another (§4.3), under a private key `also_as` `dyn BroadcastAdapter`, exports both, so `Dep<Rooms>` resolves from every module, and carries the defaults for the gateways on the HTTP server's port, `message_limit`, `max_connections`, `max_inflight`, `max_outbound`, `ping_interval` and `pong_timeout`, that `fw_ws::Server` carries for those on their own (§4.2); the hand-off's `prepare` builds its gateway table with those defaults and refuses their zeros as the server's does. An application binding the standalone server without `WsModule` gets an in-memory hub of the server's own. A gateway's mount records handlers and cannot bind, which is why the module exists: without it a same-port gateway is reachable by nothing and `Dep<Rooms>` is a missing dependency at `wire()`.

**Sessions** [24]: when the upgrade completes, the session is created before the connect guards run, from `Default` or from a factory declared with `session_with = |head: Dep<UpgradeHead>| ..`, the closure wrapped as a `with` entry's is, an explicit return type moved onto a binding inside the `async move` block; `session` beside `session_with` is a compile error naming the two spellings of one setting. A `session_with` factory runs in the connection phase's execution with the connect handler's dependencies, so `wire()` checks what it reads; a factory that fails refuses the connection with 1011. A gateway declaring no session answers a `Session<T>` read as an input never seeded. `Session<T>` is a `FromContainer` type whose `describe` declares a third WebSocket input, `SessionHandle`, which `fw-ws` seeds into every connection-scoped execution: the connect phase, every message and `on_disconnect`. The input is declared by both markers, each `also_seeded_by` the other (§2.10, X19). The session lives until the last execution holding it ends, so it is readable in `on_disconnect`. Per-message state lives in the message's execution.

**Connection hooks** [25]:

- `OnConnect::on_connect` runs after the connect guards and can refuse with a `ConnectRefused`. Under the default `refuse = close` it runs after the 101, so what it writes, a room joined or a directory entry, is visible to other connections only once the connect phase has finished.
- `OnDisconnect::on_disconnect` receives a `DisconnectReason`: `ClientClose { code, reason }` for a Close frame the client sent; `ServerClose { code }` for a close the gateway sent; `ProtocolError` for a protocol, UTF-8 or capacity error the protocol layer reports; `Drain` for the drain's 1001; `Lost` for an I/O error, a connection closed without a frame, or a Pong that missed `pong_timeout`. A connection a connect guard or `on_connect` refused never reaches `on_disconnect`: the hooks come in pairs, and that connection never connected. It opens a plain execution while the app serves and a terminal one once `Execution::open` is refused (DESIGN §6.3), so it's best effort at shutdown; room membership is removed after it runs.
- `AfterInit::after_init` runs once per gateway after `listen()`, with a `GatewayRef`; on the HTTP server's port it runs from the upgrade handler's `bound` (X21), which returns nothing, so the hand-off spawns it. The gateway is resolved in an execution that ends before the hook runs, so a long hook holds none across the drain.

**Where a refusal happens.** Connect guards run after the 101 handshake and refuse with a close code (§4.2), the one path that tells a browser why: a browser `WebSocket` cannot read the handshake's HTTP status, and sees a refused upgrade as a generic `error` and a close with 1006, while a close after 101 reaches the script as `CloseEvent.code` and `reason`. A gateway written `refuse = handshake` refuses before the upgrade instead, with 401 or 403 as RFC 6455 §4.2.2 allows, for non-browser clients and reverse-proxy access logs; such a refusal counts against no connection limit.

**Subprotocols.** The gateway attribute's `subprotocols = ["graphql-transport-ws"]` lists what the gateway speaks. RFC 6455 §4.2.2 has the server select one name from the client's `Sec-WebSocket-Protocol` list and echo it, or echo none, and §4.1 has the client fail the connection when the server names one it did not offer. The handshake echoes the first name in the gateway's list that the client offered. A client offering none of them gets a 101 without the header, after which the gateway decides: graphql-transport-ws's reference server closes 4406, a plain gateway proceeds. The negotiation runs at the handshake, before the connect guards, because the header is part of the 101; a gateway listing no subprotocol echoes none.

**Keep-alive.** The protocol layer sends no Ping on its own. `ping_interval: Bound` and `pong_timeout: Bound`, set on the gateway attribute and defaulted on `fw_ws::Server` and `WsModule`, are on at `Default`, 30 seconds each: a half-open connection nobody notices holds a slot until the next write, and proxies close idle WebSockets anyway. `Unbounded` turns the clock off. A Pong that misses `pong_timeout` ends the connection as `Lost`. The interval is timed by the app's `Timer`.

**`Reply`** [26]. `Transport::Reply` is what an interceptor's `next.run()` answers, so WebSocket's has a name: `fw_ws::Reply`, an enum `None | One(Frame) | Many(Tracked<BoxStream<'static, Result<Frame, BoxError>>>)`, the stream wrapped as an HTTP `Response` wraps a streaming body. A message handler returns a `Frame`, a `Reply`, any `Serialize` value, `()`, a stream of `Result<T, E>` with `T: Serialize` and `E: Into<CallError>`, or a `Result` of any of those. `IntoReply<Ws>` is implemented for `Frame` and `Reply` alone, since a blanket over `Serialize` or `Stream` is refused by the orphan rule (§2.3); the value side of the handler's probe is a crate-local, marker-typed `Answer<M>` with three blanket impls under three markers, `ViaReply` for an `IntoReply<Ws>` type, `ViaStream` for the stream and `ViaSerde` for a `Serialize` value, `M` inferred at the call from the one impl the value meets, as `Param<T, M>` infers `ViaCall` or `ViaContainer`. `()` takes the serde arm and is told apart by `TypeId`, answering `Reply::None`; no `IntoReply<_>` for `()` exists on any transport, since one would make every `()` answer ambiguous. A type that is both `Serialize` and a stream, or both `Serialize` and a user's own `IntoReply<Ws>`, is ambiguous at the handler and fails to compile there (E0283). An `Err` item runs `dispatch_late` (§2.3) and is written as `{"id","error":{..}}`, which ends the stream; `Tracked` reports that end as `CutOff(None)`, the `error` envelope end marker of §2.6. An event nothing handles goes through `recover(None, ..)` as a `CallError` of kind `Unimplemented` whose source is `fw_ws::NoHandler`, a public marker, so an error handler tells it from a handler's own `Unimplemented` as HTTP's `NoRoute` lets it tell a miss from a handler's `NotFound`.

### 4.2 Wire format

The message envelope is defined here, since no specification covers one. Text frames carry JSON. Binary frames carry MessagePack through `rmp-serde`, configured per gateway with `codec = msgpack`. The event field name is configurable, and graphql-ws uses `type`.

```
→ {"event":"chat.send","id":7,"data":{...}}
← {"id":7,"data":{...}}                                  single answer (ack)
← {"id":7,"data":{...}} ... {"id":7,"complete":true}     streamed answer
← {"id":7,"error":{"kind":"forbidden","message":"...","details":[...]}}
→ {"event":"cancel","id":7}                              fires ClientCancelled
```

`id` is any JSON scalar, echoed byte-for-byte and compared by equality: graphql-transport-ws ids are strings, the example writes a number, and both work. `cancel` is a reserved event name, refused by `#[fw_ws::message("cancel")]` at compile time and by `prepare` for a prefix-joined event that spells it; `complete`, `error` and `data` are server-side keys and reserve nothing. A request without a `data` key fails `Payload<T>` as `Missing { param: "data" }`. A text frame that is not a JSON object answers the `error` envelope with `bad_request` and no `id`.

A message without an `id` is fire-and-forget: success sends no ack, and a failure answers the `error` envelope without an `id`, so a guard's refusal stays visible to the client. Control frames (ping, pong, close) are answered by the protocol layer and never reach handlers [26]: control frames are at most 125 bytes and never fragmented (RFC 6455 §5.5), a Pong carries the Ping's payload (§5.5.3), no data frame follows a Close (§5.5.1), and a text frame that is not UTF-8 is a protocol error (§7.4.1); tungstenite does all four and reports the last as `Error::Utf8`. The gateway loop polls the connection after queueing a control frame, since a queued frame reaches the wire only when the connection is polled. Every failure is the one `error` envelope: extraction, a guard, a handler, a panic, or an unknown event (kind `unimplemented`, §4.1).

**Close codes** [23], from the IANA WebSocket Close Code Number Registry that RFC 6455 established (RFC 6455 itself defines 1000–1011 and 1015; 1012 and 1013 are registry entries):

- A connect refusal by kind: `Unauthorized` and `Forbidden` close with 1008 (policy), `TooManyRequests` with 1013 (try again later), `Internal` with 1011, and `Unavailable` with 1013.
- A gateway may map kinds to its subprotocol's own codes, as graphql-transport-ws does with 4401, 4403 and 4429. `ConnectRefused::code(code, reason) -> Result<Self, CloseCodeError>` sets one explicitly, and under §0.6 a fallible constructor with no infallible sibling returns `Result` under the plain name: it refuses a reason over 123 bytes of UTF-8 (§5.5.1), the codes 1005, 1006 and 1015 that are never sent in a frame (§7.4.1), the reserved 1004, and a code outside 1000–4999 (§7.4.2: 1000–2999 for the protocol, 3000–3999 registered, 4000–4999 private use), as `EventId::new` refuses line terminators.
- Frames over `message_limit` close with 1009. Binary frames on a text-only gateway close with 1003. A text frame that is not UTF-8 closes with 1007. A protocol violation closes with 1002. 1010, a mandatory extension the server did not negotiate, is a client's code and never sent.

**Extensions.** tungstenite has no RFC 7692 support, so a client offering `Sec-WebSocket-Extensions: permessage-deflate` is answered without the header, which RFC 6455 §9.1 allows; messages travel uncompressed. The limit is documented, and the conformance suite carries the same sentence.

**Limits**, in the settings vocabulary (§13): `message_limit: u64`, bytes per message after reassembly, 64 MiB at `Default` with tungstenite's 16 MiB per frame; `max_connections: Count` per gateway; `max_inflight: Count` per connection; `max_outbound: Count` per connection. Each is set on the gateway attribute and defaulted on `fw_ws::Server` and on `WsModule`. `Count::Max(0)` on any of them, and a zero `message_limit`, is refused in `prepare` with the HTTP server's hint (§3.6). Over `message_limit` the connection closes with 1009, which tungstenite answers itself when configured through `WebSocketConfig::max_message_size`.

**Load shedding:** over `max_connections`, the connection is accepted and closed with 1013. Over `max_inflight`, the gateway stops reading from that connection, which is backpressure rather than a refusal. Each connection's outbound queue is bounded by `max_outbound`. When it overflows, the connection closes with 1008 and the reason "slow consumer", or drops the oldest message if the gateway sets `overflow = drop_oldest`.

**Shutdown:** at the start of the drain, idle connections close with 1001 at once. Busy connections stop reading, finish their in-flight messages, then close with 1001 (DESIGN §9.5). Having sent 1001, the read loop waits for the client's Close under `pong_timeout`, 30 seconds at `Default`, and the app's drain window, ten seconds unset, ends the wait first; a client that never answers the close holds shutdown for the shorter of the two. On the HTTP server's port and on an embedding the same runs from the upgrade handler's `drain` and `close` (X21).

### 4.3 Rooms and broadcast [27]

`Rooms` is one binding, from `WsModule`. `Dep<Rooms>` addresses every gateway, and a gateway is addressed at runtime: `rooms.gateway::<ChatGateway>()` or `rooms.namespace("lobby")` answers a `RoomsIn` with the same `to_all`, `to_room`, `to_client` and `except` methods. A qualified `Dep<Rooms, ChatGateway>` would name a binding nothing registers, since a module's `ModuleDef` is what binds and a gateway's mount records handlers alone.

```rust
rooms.to_all().emit("notice", &n).await?;
rooms.gateway::<ChatGateway>().to_room("lobby").except([me]).emit("chat.message", &m).await?;
rooms.to_client(id).emit("dm", &dm).await?;
conn.join("lobby").await;  conn.leave("lobby").await;
```

The broadcast adapter SPI, written without macros:

```rust
pub trait BroadcastAdapter: Send + Sync + 'static {
    fn publish(&self, target: Target, frame: Bytes) -> BoxFuture<'static, Result<(), BoxError>>;
    fn subscribe(&self, node: NodeId) -> BoxStream<'static, (Target, Bytes)>;
}
```

The adapter is configuration on the module: `WsModule::for_root()` binds the in-memory adapter, and `WsModule::for_root().broadcast(fw_ws_redis::Redis::url("redis://.."))` binds Redis's. `fw-ws-redis` ships the adapter value and no module: a second module binding `dyn BroadcastAdapter` beside the first would be `DuplicateBinding` at `wire()`, and override exists in `TestApp` alone. `Rooms::to_*` and `RoomsIn::to_*` answer a `Broadcast`, whose `except(ids)` narrows it and whose `emit(event, &data)` answers `Result<(), BroadcastError>`. The frame travels between processes as JSON, `{"event","data"}`, whatever the gateways' codecs: each process re-encodes it per gateway on delivery, with that gateway's event field and codec, so one publish serves gateways of both codecs and either event field. The cost is on a MessagePack gateway, which receives the MessagePack form of the JSON value, so a byte string arrives as an array of numbers. The Redis adapter's channels are `fw:ws:room:<room>` for a room, `fw:ws:node:<node>` for a client, published to the process its id names, and `fw:ws:all` for everyone, each message the target as JSON, a newline, then the frame; a process subscribes to its node's channel and to `fw:ws:all` and pattern-subscribes to `fw:ws:room:*`, filtering rooms against its own members on delivery, since the SPI learns of no membership change; a lost subscription connects again after one second. Each process delivers to its own local members, and room membership stays local to each process by construction. Delivery is best effort and ordered per sender within one process. The API is identical in both modes.

### 5.1 API [28][29]

```rust
#[routes]
#[guards(rpc = ServiceTokenGuard)]
impl InvoicesController {
    #[fw_rpc::message("invoices.create")]                                  // request-reply
    async fn create(&self, req: Payload<NewInvoice>, h: CallHeaders) -> Result<Invoice, BillingError> { /* ... */ }

    #[fw_rpc::event("user.created")]                                       // fire-and-forget
```

The call shape comes from the signature's _types_, read by two probes and never from its spelling: an `Inbound<T>` parameter means a streamed request, and a stream return means a streamed reply. The request side is one autoref-ranked probe per parameter, so an alias of `Inbound` counts. The reply side is a probe over the generated call closure's future output, `fn shape_of<F, Fut, R>(_: &F) where F: Fn(..) -> Fut, Fut: Future<Output = R>`, which autoref-probes `PhantomData<R>` for `R: Stream` and for `Result<S, _>` with `S: Stream`; an alias and an opaque `impl Stream` are both just bounds on `R`, so the probe sees through either, and no attribute overrides it. Reading `Stream` out of the return type as written is the technique the SSE design ruled out, and a stream behind an alias read that way would mount as unary and fail at the first call. An output type the probe cannot resolve to a stream through its bounds, a projection on a controller's type parameter, reads as unary too; an opaque type, an alias and a boxed stream all resolve. The closure the probe reads is never called and costs one type-check of the call per handler; its body diverges at each parameter it never reads, so the `let` it sits in carries `#[allow(unreachable_code, clippy::diverging_sub_expression)]`, and a user's `clippy -D warnings` passes over it (§1). An event is one payload answered by nothing. A stream reply on an `#[event]` handler fails to compile at the return type, the shape probe answering a type the attribute requires to be `()`, as the metadata probe refuses a mismatch (X24). The shape is also recorded on the `HandlerSpec` (X3) at mount, where `prepare` refuses an `#[event]` handler of any shape but unary, an `Inbound<T>` parameter or a stream reply alike, which covers a handler mounted without the attribute. A bare `Bytes` parameter is the payload, as `Payload<Bytes>` is. The payload kind is recorded on the handler value: the attribute runs one autoref-ranked probe per `Payload<T>` parameter, `Payload<Bytes>` and `Bytes` answering `PayloadKind::Binary` and every other type `PayloadKind::Serde`, as the HTTP attribute's probe records `Host<T>` (§3.8), and `prepare` reads it through `MountedHandler::handler::<RpcHandler>()`; a handler value not built by `#[fw_rpc::message]` or `#[fw_rpc::event]` is refused there. `Shape` carries no payload kind, since three of the four transports have none. A streamed reply that needs the controller takes `self: Arc<Self>` (§2.3).

`fw_rpc::Reply` is the transport's `Transport::Reply`, an enum `None | One(Data) | Many(Tracked<BoxStream<'static, Result<Data, BoxError>>>)`, `Data` a payload already encoded by the link's codec, shaped as WebSocket's is (§4.1). A handler returns a `Reply`, a `Data`, any `Serialize` value, `()`, a stream of `Result<U, E>` with `U: Serialize` and `E: Into<CallError>` or `E = BoxError`, or a `Result` of any of those. `IntoReply<Rpc>` is implemented for `Reply` and `Data` alone; the value side of the handler's probe is the crate-local `Answer<M>` of §4.1's shape, its markers `AsReply`, `AsData` and `AsStream<M>`, the last carrying the item error's own marker so a domain error keeps its kind on the late path and a `BoxError` travels as it stands. `()` takes `AsData` and is answered as no payload. A stream of bare items is not an answer, and a type meeting two markers is ambiguous at the handler. An error handler claiming an error builds its reply through the context: `RpcCx::reply(&value) -> Result<Reply, IntoReplyError>` encodes a `Serialize` value with the link's codec as the call's one `res`; `RpcCx::reply_stream(items) -> Reply` takes a stream of `Result<U, E>` with `U: Serialize` and `E: Into<CallError>` as the reply stream, each `Ok` encoded and written as `item`, an `Err`, or an item the codec refuses, taking the late path and ending the stream; `RpcCx::codec() -> Codec` is the link's codec itself; and `Reply::None` is the empty answer. A handler's `Serialize` value goes through `reply` and its stream through the encoder `reply_stream` uses, so a value an error handler answers travels as a handler's does, on a CBOR link as CBOR. The constructors sit on the context rather than on `Reply` because the encoding is the link's, which the context holds. `RpcCx` implements no `FromCall<Rpc>`, so a handler cannot take `cx: RpcCx` as a parameter where HTTP's and gRPC's take theirs (§3.1, §6.1); an error handler receives it as `&RpcCx`, and a handler reads its execution through `ExecutionRef`. An unhandled pattern on TCP and UDP goes through `recover(None, ..)` as a `CallError` of kind `Unavailable` whose source is `fw_rpc::NoHandler`, a public marker, so an error handler tells it from a handler's own `Unavailable`.

### 5.2 One wire grammar [30][32][33]

Frames, defined here since no specification governs them. `t` carries the kind's name as written in the first column:

```
req     {t:"req",id,p,h,d}      one request, unary or server-streaming
evt     {t:"evt",p,h,d}         event, no reply
res     {t:"res",id,d}          single reply
err     {t:"err",id,e:{kind,message,details}}
item    {t:"item",id,d}         reply-stream item
end     {t:"end",id}            reply stream ended cleanly
open    {t:"open",id,p,h}       start a streamed request
in      {t:"in",id,d}           request-stream item
in_end  {t:"in_end",id}         request stream ended
cancel  {t:"cancel",id}         caller gave up: fires ClientCancelled
credit  {t:"credit",id,n}       flow control, reserved (below)
goaway  {t:"goaway"}            server draining: no new calls on this connection
```

`id` is a `u64` the caller allocates per connection on TCP and UDP; the brokers carry the correlation natively and need none in the body. Reserved headers: `deadline-ms` (remaining time, which becomes the execution deadline) and `traceparent` (W3C Trace Context). A `deadline-ms` that does not parse sets no deadline. When the deadline passes first, the pipeline is dropped, the execution is cancelled with `Deadline`, and the error handlers run with a `Timeout` `CallError` under `Server::timeout_grace` (§2.4), their answer the reply and an unclaimed `Timeout` the `err` of kind `timeout`; when the grace passes first, that `err` is written without them. A deadline passing while a streamed reply is written ends it with `err` of kind `timeout`, offered to no error handler (§2.4). A stream the error handlers answer after the deadline, a `Reply::Many`, is dropped unread and the call answers that `err`, the drop logged at `warn` with the pattern and the handler; a link carrying no streamed reply answers `timeout` there as every other link does, its capability check never reached.

**Codecs.** Every link is JSON at `Default` and declares `binary: false`. `codec = cbor` on a link's builder selects CBOR through `ciborium` and declares `binary: true`; the choice is the link's, so a JSON link stays readable from any client. TCP frames are length-prefixed: a 4-byte big-endian length, bounded by the link's `max_frame`, so an oversized prefix closes the connection before the body is read. UDP carries one frame per datagram.

**What travels on a broker.** TCP, UDP and Redis carry the whole frame: the first two have no native correlation, and Redis Pub/Sub carries neither headers nor a reply address. On NATS, AMQP, MQTT and Kafka the request lane carries the payload: `d` travels as the message body, `p` is the subject, queue or topic, `h` travels as the broker's own headers (NATS headers, AMQP headers, MQTT v5 user properties, Kafka headers), and `id` is the broker's correlation (the `_INBOX` reply subject, `correlation_id`, Correlation Data, the reply header). A body arriving without a reply address is an `evt` and one with it a `req`, so `nats req order.create '{..}'` from the CLI reaches a handler. The reply lane carries the envelope, `res`, `err`, `item` and `end`, as the body of each reply message, since a stream needs its kinds. The frame kinds the body alone does not tell travel in a reserved header, `fw-t`: `open` goes on the request lane as an empty body with `fw-t: open` and the reply address, the server holds the call, answers a header-only `fw-t: opened` on the reply lane and then delivers `open`; `in`, `in_end` and `cancel` go on one control lane per link that every server instance reads outside the competing group, the subject `fw.rpc.control` on NATS, a fanout exchange of that name with an auto-delete queue per instance on AMQP, the topic `fw/rpc/control` outside `$share` on MQTT, and the topic `fw.rpc.control` assigned in full from its end on Kafka, each message carrying the call's native correlation, each instance acting on those naming a call it holds, since the request lane hands a call to one instance of the group and these have to reach that instance. The client queues a streamed request's control frames until `opened` arrives; a `cancel` of a unary or server-streamed call is published at once, and one that overtakes its `req` finds no held call, is dropped, and the call runs to its end. The costs are that every instance receives every control message, and that a client stream waits one round trip before its first item. Redis carries the whole frame and needs no `fw-t`: a `req` or `open` carries the caller's reply channel as the reserved header `fw-reply` in `h`, removed before a handler reads the headers; each caller offsets its ids by a random `u64` base so two callers never share one; `in`, `in_end` and `cancel` travel on the channel `fw:rpc:control`; and no handshake is needed, since one publisher and one Pub/Sub connection deliver in order. The conformance suite's wire assertions follow this split per link.

**A pattern nothing handles** is `Unavailable` where the link signals that nothing is listening, and the client's `Timeout` where it cannot, with an `ErrorInfo` whose `reason` says what the link knows. TCP and UDP answer server-side, since the server receives the frame: `err` of kind `unavailable`, `reason: "pattern_unhandled"`, message "no handler for pattern `x`". On the brokers the subscription, queue or topic is the routing table, so a request for an unhandled pattern never reaches this server, and `RpcClient` maps each link's "no destination" signal to the same kind with `reason: "no_destination"`: NATS no-responders (a client-side 503 status since NATS 2.2); a Redis `PUBLISH` receiver count of zero; an AMQP `basic.return` on a `mandatory` publish, which lapin surfaces through `wait_for_confirms`, so the RabbitMQ link runs its client channel in confirm mode, and which fires for a pattern no server ever declared alone, since a pattern's queue is declared neither auto-delete nor exclusive and outlives the server that declared it, so a request for a pattern served once waits in the queue for the next instance and the caller sees its own `Timeout` though the link declares `miss_signal`, a hold the link declares as `Capabilities::holds_unserved` beside it (an auto-delete queue would lose the requests it holds when its last consumer cancels, which the drain does); an MQTT v5 PUBACK with reason code 0x10 "No matching subscribers" at QoS 1 and PUBREC 0x10 at QoS 2. Two cases carry no signal. MQTT at QoS 0 acknowledges nothing. Kafka answers `UNKNOWN_TOPIC_OR_PARTITION` only where the broker's `auto.create.topics.enable` is off; with it on, the default, a publish to an unhandled pattern creates the topic and the client waits to its timeout. There the miss is the client's own `Timeout`, and no mapping changes that. `Capabilities::miss_signal` declares which case a link is, and the conformance suite asserts `Unavailable` where it is `true` and `Timeout` where `false`. The Kafka link creates its handler topics at `bind`, as a stopped server's topic then still exists and a miss on Kafka is `Timeout` in every case the documentation names, and it then commits the group's offset at each handler partition's end where the group has none: a partition the group has never settled has no committed offset, and under `auto.offset.reset=latest` each assignment of it starts at its end, so an event produced while a rebalance moved the partition, or while no instance consumed, would sit behind the point the next owner starts at. Anchored, a request produced while no instance consumes, or while a rebalance moves its partition, waits for the next owner, which the link declares as `holds_unserved`. Kafka accepts that commit only while the group has no member, so it anchors a topic only when the group's first instance binds; an instance joining a running group leaves the offsets to the instances already there and logs the refusal at `debug`. A handler added in a deployment that rolls out while the group runs gets a topic with no committed offset: each assignment of its partitions starts at their end until a handler there settles a record and the next auto-commit records it, and a request produced to that topic before its first assignment, or during a rebalance, is skipped and its caller sees its own `Timeout`. Stopping every instance before starting the new version anchors it. None of the signals tells "no handler" from "server down", which is why the kind is `Unavailable` and not `Unimplemented`; the latter would be false whenever the server is down. The suite asserts the kind and accepts either reason. An unhandled _event_ is logged and counted in a server-local counter, and on brokers it's acknowledged as rejected, so it can't loop on redelivery: AMQP `basic.reject` with `requeue = false`, which routes to a dead-letter exchange if one is configured; Kafka commits the offset; MQTT has nothing beyond the QoS acknowledgment; NATS and Redis acknowledge nothing. A handled event is acknowledged on `Ok`, rejected without requeue on an error, and left unsettled when shed, refused during the drain or cancelled otherwise, so the broker redelivers it. An `#[event]` whose `deadline-ms` passes is offered to the error handlers under the grace as a request is: an `Ok` from them acknowledges the event, and an error, logged at `warn`, or the grace running out rejects it without requeue; a request sent to an event handler and claimed this way answers an empty `res`, as a completed one does. A frame of the wrong kind for its pattern, `req` or `evt` to a streamed-request pattern, or `open` to a single-payload or event pattern, reaches the error handlers through `recover(Some(handler), ..)` as `BadRequest`. A `req` to an `#[event]` handler runs it and answers an empty `res`; an `evt` to a `#[message]` handler runs it and drops the reply, so `nats req user.created` reaches an event handler.

**Delivery to two instances** differs per broker, and `Capabilities::delivery: DeliveryMode { Competing, FanOut, Addressed }` declares it. TCP and UDP are `Addressed`: the caller named the server. AMQP queues and Kafka consumer groups compete by construction. A request published on NATS reaches every plain subscriber, and MQTT delivers to every subscriber, so two instances would each answer one request; the NATS link subscribes through a queue group and the MQTT link through a shared subscription, `$share/<group>/<filter>`, which makes both `Competing`. The group defaults to the application's root module's full type path, `format!("{:#}", app.root().name())` read in `Link::prepare`, and is overridden with `.group(..)` on the link: two instances of one application share a group, and two different applications on one broker whose patterns overlap never compete for each other's requests, which a fixed default name would let them do without an error anywhere. The default is sanitised per broker, whitespace, `*` and `>` on NATS and whitespace, `/`, `+` and `#` on MQTT, and a `.group(..)` the broker would refuse fails `prepare` naming the setting. Kafka's consumer group defaults to the same path. A CONNACK announcing no shared-subscription support fails the MQTT link's `bind`, naming the setting, since the declared mode would be false. Redis Pub/Sub has no competing mode and stays `FanOut`, documented; `RpcClient` drops a second reply for an `id` it already answered. The conformance suite's two-instance scenario asserts the bound the declared mode gives.

**What a caller sees is uniform** for every failure a link can signal. `RpcError` exposes a kind from §2.4 and maps link-level failures the same way everywhere: no responders, a lost link, or a broker refusal map to `Unavailable`, a client timeout maps to `Timeout`, and an oversized payload maps to `BadRequest` with `ErrorInfo { reason: "payload_too_large" }`. The one condition that differs is the miss above, where a link without a signal answers `Timeout`, and the difference is declared rather than discovered.

**Binary payloads.** `Bytes` and `Payload<Bytes>` travel raw inside CBOR frames. A JSON link declares `binary: false`. A handler with a binary payload on such a link is refused in `prepare`, from the `PayloadKind` on its handler value (§5.1), with a `Configure` error naming the pattern and the link. A client call with one is a runtime value `prepare` cannot see; it fails before any I/O with an `RpcError` of kind `BadRequest` and `ErrorInfo { reason: "binary_unsupported" }`.

**Flow control.** `credit` is a reserved frame kind: a window on NATS and Redis needs both the client and the server to implement it, and the mechanism is deferred, so no link sends `credit` and every link honours the grammar that names it. `max_inflight` sheds on every link. Where the broker offers flow control it is used too: AMQP prefetch, set per consumer (`basic.qos` with `global = false`) to `max_inflight`'s `Max(n)`, and to 64 under `Default` or `Unlimited`, so the two bounds cannot contradict each other; and pausing Kafka partitions. The frozen `Link` gives a link no path to the server's settings, `prepare` taking the app and `listen` the patterns, so the server hands the count over: `Link::max_inflight(&mut self, count: Count)`, defaulted to nothing, is called by `Server::prepare` beside `Link::prepare`, and the RabbitMQ link implements it to set its prefetch; no link carries a prefetch setting of its own.

**Conformance.** `fw-rpc-conformance` runs one scenario list against every link through a `Broker` trait each link crate implements in its `tests/`: `type Link: Link`; `start()` once per scenario, so no state leaks between them, each start answering a broker or a namespace no other scenario shares, since every scenario uses the same patterns and the stamped tests run in parallel; `link(&self)` for the server; `client_link(&self)` for the client, defaulted to `link()`, for an environment that puts something between the two, every link it answers declaring the capabilities `link` does; `disrupt(&self)` severing the client's connection however the environment allows; `outage(&self) -> Option<Outage>`, `None` unless declared, the client's last outage as the environment observed it, `Outage { shut, reopened }` being when the cut's connections had all ended and when the environment first let one through again; `client_connections(&self) -> Option<usize>`, `None` unless declared, how many connections the client's link holds through the environment; `PARALLEL: Option<NonZeroUsize>`, `None` unless declared, how many scenarios hold an environment at once, each stamped test taking a slot before `start` and holding it until the scenario has returned and dropped its environment; and `budget()`, a `Budget` of `boot`, `settle` and `recovery` durations a slow broker raises. One macro stamps every scenario per implementation, and `conformance_suite!(BrokerType; not_applicable { scenario: "reason", .. })` declares the scenarios that cannot apply to a link under the rules the HTTP suite states (§3.8): stamped `#[ignore = "not applicable: <reason>"]`, a declared name that is no scenario a compile error, a declared scenario failing when run. `relay::Relay` is the TCP relay a `Broker` puts in front of its client: `Relay::start(upstream)` on a loopback port of its own, or `Relay::bind()` and `Relay::listen(listener, upstream)` for an environment that has to name the relay's address before it knows the upstream one, a Kafka broker advertising the relay as its listener; `addr()`; `cut() -> usize`, closing every connection through it and answering how many, the relay accepting on; `cut_for(outage) -> usize`, which also closes each connection accepted for `outage` from then; `open() -> usize`, the relayed connections whose two directions have not both ended, which `client_connections` answers on every relay-carried link, a connection ended by a reset counting as ended like one ended by a FIN; and `last_outage() -> Option<Outage>`, the last `cut_for`'s outage, `shut` recorded once every connection it closed had ended and `reopened` at the first connection relayed after that, which `outage` answers on Kafka. `relay::reachable(addr, within)` connects until one succeeds, since a container's forwarded port can refuse connections for a moment after the broker inside reports ready. Each broker link's suite runs against a broker in a container per scenario behind the link crate's `integration` feature, the server link on the broker's forwarded port and the client link through a relay; the stamped tests run in parallel, bounded by `PARALLEL` where the `Broker` declares one, and one shared broker with a topic and group namespace per scenario is not built. Kafka declares four: a container per scenario keeps every scenario's group offsets, control topic and reply topics apart and the recovery scenario's relay cut away from another scenario's client, and a container exiting before its ready line fails its scenario rather than retrying, the exit being a symptom of a host running short. CI's broker job runs the NATS, Redis, MQTT, RabbitMQ and Kafka suites on every push, one crate per step. TCP's suite runs its client through a relay too, and is stamped twice, once on a JSON link and once with `Tcp::new(addr).codec(Codec::Cbor)` on both sides: every other stamp runs a JSON link, so the CBOR stamp is where a payload encoded with a codec other than the link's fails. The suite's `report(error: &(dyn Error + 'static)) -> String` joins the error's text with each cause under `source()`, a colon and a space between, skipping a cause whose text the message already carries, and every startup path of a suite panics with it, the broker container's start and port mapping, the TCP and UDP probe sockets, the relay's bind and address, the server's `listen` and the client's wiring and connect; the server keeps how its `serve` returned, and the readiness wait names that rather than the last call's outcome, so a scenario failing while its environment starts says what failed and why. A container that fails to start answers no handle, so its logs are not collected. UDP's declares the recovery scenario not applicable, holding no connection to lose, and answers no connection count, holding none to count.

No scenario passes on silence. The client's own `Timeout` passes only where it is the declared answer: a scenario about the client's timeout or `deadline-ms`, a call nothing takes on a link without `miss_signal`, and a call reaching a draining server on a link declaring `holds_unserved`, where an event emitted during the drain then has to reach the next instance. and two instances under the declared `DeliveryMode`, one instance on an `Addressed` link, where a second cannot share the address. ### 5.3 Links [30], written without macros

```rust
pub trait Link: Send + Sync + 'static {
    const NAME: &'static str;
    fn capabilities(&self) -> Capabilities;

    /// What can fail before any I/O: endpoint text, `Tls`, a broker URL. Called from `Server::prepare` with the app,
    /// whose root module's full type path is the default competing-consumer group (§5.2).
    fn prepare(&mut self, app: &AppHandle) -> impl Future<Output = Result<(), BoxError>> + Send { async { Ok(()) } }
    /// The server's in-flight bound, handed over beside `prepare`; the RabbitMQ link sets its prefetch from it (§5.2).
    fn max_inflight(&mut self, count: Count) {}
    /// Server side: subscribe to the given patterns, all-or-nothing. Called from `Server::bind`.
    fn listen(&self, patterns: &[Pattern]) -> impl Future<Output = Result<Inbound, BoxError>> + Send;
    /// Client side: connect. `RpcClient` calls it lazily, on first use.
    fn connect(&self) -> impl Future<Output = Result<Outbound, BoxError>> + Send;
    /// The link's own close signal (below). Called from `Server::drain`.
    fn drain(&self) -> impl Future<Output = ()> + Send;
    fn close(&self) -> impl Future<Output = Result<(), BoxError>> + Send;
    /// The addresses bound, for `App<Bound>::addresses()`; a broker link answers none.
    fn bound(&self) -> Vec<BoundAddr> { Vec::new() }
}

pub type Inbound = BoxStream<'static, Delivery>;
pub struct Delivery { pub frame: Frame, pub reply: Option<ReplyPath>, pub ack: Ack }   // `reply` is `None` for an event, and for a `cancel` the link raises itself
impl ReplyPath {
    pub fn new(send: impl Fn(Frame) -> BoxFuture<'static, Result<(), BoxError>> + Send + Sync + 'static) -> Self;
    pub fn peer(self, peer: SocketAddr) -> Self;                                         // the caller's address, seeded as `LinkInfo::peer`; TCP and UDP set it
    pub fn send(&self, frame: Frame) -> BoxFuture<'static, Result<(), BoxError>>;
}
impl Ack {
    pub fn new(settle: impl FnOnce(bool) + Send + 'static) -> Self;                      // `true` acknowledges, `false` rejects without requeue
    pub fn none() -> Self;                                                               // a broker that acknowledges nothing
    pub fn ack(self); pub fn reject(self);
}

pub struct Outbound {
    pub send: Box<dyn Fn(Pattern, Frame, Option<ReplyTo>) -> BoxFuture<'static, Result<(), BoxError>> + Send + Sync>,
    pub replies: BoxStream<'static, Frame>,
}
pub struct ReplyTo { pub id: u64 }                                                       // the correlation a link maps onto its own mechanism

#[non_exhaustive]

    pub max_frame: Option<u64>,       // `None` for no limit of its own, or one not yet read off the broker
    pub ordering: Ordering,
    pub shapes: &'static [Shape],     // `ALL_SHAPES`, or `UNARY_ONLY`

}

```

Four rules bind every link beyond its signatures. The `id`s a link delivers are unique among the calls in flight on one inbound stream, so an `in`, `in_end` or `cancel` reaches the call its `req` or `open` started: TCP and UDP map each caller's ids to ids of their own and write the caller's back on the reply path, and a broker link keeps a table from the native correlation to a local `u64` that the client rewrites back. A link that loses a caller with calls in flight, a TCP connection closing, delivers `cancel` for each with `reply: None`, which the server reads as `Disconnected`; a `cancel` the caller sent carries its reply path and is `ClientCancelled`; no broker loses one caller apart from the others. A reply `send` that fails with `FrameTooLarge` is replaced by an `err` of kind `internal` under the same `id`, and any other send failure means the caller is gone and cancels the call `Disconnected`, logged at `debug`. A frame the link cannot encode fails `send` without `FrameTooLarge` and is read the same way, so its caller sees its own `Timeout` and no `err`; telling an encoding failure from a closed lane needs the send error to say which it is, which it does not say. The codec is read off `Capabilities::binary`, CBOR when `true` and JSON otherwise, through a crate-private `Codec::of`; a third codec needs a field. `new` sets `holds_unserved` and `durable_replies` to `false`. RabbitMQ and Kafka declare the first, an AMQP queue and a Kafka topic holding what no consumer takes, and Kafka alone the second, its reply topic holding what a disconnected client has not read. Each names what a caller sees: under `holds_unserved` a caller reaching a draining or stopped server sees its own `Timeout`, and `miss_signal` covers only a pattern never subscribed; under `durable_replies` a call waiting when the client loses its connection is answered once the client reconnects, where every other link fails it `Unavailable`.

`fw_rpc::Server<L: Link>` implements the core `Server`. `Server::new(link)` carries `max_inflight: Count`, refused at `Max(0)` in `prepare` with the HTTP server's hint, and `timeout_grace: Bound`, one second at `Default`, the window the error handlers get after a `deadline-ms` passes (§5.2), refused at `After(Duration::ZERO)` with the HTTP server's hint; `max_frame: u64` is the link's. In `prepare` it calls `Link::prepare` with the app and `Link::max_inflight` with its count, then checks each handler's shape against `capabilities()`, so a streamed shape on UDP is a `Configure` error, and each handler's `PayloadKind` against `binary`; a frame bigger than `max_frame` is refused at runtime with the error above. `bound` reports what the link reports, so a TCP or UDP server on port 0 shows its port in `App<Bound>::addresses()`. Over `max_inflight` the shed `err` of kind `unavailable` carries a `RetryAfter` detail of one second.

The links are built as `Tcp::new(endpoint)` with `.tls(Tls)`, `.codec(Codec)` and `.max_frame(u64)`; `Udp::new(endpoint)` with `.codec`; `Nats::url(..)`, a comma-separated list for several servers, with `.group(..)` and `.codec`; `Redis::url(..)` with `.codec`; `RabbitMq::url(..)` with `.codec`; `Mqtt::url(..)` with `.group`, `.qos(QoS)` and `.codec`; and `Kafka::brokers(..)` with `.group`, `.reply_topic(..)`, `.topic_partitions(i32)`, `.replication_factor(i32)` and `.codec`.

Each broker's TLS is its client library's, selected by the URL scheme in the right column and enabled as a feature of the link crate; TCP takes `fw_net::Tls` (§2.7) on its server side, and its client speaks plain TCP. Links connect lazily: the server side at `bind`, the client side on its first call. A broker link connects once, in `listen` or `connect`, and does not retry: an unreachable broker fails `bind` as `StartupError::Bind`, one report at startup, and a retry window is a `Bound` to add when a deployment needs one. After `bind`, a server side keeps its own reconnect: async-nats, lapin with auto-recovery on the server connection, and librdkafka reconnect inside their clients, and the Redis and MQTT links reconnect in their read loops. A client side carries no call across a reconnect. Each link but Kafka's ends its reply lane when its connection drops, NATS on async-nats's `Disconnected` event, Redis when its Pub/Sub stream ends, MQTT on a connection error after the first CONNACK, and RabbitMQ on its reply consumer's error, its client connection opened without lapin's auto-recovery, since a recovery that re-consumes `amq.rabbitmq.reply-to` on a new channel loses the replies addressed to the old one. A reply published during the gap is lost on all four, and ending the lane reports that loss; a reconnect finishing before the reply would answer short outages and leave longer ones to the caller's `Timeout`, with nothing reporting what was lost. `RpcClient` then fails every call waiting on the lane `Unavailable`, and the next call connects through a fresh `Link::connect` (§5.4). Kafka's client keeps librdkafka's reconnect: its reply topic holds a reply published while the client is out, read once it reconnects, which the link declares as `durable_replies`. Load shedding refuses with `err` of kind `unavailable` over the server's in-flight limit.

**Shutdown:** `Link::drain` is the link's own close signal. TCP closes its listener and sends `goaway` on every connection without waiting for room in a writer's queue, and finishes the calls in flight. UDP sends nothing and keeps receiving, so a `cancel` still arrives. NATS drains each pattern subscription; async-nats removes the subscription on its connection task's next poll, without waiting for the server's `PONG` to the `UNSUB`, and discards a message for a removed subscription, so a request the server routed to this instance before it processed the `UNSUB`, still in flight at the removal, never reaches the link and its caller sees its own `Timeout` rather than the drain's `Unavailable`; async-nats's public API offers no way to hold the subscription for the `PONG`, and that window is a stated limit of the NATS link's drain. AMQP cancels its consumers (`basic.cancel`). MQTT unsubscribes each `$share` filter and resubscribes only the control topic after a reconnect. Kafka pauses its assignment and commits asynchronously. The control lane stays open and the inbound stream ends once the draining server holds no call, since a held call can still receive its items or a `cancel`. In-flight calls then drain under the core's rules, and `Link::close` runs under the core's `close` bound, closing the connections and committing synchronously on Kafka. On NATS, `close` subscribes each connection still connected to a fresh inbox, publishes an empty message there and waits for it to come back before draining the connection: async-nats's `publish` and `drain` only queue commands for the connection's task, and a task that finds its command channel closed exits without writing what it already took, so a `close` that drained and dropped the last `Client` at once could lose the replies of the calls the drain let finish. NATS routes one connection's messages in order, so the echo shows every earlier one was routed; `Client::flush` would show async-nats's own write and not the server's routing. A connection that drops during the round trip leaves `close` waiting until the core's `close` bound drops it, recorded `ShutdownFailure::Close` with `TimedOut`. On Kafka, `close` drops each consumer on a thread of its own: a librdkafka consumer's drop leaves the group and polls until the broker confirms, about a tenth of a second with the broker up and without bound once it is gone, and on a runtime worker it stalls every task scheduled there, while a `spawn_blocking` task would hold the runtime's shutdown instead; a thread that cannot be spawned drops the consumer where it is, logged at `warn`. The client side's `close` signals its reply router and awaits it, the router dropping the reply consumer before it ends, so the consumer leaves its group while the broker is there to answer, and then takes the producer out of the slot the send closure reads and awaits its drop on a thread of its own, librdkafka purging, flushing for up to 500 ms and destroying the handle, which closes the client's last connection; a send afterwards fails until the next call connects anew. A router dropped before it ends, its client never closed and the runtime shutting down, still drops its consumer on a thread of its own. The server's group and control consumers are dropped with their last reference and not awaited: once the broker is gone that drop blocks without bound, holding its thread and librdkafka's and neither the tokio runtime's shutdown nor the process's exit. On TCP, `close` advances a client epoch every client connection subscribed to when it was made: each writer, owned by the link, shuts its half of the socket on it and is awaited, and the reply lane ends with it, so the peer reads the end of the connection, the waiting calls fail `Unavailable`, and a call made afterwards connects on a new subscription. On UDP the reply lane owns the client socket and ends on the same epoch, releasing the socket; the send closure holds a `Weak` and fails once it cannot upgrade, and a call made afterwards binds a new socket. On Redis the client's `close` takes the `PUBLISH` connection out of its slot beside aborting the Pub/Sub lane, the `RpcClient` keeping a connection's send half until its next call replaces it.

### 5.4 Client [31]

```rust
#[module(imports = [RpcClientModule::for_root(fw_rpc_nats::Nats::url("nats://bus:4222")).timeout(Bound::After(Duration::from_secs(2))).keyed::<Billing>()])]
pub struct OrdersModule;

#[injectable]
pub struct Checkout { billing: Dep<RpcClient, Billing> }

impl Checkout {
    async fn finish(&self, order: &Order) -> Result<Invoice, RpcError> {
        self.billing.request::<_, Invoice>("invoices.create", &NewInvoice::from(order))
            .header("tenant", order.tenant())
            .timeout(Duration::from_secs(2))
            .await
    }
}
```

The client offers `request(pattern, &req)`, `emit(pattern, &data)`, `stream(pattern, &req)`, which answers a stream, `send_stream(pattern, items)` and `duplex(pattern, items)`, each an `IntoFuture` builder carrying `.header(name, value)`, `.timeout(Duration)` and `.within(&exec)`. The module's `timeout` is a `Bound`, five seconds at `Default`; the per-call `.timeout(d)` is a `Duration`, a value no startup check sees. A module has no `prepare`, so `RpcClientModule::timeout(Bound::After(Duration::ZERO))` is recorded through `ModuleDef::try_value` and reported by `wire()` beside every other wiring error, naming the link and pointing at `Bound::Unbounded`; a zero on a module is visible there, and `wire()` comes before `prepare`, so one report still precedes any socket. Each `for_root` is its own module, labelled `RpcClientModule`, so two clients of one link type are two imports; the client is a singleton reading `Dep<dyn Timer>`, so an application without a `Timer` fails `wire()`. The binding's `on_destroy` hook calls the link's `close`, so the client's connections end with the app rather than when the runtime drops it, a failure logged at `warn`; the calls waiting on the link fail `Unavailable`, and a call made after the hook connects again. Every link's `close` reaches the client side: the conformance suite's client-close scenario holds each to it (§5.2), and the TCP and UDP links' own tests add what the suite cannot see, a raw peer reading a clean FIN with nothing written after the call's frame on TCP, and the client's address binding again on UDP. A reply lane that ends fails every call waiting on it `Unavailable`, and the next call connects again through `Link::connect`; each broker link but Kafka's ends its lane when its connection drops (§5.3), and Kafka's holds the reply on its topic for the reconnected client. On Kafka the hook's `close` waits for the reply router to drop its consumer, about a tenth of a second with the broker up, and then for its producer's drop, which flushes queued records for up to 500 ms; with the broker gone the consumer's wait is unbounded on the drop's own thread, and the hook's bound ends it. A timeout uses the app's `Timer`. Dropping a stream or a pending request sends `cancel`, from a spawned task, and not at all outside a tokio runtime. There is no ambient execution, so a call made inside one says so: `.within(&exec)` stamps `deadline-ms` with the remaining time, refuses a deadline already passed as `Timeout` before any I/O, bounds the wait by the shorter of the timeout and the remaining time, and cancels the call when the execution is cancelled. A stream call answered by a single `res` yields that value and ends; a failure in a streamed request's items fails the call and sends `cancel`. The TCP client resolves its endpoint as written, so a client in a `fw dev` child whose address equals the held socket connects to it rather than adopting it (§9).

### 6.1 Generation and API [34][36]

```rust
// build.rs
fn main() -> Result<(), Box<dyn std::error::Error>> {
    fw_build::configure().file_descriptor_set_path("users.bin").compile(&["proto/users.proto"], &["proto"])?;   // a vendored protoc: no system protoc
    Ok(())
}

// src/pb.rs
fw_grpc::include_proto!("users.v1");
```

The build step is `fw-build`: tonic-prost-build over a vendored `protoc` binary, behind a default-on `vendored-protoc` feature that yields to a `PROTOC` environment variable; that meets [34]'s "no system protoc", and a pure-Rust compiler is a later swap behind the same `configure()` API. `configure()` carries `out_dir(..)`, `OUT_DIR` unset, `file_descriptor_set_path(..)`, relative to the package root, `build_client(bool)`, `true` unset, and `compile(&protos, &includes)`. For every RPC method, generation emits the messages (prost), a client (tonic), a file descriptor set (for reflection) and a marker type; no server trait is generated, tonic's generator running with `build_server(false)`, since handlers bind to the markers and the dispatcher calls them by path. The markers are written by a `ServiceGenerator` wrapping tonic's, which prost-build takes through `Config::service_generator`: after each service the wrapper appends `pub struct GetUser; impl fw_grpc::Method for GetUser { .. }` per method under a module named by tonic-build's own snake-casing, `user_service` beside `user_service_client`, so the two agree character for character, the module carrying `#[allow(clippy::module_inception)]`, since a wrapper module named as the service, `mod users { include_proto!("users.v1"); }` for the service `Users`, holds `users::users`, which clippy would report in the user's crate on a module the user cannot rename (§1), and, with clients on, the `fw_grpc::GrpcClient` impl for the client, through which `GrpcClientModule` builds it (§6.3); a message path prost made relative gains `super::`. `fw_grpc::include_proto!("users.v1")` includes `$OUT_DIR/users.v1.rs`, where the markers sit. The descriptor set comes from `file_descriptor_set_path`, and the package's file then ends with `pub const FILE_DESCRIPTOR_SET: &[u8] = include_bytes!(..)` of the absolute path, since a relative one would resolve against `OUT_DIR`; `Server::file_descriptor_set(pb::FILE_DESCRIPTOR_SET)` hands it to reflection (§6.2). The generated code names `tonic`, `tonic-prost` and `prost`, and `prost-types` where a proto uses a well-known type, so the crate running the build step depends on those beside `fw-grpc`.

```rust
pub struct GetUser;
impl fw_grpc::Method for GetUser {
    const PATH: &'static str = "/users.v1.UserService/GetUser";
    const SHAPE: Shape = Shape::Unary;
```

Handlers bind to a marker, and the attribute checks the signature against the marker's types and shape at the concrete site, so a mismatch fails to compile:

```rust
#[routes]
#[guards(grpc = TokenGuard)]                                               // reads a bearer token off `GrpcMetadata`
impl UsersGrpc {
    #[fw_grpc::method(pb::user_service::GetUser)]
    async fn get_user(&self, req: Message<pb::GetUserRequest>) -> Result<Response<pb::User>, UserError> {
        let user = self.users.find(req.0.id).await?;
        Ok(Response::new(user.into()).metadata("x-cache", "miss"))      // reply metadata [35]
    }

    #[fw_grpc::method(pb::user_service::WatchUsers)]
    async fn watch(&self, req: Request<pb::WatchRequest>, cx: GrpcCx)  // the whole request, and the context
        -> Result<impl Stream<Item = Result<pb::UserEvent, UserError>>, UserError> { /* ... */ }

    #[fw_grpc::method(pb::user_service::ImportUsers)]
    async fn import(&self, rows: Streaming<pb::UserRow>) -> Result<pb::ImportSummary, UserError> { /* ... */ }

```

`Message<T>`, `Request<T>` and `Streaming<T>` each declare `CONSUMES_BODY = true`, so a handler taking two of them fails the pairwise check naming both (§2.2). The marker checks are const generics at the concrete site: the attribute writes, beside each `#[method]` handler, a hidden `__fw_grpc_<name>` method taking the same parameters, in which one `ParamProbe::<M, P>` per body-consuming parameter takes `{ streams_request(M::SHAPE) }` and the reply probe takes `{ streams_reply(M::SHAPE) }`, and a mismatch in message type or shape leaves `ParamCheck::matches` or `Checked::checked` uncallable, an E0599 whose type spells what the handler declares beside what the marker requires: `Checked<(Shaped<true>, UserEvent), (Shaped<false>, User)>` is a stream of `UserEvent` returned for a unary method replying `User`. The reply probe is spanned at the return type, the `impl` token for an `impl Stream<..>` return, since on stable a span over several tokens keeps the first one's, and at the method's name for a handler with no return type; spanned at the signature's output as a whole, the caret would sit on the `-` of `->`. A handler reading no message is accepted, its request unread. The hidden method answers a crate-local `Answer`, which the generated call reads as the handler's `IntoReply<Grpc>` value, through a six-arm autoref probe, each arm one reference deeper than the priority reads, the first that applies winning: a `Result` of a reply stream whose error converts into a `CallError`, then one whose error boxes, then a bare stream; then the same three over a reply value. The streams come first, so a type that is both is answered as a stream. The detour exists because a handler answers a prost message or a stream of them, and neither can implement `IntoReply<Grpc>`: a blanket in `fw-grpc` over the foreign `prost::Message` is refused by the orphan rule, and a message `fw-build` wrote cannot cover `()` or a `prost_types` message. What a handler returns, then: the reply message, `()`, `Response<T>` with `.metadata(key, value)` for reply metadata, a stream of `Result<M, E>` with `E: Into<CallError>`, or a `Result` of any of those; the error implements `Classify`, or is a `tonic::Status`, which the probe boxes unchanged and the wire sends as it stands (§6.2). Three public traits name those sets, and `GrpcCx::reply` and `reply_stream` take them (§6.2): `ReplyValue` is a reply of one message, a prost message or `Response<T>` around one, `()` among them as `google.protobuf.Empty`; `ReplyStream` is a reply stream, any stream of `ReplyItem`s or `Response<S>` around one; `ReplyItem` is one item, `Result<T, E>` with `E: Into<CallError>`. Each has one method, `into_grpc` on the first two and `into_item` on the third, and none is sealed: the probe's value arms are blanket over the traits, so a type implementing `ReplyValue` is a value a handler may return. `fw_net::Tls` verifies no client certificate, so a guard that would read the peer's certificate has nothing to read; client authentication is a later `fw-net` item, where it serves every transport at once, and the example guard reads a token.

**How a marker becomes a service.** tonic's generated `UserService` trait is never implemented. `fw-grpc` builds one tower service that dispatches on `:path` to the marker's call. It does not go through `tonic::server::Grpc::unary` and its siblings: those decode the message before the service runs, which would run the guards after a decode, against §2.2, and answer an unencoded `Response<M>` where the pre-dispatch stage's reply is the encoded `http::Response` an interceptor reads. The dispatcher uses the two pieces `Grpc` composes instead, `Streaming::new_request` under the extractors and `EncodeBody::new_server` for replies, so the message is decoded by the extractor that reads it and encoded at the reply. A path off the table answers UNIMPLEMENTED, as the gRPC specification requires; the dispatcher writes it and offers it to no error handler, as HTTP's `OPTIONS` 204 is offered to none. Two handlers for one `PATH` are a `Configure` error.

### 6.2 Wire behavior [35]

- **Engine:** `fw_grpc::Server::new(endpoint)` is an HTTP/2 server over `fw-hyper-serve` (§3.7): `fw-net` endpoints and inherited sockets, `fw_net::Tls` with ALPN `h2`, hyper's `http2::Builder` per connection, so TLS and socket activation have one story and one vocabulary with HTTP. tonic's own `transport::Server` is not used: it owns its socket, its TLS and its limits, which would be a second vocabulary for each.
- **Reply:** `fw_grpc::Reply` is `http::Response<tonic::body::Body>`. An interceptor reads and writes reply metadata through its headers and cannot read the message, which is what lets one enhancer list serve every method of a service. An error handler claiming an error with `Ok` builds that `Reply` through the context, in the three forms a reply takes. `GrpcCx::reply(value)` takes a `ReplyValue` (§6.1), the message or `Response<T>` around it with reply metadata, encoded as a handler returning it is. `GrpcCx::reply_stream(stream)` takes a `ReplyStream`, each `Ok` item written as a message and an `Err` item run through the matched handler's error handlers on the late path and written in the trailers. `GrpcCx::reply_status(status)` is a trailers-only `tonic::Status`, which claims the error when answered with `Ok`; the same `Status` returned as the error is offered to the next handler and sent as it stands when none claims it. The handler path and the three methods share one encoder. They sit on the context rather than on `Reply` because `Reply` is a type alias of `http::Response`, which takes no inherent constructor in `fw-grpc`, and because a stream reply needs the call for its late path. `IntoReply<Grpc>` for `Response<T>` over a message and over a stream would overlap, a foreign type being free to implement both `prost::Message` and `Stream`, and `GrpcCx::reply(impl Into<Response<T>>)` is ambiguous for a `Response<T>` argument between the reflexive `From` and `From<T> for Response<T>`. A stream item's `Err` goes through `dispatch_late` (§2.3) and is written as the trailers `grpc-status`, `grpc-message` and `grpc-status-details-bin`, gRPC's mid-stream error form: once data frames have been sent the status travels in the trailers.
- **Pre-dispatch:** gRPC is HTTP/2, and `http::Request` and `http::Response` are already its types, so `fw_grpc::PreDispatch`, a name for `fw_http::PreDispatch<Grpc>` (X23, §3.4), takes `.apply`, `.apply_for`, `.layer` and `.layer_for` as HTTP's does, scoped by method path (`/users.v1.UserService/*`). A layer that answers with a non-200 HTTP status is not a valid gRPC response, so the transport translates such a response with the specification's HTTP-to-status table and the client receives a proper `grpc-status`:

  | HTTP status        | gRPC code         |
  | ------------------ | ----------------- |
  | 400                | INTERNAL          |
  | 401                | UNAUTHENTICATED   |
  | 403                | PERMISSION_DENIED |
  | 404                | UNIMPLEMENTED     |
  | 429, 502, 503, 504 | UNAVAILABLE       |
  | any other          | UNKNOWN           |

- **Deadlines:** `fw-grpc` parses `grpc-timeout` itself, a `TimeoutValue` of one to eight digits and a `TimeoutUnit` in `H`, `M`, `S`, `m`, `u` or `n`, into the execution deadline; a value off that grammar is logged at `debug` and ignored, and the call runs without a deadline. When the deadline passes first, the pipeline is dropped, the execution is cancelled with `Deadline`, and the error handlers run with a `Timeout` `CallError` under `Server::timeout_grace` (§2.4): their answer is the reply, an unclaimed `Timeout` is DEADLINE_EXCEEDED, and when the grace passes first DEADLINE_EXCEEDED is written without them. A caller past its deadline has stopped waiting, and the handlers still run, because the grace bounds them and running them is what lets an application log, count or reshape its timeouts on every transport alike. The deadline is the caller's and starts when the call arrives, so it covers the unscoped pre-dispatch stage, routing, the scoped stage and `dispatch`: routing records the handler it matched, and a deadline passing after routing offers that handler's tiers then the global ones, one passing before routing the global ones alone, with a context rebuilt from the path, metadata and peer the call arrived with and carrying no request. A caller through tonic's `Channel` wraps every call in its own `GrpcTimeout`, which answers CANCELLED at the same deadline, so a tonic client never reads what the handlers answer; a client enforcing no deadline of its own reads it. When the reply comes first, the deadline moves into its body, which ends with DEADLINE_EXCEEDED trailers if the deadline passes while it streams. The reply the error handlers answer is delivered as a single reply: a trailers-only status as it stands, or a body read under the rest of the grace and written as one data frame followed by its trailers. A body whose bytes run past its first length-prefixed message, or one still open when the grace runs out, is a stream, dropped unwritten for a trailers-only DEADLINE_EXCEEDED, the reply's metadata dropped with it and the drop logged at `warn` naming the path (§2.4); a body failing while it is read answers DEADLINE_EXCEEDED, logged at `debug`. The stream is told by its bytes because `Reply` is an erased `http::Response<tonic::body::Body>`, a body an error handler writes by hand carrying no mark of its shape and `GrpcCx::reply` and `reply_stream` producing the same erased `Reply`, and on the wire a server stream of one message and a unary reply are the same bytes. A stream whose items come readily is ended at its second message, one that yields an item and then waits at the grace's end, and under an `Unbounded` grace the body is read until its end or its second message.
- **Errors:** kinds map to canonical codes per §2.4; `fw_grpc::code_for(kind)` is the table and `fw_grpc::to_status(&CallError) -> Status` the rendering. `CallError::with_grpc_code(i32)` names a canonical code in place of the kind's, `google.rpc.Code`'s number, read back by `grpc_code()`: an error naming a resource that exists writes `.with_grpc_code(6)` for ALREADY_EXISTS where `Conflict` maps to ABORTED, the kind still deciding every other transport's rendering; a code outside 1 to 16, `OK` included, is ignored. The code is an `i32` because `fw-transport` depends on no gRPC crate. A `tonic::Status` returned as the error, by a handler or by an error handler, reaches the wire as it stands: the rendering downcasts what the error handlers left to `Status` before anything else, since `from_boxed` would answer `Internal` for a type it does not recognise, and the error handlers see the `Status` first, so nothing bypasses them; it is the one way to name a code outside the eleven kinds without a `CallError`. `Details` are packed into a `google.rpc.Status` and sent in `grpc-status-details-bin` through tonic-types, whose `ErrorDetails` takes the design's variants one to one: `FieldViolations` through `set_bad_request`, `ErrorInfo` through `set_error_info`, `RetryAfter` through `set_retry_info`, `Help` through `set_help`, and `StatusExt::with_error_details` writes the trailer. `ErrorDetails` holds one of each message, so every `FieldViolations` detail's violations go into the one `BadRequest` and every `Help` detail's links into the one `Help`, and the first `ErrorInfo` and the first `RetryAfter` are kept. `Detail::Json` has no setter: a `prost_types::Value` built from the `serde_json::Value` is packed in a `prost_types::Any` with type URL `type.googleapis.com/google.protobuf.Value` and appended to the `Status.details` list by hand. An error with no details sends no trailer.
- **Cancellation:** `ClientCancelled` fires for every abandonment hyper reports, the call's future dropped before it answered and the reply body dropped before its end (§2.6).
- **Message size and compression:** the extractors decode under tonic's own 4 MiB limit, and a larger message fails extraction as `ExtractError::TooLarge`, INVALID_ARGUMENT; the server carries no message-size setting. A request whose `grpc-encoding` is not `identity` answers UNIMPLEMENTED with `grpc-accept-encoding: identity` before dispatch, as the compression specification prescribes.
- **Load shedding and settings:** `fw_grpc::Server::new(endpoint)` carries `.endpoint(..)` for a further endpoint, `tls: fw_net::Tls`, `max_inflight: Count`, `max_per_connection: Count` and `max_concurrent_streams: Count`, each refusing `Max(0)` in `prepare` with the HTTP server's hint, `handshake_timeout: Bound`, 30 seconds at `Default`, and `timeout_grace: Bound`, one second at `Default`, each refusing `After(Duration::ZERO)` the same way, plus `reflection(bool)` and `file_descriptor_set(&'static [u8])` below. `SETTINGS_MAX_CONCURRENT_STREAMS` bounds each connection, and excess streams get `REFUSED_STREAM`. Over the server's in-flight limit or the connection's, and during the drain, a call gets UNAVAILABLE before an execution opens, with no `Retry-After`; clients treat it as retryable.
- **Health:** `tonic_health::server::health_reporter()` answers the `HealthReporter`, and `GrpcHealth::module()` binds it as `Dep<GrpcHealth>` for an application that sets status per service through `set_service_status`; without the module the server keeps a reporter of its own and health still answers. The known services are those the handlers' paths name. `grpc.health.v1` reports SERVING for every known service after `bind`, overwriting what an init hook set, and at `drain` sets the overall status `""` and each known service NOT_SERVING before the accept loop's drain, so a client polling health stops sending before the GOAWAY. It stays SERVING through the before-shutdown stage, consistent with `is_draining()`. Health and reflection are routed after the unscoped pre-dispatch entries, with no scoped entries and no error handlers, since no handler matched.
- **Reflection:** `grpc.reflection.v1` and `v1alpha`, from the descriptor set `Server::file_descriptor_set(pb::FILE_DESCRIPTOR_SET)` hands over, through `tonic_reflection::server::Builder::configure().register_encoded_file_descriptor_set(..)` and its `build_v1()` and `build_v1alpha()`. Both are added to the route table in debug builds and behind `reflection(true)` in release builds (decision 7). With reflection on and no set, the two services serve, describing only themselves; a set that does not decode is a `Configure` failure.
- **Shutdown:** GOAWAY through `fw-hyper-serve`'s drain, then the core's drain and close.
- **Scope:** gRPC serves on its own port. Nothing routes an `application/grpc` request arriving on the HTTP server's port, or on an embedding host, to the gRPC server. The extension point, if that is ever wanted, is a hand-off like `UpgradeHandler` keyed by path and content type rather than by `Upgrade`, on `Server<B>` and on `Embedded<A>` alike.

## 7. GraphQL [37]

```rust
type ApiSchema = Schema<QueryRoot, EmptyMutation, SubscriptionRoot>;

#[module(
    providers = [
        with = |q: Dep<QueryRoot>, s: Dep<SubscriptionRoot>| Schema::new(q, EmptyMutation, s),   // the schema, `Auto`
        AsyncGraphql<ApiSchema, GqlContext> as dyn Engine,                                      // the engine, under the SPI key, naming its context type
        GqlContext,                                                                             // resolved in this module, per execution
    ],
    exports   = [dyn Engine],
)]
pub struct ApiSchemaModule;

#[module(imports = [
    fw_ws::WsModule::for_root(),                                                               // once per application; the gateway is reachable through it
    GraphqlModule::for_root(GraphqlConfig::at("/graphql").subscriptions("/graphql/ws").engine_from(ApiSchemaModule)),
])]
pub struct ApiModule;

#[injectable(execution)]                                    // built per execution [37]
pub struct GqlContext {
    user: Option<Ext<CurrentUser>>,
    loaders: Dep<Loaders>,
    head: Option<Dep<RequestHead>>,                         // `Some` over HTTP, `None` over the subscription gateway and RPC
}
```

GraphQL names no transport: the specification defines the language, validation and execution, and GraphQL-over-HTTP and graphql-transport-ws are two bindings. The crates follow that split. `fw-graphql` is transport-neutral, holding the `Engine` SPI, `GqlRequest: Deserialize` and `GqlResponse: Serialize`; the two engine adapters depend on it alone, each a `Construct` type reading its schema (`AsyncGraphql<S, C>` reads `Dep<S>`), bound under `dyn Engine` as above so a handler on any transport takes `Dep<dyn Engine>`. `fw-graphql-http` holds the endpoint, the playground and the GraphQL-over-HTTP status rules, and its `GraphqlModule` is the module imported above: it mounts the endpoint controller `.at(path)` and, with `subscriptions(path)`, the `GraphqlWs<Q>` gateway of `fw-graphql-ws` `.at(path)`, both as its own controllers, so `fw-graphql-http` depends on `fw-graphql-ws` and through it on `fw-ws`. The application imports `WsModule` once itself: an import from `GraphqlModule` would make a second `WsModule` identity beside the application's. `GraphqlConfig::engine_from(module)` names where the engine lives: `GraphqlModule` imports that module and reads its exported `dyn Engine`, and a configured module instance works as the import since module identity is by value (DESIGN §8.3). The visibility rule makes the import necessary: a module sees its own bindings, its imports' exports and the globals' exports, and the module that imports `GraphqlModule` is none of those, so without `engine_from` the engine is read from a global module that exports `dyn Engine`, which puts it into every module's view to solve a visibility problem between two. An RPC-only application serves the same engine with an ordinary handler, `#[fw_rpc::message("gql")] async fn gql(&self, req: Payload<GqlRequest>, engine: Dep<dyn Engine>) -> GqlResponse`, and `subscribe`'s stream over RPC's streamed-reply shape.

The engine SPI, written without macros:

```rust
pub trait Engine: Send + Sync + 'static {
    fn execute(&self, req: GqlRequest, exec: ExecutionRef) -> BoxFuture<'static, GqlResponse>;
    fn subscribe(&self, req: GqlRequest, exec: ExecutionRef) -> BoxStream<'static, GqlResponse>;
    fn sdl(&self) -> String;
    fn playground_html(&self, endpoint: &str, subscriptions: Option<&str>) -> Option<String>;   // the engine's own page
}

pub struct GqlResponse { outcome: Outcome, data: Option<Value>, errors: Vec<GqlError>, extensions: Option<Value> }   // serialized without `outcome`; built by `executed(..)`, `request_error(..)` or `failed(..)`
pub enum Outcome { Executed, RequestError, Failed }   // whether execution began, or the server could not begin it, which decides the HTTP status
```

**The context is a type parameter of the engine adapter.** async-graphql takes context as `Request::data(D)` for any `D: Any + Send + Sync`, and juniper's `Context` is a type the schema's root types name, so no adapter can know the user's type by convention. `AsyncGraphql<S, C>` with `C: Send + Sync + 'static` keeps the `ModuleRef` of the module that binds it and resolves `module.with_execution(&exec).get::<C>()` per call, built once in the call's execution, so the context is resolved with the engine's module's visibility and need not be exported to the module serving the endpoint; it inserts the context with `Request::data` as a `Dep<C>`, since the resolver hands back a shared value and `C` is not `Clone`, plus the `ExecutionRef` itself as a second `data`, and `fw_graphql_async::dep::<T>(ctx)` reads `ctx.data::<ExecutionRef>()?.get::<T>()`. `Juniper<Q, M, Sub>` resolves `Q::Context` the same way and hands it over as the context, where the user's `Context` struct holds an `ExecutionRef` field and `fw_graphql_juniper::dep::<T>(ctx)` reads through it. `dep` is therefore engine-specific and lives in each adapter crate under one name. Neither adapter declares `Dep<C>` as a dependency: declaring it would make the engine per-execution under an execution-scoped context, so the binding is read at each call and not checked when the application wires, and a context that is not bound fails each call rather than `wire()`, logged at `error`, answered as `Outcome::Failed`. A resolver that reads the HTTP request does it through the context: the HTTP controller seeds `Dep<RequestHead>` into the execution, so a context built in the call's execution reads it as any execution-scoped binding does, and the SPI needs no HTTP head. The read is a runtime one, which is why a context also built over the subscription gateway or RPC reads `Option<Dep<RequestHead>>`, as the example does. Juniper's `Engine::subscribe` is built on `resolve_into_stream` directly.

- **HTTP:** the endpoint is a controller in `fw-graphql-http`, mounted `.at(config.path)` (§2.5), so role keys and inputs work as for any route, and HTTP guards, interceptors and pre-dispatch entries apply because the endpoint is an HTTP route. It follows GraphQL-over-HTTP, whose rules the endpoint controller applies from `outcome`; the controller is written by hand over the HTTP handler protocol, since `GqlResponse`, `IntoReply` and `Http` are three crates' types and no `IntoReply<Http>` for `GqlResponse` can be written. In `application/graphql-response+json` a request that executed answers 200, errors included, and a request that failed before execution, a document that does not parse or validate, a missing `query`, an unparseable JSON body, answers 400; in the legacy `application/json` media type every response is 200. A `Failed` outcome, a context the server could not build, answers 500 in both: a 400 would tell the client to fix a document it cannot fix. The response media type is negotiated from `Accept` with qualities read per RFC 9110, a type's quality that of the most specific matching range: the response is `application/graphql-response+json` when its quality is nonzero and at least `application/json`'s, and `application/json` otherwise, with no 406. No `Accept`, or only empty ones, negotiates `application/graphql-response+json`, which is how GraphQL-over-HTTP reads it from its 2025-01-01 watershed and what §0.3 leaves to the specification; the consequence is that a client sending no `Accept` receives 400 for a document that does not parse. A POST whose body is not `application/json` is refused with 415. A GET names `query`, `operationName`, `variables` (JSON text) and `extensions` (JSON text) as query parameters, and a GET whose operation is a mutation is refused with 405, built as a `MethodNotAllowed` with `Allow: GET, HEAD, POST, OPTIONS` and offered to the error handlers as the router's 405 is (§3.2), so a 405 has one rule.
- **Subscriptions:** graphql-transport-ws on an `fw-ws` gateway with `event = "type"` and `subprotocols = ["graphql-transport-ws"]` (§4.1). The protocol's `connection_init`, `ping` and `pong` carry no `id` while expecting an answer, and its `complete` from the client cancels an operation, so the `#[fw_ws::message]` convention of §4.2 does not fit and the gateway is a hand-written `Gateway` in `fw-graphql-ws` over `Engine::subscribe`, one for both engines, mounted by `GraphqlModule` at the `subscriptions` path. It owns: the subprotocol echo, a handshake that echoed none closing 4406; `connection_init` once, its payload kept in `Session<ConnectionInit>` for the context builder, a second one closing 4429; `connection_ack`; a `subscribe` before the ack closing 4401; a duplicate `id` closing 4409; an unparseable message closing 4400; an init that does not arrive within `GraphqlConfig::connection_init_timeout(Bound)` closing 4408, 3 seconds at `Default`, the reference server's, `Unbounded` no clock, timed by the app's `Timer`; `ping` answered with `pong`, and `pong` accepted in both directions; one execution per `subscribe`, opened on the connection with its inputs seeded and run in a task of its own, whose stream writes `next` items and `complete`, or `error` with an array of GraphQL errors, a `Failed` outcome among them; `complete` from the client cancelling that execution with `ClientCancelled`; and the context built per execution as above. The timeout lives on `GraphqlConfig` because `GatewayConfig::settings()` is a static function: `GraphqlModule` binds it as a module-private value the gateway reads optionally, and a zero is refused through `try_value` when the application wires, with the one hint every zero bound gets. **Connect guards are this gateway's only authorization point.** They run once per connection, and no `Ws` guard, interceptor or error handler runs per operation: the hand-written gateway has no handler for them to wrap, so a `Ws` guard written expecting to run on every message does not run on graphql-transport-ws. An operation's authorization is decided at `connection_init`, from its payload in the session, or inside the resolvers.
- **Playground:** `fw-graphql-http` serves the page `Engine::playground_html` answers, async-graphql's `GraphiQLSource` and juniper's `graphiql_source`, on a GET with `Accept: text/html` and no `query` parameter, under `GraphqlConfig::playground(bool)`, which defaults to `cfg!(debug_assertions)`; an engine answering `None` serves no page.
- **Two engines:** one `GraphqlModule` serves one engine. A second schema is bound under `dyn Engine` with the DI's ordinary qualifier, `dyn Engine @ Admin`, and a second `GraphqlModule` at another path reads it, `GraphqlConfig::at("/admin/graphql").engine::<Admin>().engine_from(AdminSchemaModule)`, as `Dep<dyn Engine, Admin>`; `engine::<E>()` turns a `GraphqlConfig` into a `GraphqlConfig<E>`, the parameter carried by `GraphqlModule<Q>`, the endpoint controller and `GraphqlWs<Q>`. The configuration is the module's identity, so the same configuration imported twice is one module and two paths are two. No GraphQL rule is added for it.

## 9. Development command [39]

`fw dev`, in `fw-cli` beside `fw new` and `fw generate`, watches the source through `watchexec`, rebuilds (`cargo build`), and restarts. `fw dev --listen 0.0.0.0:8080` holds a listening socket across restarts: the command binds the address **itself** and passes the socket to each child using the socket-activation protocol, `LISTEN_FDS`, `LISTEN_FDNAMES` and `LISTEN_PID`, with the address text as the socket's name, `%` written `%25` and `:` written `%3A`, since `LISTEN_FDNAMES` separates names with `:` and every socket address contains one. `--listen` takes an IP socket address, optionally written `tcp://`; a bare port, a `udp://` address and a host name are each refused with their own message, since the held socket goes to the endpoint written as the same address. The application changes nothing for it. `main` is written `Server::new("0.0.0.0:8080")` in development and in production alike, and under `FW_DEV=1`, which the command sets in every child, `EndpointSpec::resolve` in `prepare` resolves an `Endpoint::Addr` equal to an inherited socket's name to that socket, the address compared as parsed so three spellings of one address match; without the variable, with no name matching, or with inherited sockets the process cannot adopt, a `LISTEN_PID` naming another process among them, logged at `debug` for that case and `warn` for any other, the address binds as written, and the `LISTEN_PID` check keeps a stale variable harmless (§2.7). `EndpointSpec::resolve_as_written` is the lookup-free form, for a client, which connects to the address, and for a socket the activation cannot carry: the TCP client uses it, so a client in a child whose address equals the held socket connects rather than adopts, and the UDP link uses it on both sides, so a UDP endpoint at the held TCP address stays an address. An `Endpoint::inherited(..)` the application writes itself is matched by name as in production. UDP is outside `--listen`: the activation vets every inherited descriptor as a listening TCP socket, so an RPC application on UDP restarts without holding its socket, and the documentation says so.

`LISTEN_PID` has to equal the child's process ID, and `pre_exec` runs between fork and exec where only async-signal-safe calls are allowed and `setenv` allocates. The command therefore re-executes its own binary as a trampoline, `fw __exec -- <child> <args>`, which runs after exec with an ordinary allocator, sets `LISTEN_PID` to `std::process::id()` and `exec`s the child; `exec` keeps the pid, so the variable equals the child's. The trampoline runs only when a socket is held; every child gets `FW_DEV=1` with `LISTEN_PID` removed from its environment, and `LISTEN_FDS` and `LISTEN_FDNAMES` only with a held socket. No shell is involved, and nothing runs between fork and exec but the `dup2` and `fcntl` that place the held socket at descriptor 3 with `FD_CLOEXEC` clear, so the socket survives both execs. In the child, `fw-net` sets `FD_CLOEXEC` on each inherited socket and leaves the three variables set (§2.7), so a subprocess the app spawns inherits neither the sockets nor a `LISTEN_PID` that matches it.

The restart sequence is build, then swap:

1. Each change runs `cargo build --message-format=json-render-diagnostics` with the command's mirrored flags (`--release`, `-p`, `--bin` or `--example`, `-F`, `--all-features`, `--no-default-features`, `--cargo-arg`) while the old child keeps serving. A failed build leaves the running application in place. A change during a build builds again before swapping, so a binary behind the source never starts.
2. A build that succeeds stops the old child with SIGTERM and a two-second grace before SIGKILL, the same grace Ctrl-C gets: an application past it is killed mid-drain, which a development restart accepts in exchange for not waiting out the app's own drain window, ten seconds unset, on every save; an open WebSocket or SSE client holds a restart two seconds and is then cut. The grace has no flag.
3. The new child starts on the same sockets. The binary is the one cargo's artifact messages name, chosen as `cargo run` chooses: `--bin` or `--example`, else the only binary, else the package's `default-run`, else an error naming `--bin`. A child that exits on its own is not reported; the next successful build starts it again.

While no child is accepting, the kernel queues connections in the listen backlog, which `fw dev` keeps open. Clients see a delay, never a refused connection. Socket holding is Unix-only. Off Unix `--listen` is accepted with a warning and the application binds the address itself, so a client can see a refused connection during a restart, and the documentation says so; a Windows handoff (`WSADuplicateSocket` into the child) is the path to add once the Unix one is built.

## 13. Decisions taken with defaults

1. **There is no per-module middleware.** One pre-dispatch stage in two sub-steps covers app-wide work scoped by path, and controller interceptors cover local work, both inside the error chain (§3.3). "Every controller in this module" takes the form of a module tier in the enhancer stack if a case needs it; until then `.at(prefix)` with a pattern-scoped entry covers it.
2. **`Conflict` maps to gRPC ABORTED.** Google's API guidance pairs HTTP 409 with both ABORTED and ALREADY_EXISTS. `CallError::with_grpc_code(..)` overrides it per error, and a `tonic::Status` returned as the error names any code as it stands (§6.2).
3. **`Timeout` renders as HTTP 504.** The server ran out of time, usually waiting on something downstream. 408 means the server gave up waiting for the _client's request_, which is a different situation.
4. **Connect guards run after the 101 handshake** and refuse with a close code, as [23] asks, since a close code is the only refusal a browser can read. `refuse = handshake` on a gateway refuses before the upgrade with an HTTP 401 or 403 instead, as RFC 6455 allows, for non-browser clients and proxy logs (§4.1).
5. **The WebSocket and RPC envelopes are this design's own**, JSON on every gateway and link by default, with MessagePack through `rmp-serde` (`codec = msgpack`, §4.2) and CBOR through `ciborium` (`codec = cbor`, §5.2) opted into per gateway or link. Nothing here aims at wire compatibility with NestJS or socket.io.
6. **A slow WebSocket consumer is disconnected** with 1008 by default, with drop-oldest as an option.
7. **gRPC reflection is on in debug builds and opt-in in release builds.** The GraphQL playground follows the same rule.
8. **`fw dev` socket holding is Unix-only, and holds TCP sockets alone** (§9). UDP is outside `--listen` until the activation vets a datagram socket.
9. **`fw-http-hyper` is the one backend, and actix-http owns no sockets.** An application wanting actix's per-core runtime model embeds in an actix-web host, where the model is kept (§3.8). A second socket-owning path would be a second reference for the conformance suite to keep in agreement, and nothing above it changes if one is added.
10. **The actix embedding declares `upgrades: false`.** actix's upgrade is a payload/body pair bridged across a `!Send` boundary rather than a per-request future, and a gateway on an actix host is refused in `prepare` (§3.8). The limit is the adapter's declaration, so lifting it changes the table and nothing else.
11. **One settings vocabulary.** A byte size is `*_limit: u64`; a count is `max_*: Count`; a time that may be off is a `Bound`, `*_timeout` or named for what it bounds; a time that is a value, never off, is a `Duration`. §3.6, §4.2, §5.3 and §6.2 read it: `message_limit`, `max_connections`, `max_inflight`, `max_outbound`, `ping_interval`, `pong_timeout`, `max_frame`, `max_per_connection`, `connection_init_timeout`. A `Count::Max(0)` or a `Bound::After(Duration::ZERO)` is refused in `prepare` with one hint on every transport (X22).
12. **Brokers carry the payload, not the envelope**, with the correlation in the broker's own mechanism; TCP, UDP and Redis carry the whole frame (§5.2). The request lane stays readable by a broker's own tools.
13. **The competing-consumer group defaults to the root module's full type path** on NATS, MQTT and Kafka, sanitised per broker and overridden with `.group(..)` (§5.2). A fixed name would let two applications on one broker compete for each other's requests with no error anywhere.
14. **A miss is `Timeout` where the link cannot signal it**, Kafka under auto-create, MQTT at QoS 0, and RabbitMQ for a pattern served once, whose queue outlives the server, declared through `Capabilities::miss_signal` for the first two and `Capabilities::holds_unserved` for the third, which Kafka declares too (§5.2). The Kafka link creates its handler topics at `bind` and anchors the group's offsets at their end while the group is empty, so a stopped server's topic exists, a request produced while no instance consumes waits for the next owner, and that case is a `Timeout` on every broker.
15. **`credit` is reserved and unsent** (§5.2). `max_inflight` sheds on every link, and the AMQP prefetch follows it through `Link::max_inflight`, which `Server::prepare` calls beside `Link::prepare`; no link carries a prefetch setting of its own.
16. **WebSocket keep-alive is on by default**, 30 seconds for `ping_interval` and for `pong_timeout`, `Unbounded` turning it off (§4.1).
17. **A connection a connect guard refused never reaches `on_disconnect`** (§4.1). The hooks come in pairs.
18. **The gRPC build step uses a vendored `protoc`** (§6.1). It meets "no system protoc", and a pure-Rust compiler is a later swap behind the same API.
19. **gRPC serves on its own port alone.** gRPC on the HTTP server's port or on an embedding host is outside this design, and §6.2 names the extension point.
20. **Client-certificate verification is not built.** `fw_net::Tls` verifies no client certificate on any transport, and the gRPC example reads a token (§6.1). When built it lands in `fw-net`, once for every transport.
21. **One `GraphqlModule` serves one engine**; a second engine is reached through the DI's qualifier (§7).
22. **A metadata type may name its transport**, and is then refused on every other at compile time (X24, §2.5). A type naming none is valid everywhere.
23. **The gateway on the HTTP server's port is module-driven.** `WsModule` registers the hand-off, and the upgrade handler carries the server's lifecycle (X21), rather than a second socketless server the user binds in `main` (§3.5).
24. **One deadline rule.** A passed deadline on HTTP, RPC and gRPC runs the error handlers with a `Timeout` `CallError` under the server's `timeout_grace`, one second at `Default`, and renders canonically only when the grace passes first (§2.4). The argument that a caller past its deadline has stopped waiting applies to all three alike, and was weighed against the application's need to log, count or reshape its timeouts consistently. The handlers' answer is delivered when it is a single reply produced within the grace; a streamed answer is ended with the canonical timeout and logged at `warn`, since the grace bounds the handlers and not a stream they return, and a caller at its deadline reads nothing. Each transport defines a single reply by its own protocol, RPC a `Reply::One` or `Reply::None`, gRPC one length-prefixed message, HTTP a body that completes within the grace, HTTP having no message boundaries; a single payload written through `Body::stream` is delivered, and an `Sse`, which never ends, is not. A body judged by its `size_hint` instead would cut a single reply sent through `Body::stream`, a false positive its author cannot see coming.
25. **A gateway is served on one port.** `port = http | own` on the gateway attribute selects the hand-off or `fw_ws::Server`, `http` unset, and no gateway is served on both (§4.1). A `port = own` gateway in an application binding no `fw_ws::Server` is served by nothing and reported by nothing, since no module sees whether the server exists.
26. **A prefix nothing reads is refused.** `Transport::READS_PREFIX` says whether a transport reads `.at(prefix)`, `false` unless declared, and the freeze refuses the prefix on a controller none of whose handlers' transports do, or that mounts no handler (X25, §2.5). `Ws` answers `true` beside `Http` and `WsConnect`, since a controller with message handlers mounts its gateway's connect handler too. A controller mixing HTTP routes with gRPC methods keeps its prefix for the routes.
27. **The RPC call shape is read from types, never from spelling.** An `Inbound<T>` parameter and a stream reply are each found by an autoref probe, the reply's over the generated call closure's future output, so an alias or an opaque type counts and no attribute overrides the read (§5.1).
28. **Broadcasts travel as JSON** between processes and are re-encoded per gateway on delivery, so one publish serves gateways of both codecs; a byte string reaches a MessagePack gateway as an array of numbers (§4.3).
29. **Connect guards are graphql-transport-ws's only authorization point.** No `Ws` guard, interceptor or error handler runs per operation on that gateway, and the documentation of gateways states it (§7).
30. **A broker link connects once at `bind`.** An unreachable broker is one `StartupError::Bind` at startup, not a retry loop; a retry window is a `Bound` to add when a deployment needs one (§5.3).
31. **A module-level setting is refused at `wire()`.** `RpcClientModule::timeout`, `GraphqlConfig::connection_init_timeout` and a `GrpcEndpoint` URI live on modules, which have no `prepare`; each is recorded through `try_value` and reported with the wiring errors, which precede any socket as `prepare` does (§5.4, §6.3, §7).
32. **A host's drain behavior is declared and asserted, never noted.** `drain_pending`, `drain_abandoned` and `drain_http2` on `EmbedLimits` (§3.8) record what each host was observed to do, and a scenario checks each in both directions; a note asserts nothing, and a host's next version changes the behavior unseen. actix declares `DrainPending::Closed` rather than its `run` delaying `stop(true)` past `stopping()`, which would add a second signal to work around one host, or actix-web being pinned below 4.15, which trades a declared limit for a version trap; and it declares `DrainHttp2::Reset` in every build, since Cargo unifies features and the adapter cannot read whether another crate turned actix-web's `http2` on.
33. **No conformance scenario passes on silence**, in either suite (§3.8, §5.2). A request the client's timeout ends fails its scenario unless the scenario is about a timeout, and a scenario that cannot apply to a host or link is declared in the stamping macro and reported ignored, never passed. salvo's listener held open through the drain was the first thing the rule caught. A scenario that fails while its environment starts names the underlying error: each suite's `report` joins every cause under `source()`, and every startup path panics with it, so a broker container, a bind or a connect that fails is reported with its chain rather than as a timeout downstream.
34. **A broker's hold is declared, and the declaration is asserted.** `holds_unserved` lets the drain scenario accept the caller's `Timeout` on RabbitMQ and Kafka, and the scenario then shows the hold by delivering an event emitted during the drain to the next instance; `durable_replies` lets the recovery scenario require the held call's answer on Kafka, and the environment shows the cut and the outage, observed by the relay rather than arranged by a sleep, the handler's answer moment standing for the publish with a second to spare (§5.2, §5.3). Declaring either scenario not applicable would hide a stronger property than the one it skips.
35. **A client link ends its reply lane on a lost connection** rather than carrying calls across a reconnect (§5.3). A reconnect that lets in-flight calls vanish reports nothing; the RabbitMQ client drops lapin's auto-recovery for the same reason, and the next call connects again anyway. Kafka's reply topic loses nothing, so its client keeps the reconnect and declares it.
36. **The salvo server stays the caller's.** `run` takes `salvo::Server<Closing<A>>`, the public `Closing<A>` acceptor closing the listener when the drain begins, rather than building the server itself over a private wrapper, which would lose `with_http_builder`, `http1_mut`, `http2_mut` and `fuse_factory`; the type requires the wrapper, `Closing::new` registers the acceptor with the handle both sides share, and `run` sends the stop once `listeners_closed()` resolves, which pairs the two through the handle with no extra parameter and no dependence on salvo's poll order; a `Closing` from another handle is refused before serving, a warning there leaving `run` nothing to wait on (§3.8).
37. **A Kafka group anchors its offsets at `bind` while it is empty** (§5.2), the one moment Kafka accepts the commit; a topic added while the group runs starts at its end on each assignment until a handler settles a record there, and the documentation says so.
38. **`RpcClientModule` closes its link on the app's destroy hook** (§5.4), as the server's `close` closes its links, so a client link's connections do not outlive the app on any link: TCP's writers are owned by the link and awaited, UDP's reply lane owns its socket, and Redis's publisher and Kafka's producer are taken out of the slot the `RpcClient` keeps until its next call. The suite's client-close scenario holds every link to it and requires the close's report clean, since a hook the core drops at its bound ends the link's tasks itself and would pass a `close` that did nothing.
39. **A heavy environment bounds its own suite.** `Broker::PARALLEL`, `None` unless declared, holds each stamped scenario to a slot from before `start` until its environment is dropped (§5.2). Kafka declares four: a container per scenario keeps offsets, topics and the relay cut apart with no namespace, and a container exiting before its ready line fails its scenario rather than retrying, the exit being a symptom of a host running short.
40. **Generated code is lint-clean in the user's crate** under clippy's default set with `-D warnings` (§1). `fw-macro-lints` expands every attribute and derive macro over a proto `fw-build` compiles, and CI's `generated code lints` job lints that crate alone on stable clippy, the cost being a red job on a change unrelated to the macros when a new lint arrives. The existing test crates carry hand-written code with warnings of their own, which `-D warnings` would fail on code no user inherits. An `allow` goes into the generated code where the lint is one the user cannot act on: the reply-shape probe's diverging closure (§5.1) and the marker module named as its wrapper (§6.1).
